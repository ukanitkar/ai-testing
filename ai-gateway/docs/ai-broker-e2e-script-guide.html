ai-protect · commands/

What every AI Broker e2e script does

The commands/ directory holds two generations of test tooling: the current, actively-maintained e2e suite documented here, and an earlier set of one-off manual debugging transcripts from before it existed (listed at the end, for context, not detail). This guide covers only the former — the orchestrator, its elevated companion, every script it runs automatically, and the manual follow-ups it names by name for the cases it deliberately doesn't automate.

01Orchestrator & elevated companion

Every other script in this guide is called by, or answers requests from, one of these two.

run-e2e-suite.ps1
entry pointdestructive

The main orchestrator — runs all 14 numbered steps in order, in one non-elevated window as umesh.

Deploys fresh binaries, starts the service, and works through privilege-drop verification, TLS/token checks, unit suites, ACL checks, the credential and config-delta watchers, the MCP relay, and four negative cases (protocol mismatch, the enable/disable transition, the parent-death watchdog, graceful shutdown) ending with --recover. Stops on the first failing step rather than continuing through all 14 and reporting at the end. -SkipDestructive skips the last four teardown-heavy steps; -IncludeReboot opts into restarting the VM.

Runpowershell -File \\tsclient\Z\commands\run-e2e-suite.ps1
run-e2e-suite-elevated-helper.ps1
separate windowread-only bridge

A file-drop request/response server that does the one thing the non-elevated orchestrator structurally cannot.

Runs in its own elevated (Administrator) PowerShell window for the whole suite's duration, polling C:\ai-broker-test\elevated-request.json every 750ms. Answers exactly six hardcoded actions — sc-query, sc-stop, sc-start, psinfo, cargo-test-elevated, read-daemon-log — and nothing else: the request carries only an action name (plus a regex pattern/tail for the log-read action), never a command or path, specifically so a file drop can't become a privilege-escalation primitive.

Runpowershell -File \\tsclient\Z\commands\run-e2e-suite-elevated-helper.ps1in an elevated window, before starting the suite
02Run automatically — the 14 steps

Called by run-e2e-suite.ps1 itself, via Run-Phase or a background job. Listed in the order the orchestrator invokes them.

phase-a-acl.ps1
Step 6read-only

Confirms the broker's secret files carry an owner-only, protected DACL.

Checks llm-proxy.token, .credentials.json, and mitm-ca-key.pem for exactly one ACE (the writing user, full control, not inherited), plus a control file (mitm-ca-cert.pem) expected not to be locked down. Exists because the Rust code's own restrict_to_owner calls discard their Result, so a DACL failure would otherwise be silent. Run as umesh deliberately — a file's owner always holds READ_CONTROL regardless of what the DACL says, which is what makes the non-elevated identity the correct one to check from.

phase-b-cred-watcher.ps1
Step 7read-only

Proves the credential-refresh edge-trigger fires end to end.

Ages the cached JWT sidecar directly (sets zax_expires_at to now) and polls daemon.log for the resulting credential_requested: false→true flip and the subsequent broker.json rewrite — even though the pushed credential itself is still an empty daemon-side stub. Restores the original sidecar afterward.

phase-b-config-apply.ps1
Step 8destructive

Exercises the Windows ownership reassignment behind config-delta merges, both the happy path and the defense.

Positive: observes the already-live codex ConfigDelta land in .codex\config.toml, confirming the file's owner was reassigned via SetSecurityInfo — a path unit tests can only skip without SeRestorePrivilege. Negative: briefly stops the broker (not the daemon), hand-crafts a status.json naming .ssh/authorized_keys, and confirms the daemon's allowlist refuses to write it. Backs up and restores the real config file, then forces a broker respawn.

phase-c-mcp-stdio.ps1
Step 9read-only

Drives the --mcp-server stdio relay directly, since no real MCP client is installed on the test VM.

Codex isn't on this VM, so this pipes six raw JSON-RPC lines (initialize, ping, tools/list, a notification, an unknown method, invalid JSON) into ai-broker-mon.exe --mcp-server over stdin and checks the replies by id: capabilities advertised, exactly 4 replies (the notification and invalid JSON draw none), and the unknown method returns JSON-RPC -32601. Run by the orchestrator inside a background job under a 60-second watchdog — a hang here is itself a finding (interactive OIDC on an aged-out cached credential is the documented risk), since the script sets no exit code of its own for the job to check.

phase-c-protocol-mismatch.ps1
Step 10read-only

Proves a broker.json protocol-version mismatch refuses cleanly and recovers, without ever touching the live service.

Spawns a fully isolated --control under its own ZAX_DEMO_HOME and proxy port (:18788, never :8788), writes a bad protocol_version by hand (must produce ready:false and an empty agents[]), then a good one (must recover to ready:true). Because the sandbox skips the real bootstrap flow entirely, it has to hand-build everything bootstrap would have: config.yaml, two distinct init.yaml files, a working directory holding a copy of the SDK's bundled config, and a credential seeded from the live broker's own sidecar so recovery doesn't need an interactive OIDC login.

phase-c-negative-setup.ps1
Step 11, part 1destructive

Restarts the mock device plane on a fast 60-second heartbeat so the enable/disable test below doesn't wait up to 10 minutes for the daemon to notice.

The daemon only adopts a pushed heartbeat cadence after receiving one, which itself needs a heartbeat at the current (slow, 600s default) cadence — so this restarts the service immediately afterward to short-circuit that: a service restart heartbeats right away. Confirms /config serves the fast cadence before handing off.

phase-c-negative-flip.ps1
Step 11, part 2destructive

The actual negative test: flips ai_broker.enabled to false and confirms the daemon reaps the already-running broker.

Tests the enabled→disabled transition specifically — not just a fresh start with the toggle already off — by bumping the mock's config version with enabled:false and polling daemon.log for a new "stopped ai-broker-mon" line within 150 seconds, then confirming the process is actually gone and the port released.

phase-c-watchdog.ps1
Step 12destructive

Confirms the LLM-proxy child exits on its own when its parent dies, instead of orphaning the port.

Identifies the parent/child PIDs via whichever process owns :8788, kills only the --control parent, and polls for the --llm-proxy child to notice and exit within seconds, then for the port to release. Before commit f5c3e367 there was no Windows watchdog at all, so an orphaned proxy would squat on the port until killed by hand.

phase-d-recover.ps1
Step 14destructive, last

The last and most involved step: verifies --recover's dry-run safety, its real teardown, and a deliberate self-heal gap in the daemon.

Dry-run first (must change nothing) → real run (kills both broker processes via a toolhelp32 sweep, strips codex's MCP entry, drops the cached JWT) → verifies each specific claim → proves the broker stays dead for 90 seconds with no new settings frame, since reconcile() has exactly one call site and never fires on a timer → restores a session-backed-up credential so the forced respawn that follows doesn't need an unattended, un-clickable OIDC round → polls the final state until the box is fully restored.

03Run by hand — named by the orchestrator, not automated

run-e2e-suite.ps1 deliberately excludes two cases from its automatic run and names these scripts, by filename, as the way to run them: the "nobody logged on" negative case (needs a real RDP logoff of the session running the suite) and reboot-survival (opt in with -IncludeReboot, otherwise run these by hand after a manual reboot).

phase-e-nobody-setup2.ps1
elevateddestructive

Arms a SYSTEM-hosted mock device plane that survives a real logoff, then tells the operator to log off.

Registers phase-e-mock-wrapper.ps1 as a SYSTEM Scheduled Task (ZaxMockDevicePlane) so the mock keeps answering heartbeats after the console session ends — a plain child process would die with the session. Confirms the task is serving the unchanged config version, then instructs a genuine shutdown /l (a mere RDP disconnect leaves the session as WTSDisconnected, which still counts as logged in) within about two minutes.

Thenlog off → wait 5–6 min → log back in → run phase-e-nobody-check2.ps1
phase-e-mock-wrapper.ps1
templateread-only

The template phase-e-nobody-setup2.ps1 fills in and registers as the scheduled task's actual target.

Not run directly. A scheduled task doesn't inherit the creating session's environment, so this file's env vars are literal __PLACEHOLDER__ tokens substituted by the setup script before the filled copy is written to C:\ai-broker-test\phase-e-mock-wrapper-filled.ps1 and registered. Kept as its own file because schtasks' quoting for a nested powershell -Command string gets unreliable fast.

phase-e-nobody-check2.ps1
after logging back indestructive

Verifies the SYSTEM-context fallback fired while nobody was logged on, then tears down and restores.

Confirms the scheduled-task mock survived the logoff, checks daemon.log for the fallback spawn line and the current process/port state, then tears down the scheduled task and restarts the mock normally with a bumped config version — polling up to 90 seconds for the daemon to notice and launch the broker back in the user's own session.

phase-b-prep.ps1
non-elevatedread-only

Brings the mock device plane back up after a manual reboot, before re-verifying the stack.

Copies the mock script locally first (so it doesn't depend on \\tsclient\Z staying mounted, which evaporates if the RDP session drops), starts it detached if not already running, and confirms /health. Hands off to starting the service from the admin window, then phase-b-verify.ps1.

Thensc.exe start AiBrokerTest (admin window) → phase-b-verify.ps1
phase-b-verify.ps1
non-elevatedread-only

Confirms the daemon and broker came back up correctly after a reboot, using cached credentials rather than a fresh login.

Checks process ownership/session (daemon SI=0, broker SI=console), whether :8788 is listening, and tails daemon.log/zax.log for the spawn, status-ready, and cached-credential lines — the whole point being that ready:true should be reached with no interactive OIDC round, proving the cached JWT survived the reboot.
