AI Broker · Control-Plane Reference

How ai-protect and the AI Broker talk to each other

Every process, message, and boundary crossing between ai-protect and ai-broker-mon, one mechanism per diagram — sequence, schema, and the code that backs each step.

01 Bootstrap & the control handshake

Superseded — the control socket is gone

This diagram documents the Unix-socket / named-pipe start_up / register_agent handshake as it existed before the file-protocol migration. There is no socket or named pipe anymore — ai-protect and ai-broker (ai-gateway) now exchange broker.json / status.json snapshots, each watched independently. See Diagram 09 for what actually runs today. Kept here as a historical record of the design this replaced.

What happens between ai-protect deciding the AI Broker should run, and the broker's local LLM proxy reporting itself ready — every process born, every message exchanged, and the privilege boundary each one crosses.

Scope

This covers the sequence triggered by a settings.received frame carrying ai_broker.enabled: true: spawning ai-broker-mon --control, the start_up / register_agent handshake, and the two background watchers it starts. It stops at the point the LLM proxy reports itself listening — the traffic that later flows through that proxy (Diagram 03) and through the MCP relay an agent spawns on its own (Diagram 02) are separate diagrams.

Every zax-anchor: … tag below marks a one-line comment placed directly above the matching code, e.g. grep -rn "zax-anchor(ai-broker-control-plane): boot-1-spawn-broker" — grep for the slug rather than trusting a line number, which drifts.

Who runs as whom

ai-protect daemon

root · LocalSystem

Always privileged. Never touches agent config or the network the broker uses — it only spawns, supervises, and exchanges control messages.

ai-broker-mon --control

console user

macOS: dropped via setgid/setuid to the /dev/console owner. Windows service: CreateProcessAsUserW into the active session. Linux: not dropped — stays root (no portable console-session primitive; accepted gap).

ai-broker-mon --llm-proxy

same as --control

A child of the already-dropped control process, so it inherits that identity directly — no second privilege drop.

Sequence

Walkthrough

  1. Trigger

    The heartbeat republishes tenant config as a settings.received trigger. The ai_broker.launch subscriber reads payload.settings.ai_broker.enabled — absent leaves the current state alone; true calls reconcile(true), which is a no-op if the broker is already up.

  2. spawn_broker() — cross the privilege boundary

    On a Windows service, CreateProcessAsUserW crosses from session 0 into the active console session; on macOS, the root daemon forks and drops uid/gid/full group set to the /dev/console owner via the existing utils::exec primitive.

    zax-anchor: boot-1-spawn-broker — src/subscribers/ai_broker_launch.rs On Linux there's no portable console-session primitive (no shelling to loginctl from a root daemon), so the broker simply inherits root. Accepted for now — revisit if Linux desktop deployment becomes a real target.
    If no user is logged on, or the crossing fails, the daemon falls back to spawning the broker in its own context and logs it; the next settings tick reconciles again.
  3. The handshake runs off-thread

    Steps 2–8 all run on a detached thread, not the settings-tick thread — start_up can block on interactive OIDC, and the settings.received subscriber is Sync and must not stall.

    zax-anchor: boot-2-connect — src/subscribers/ai_broker_launch.rs
  4. start_up: identity + credential handoff

    The daemon sends the bound user's email/id, the resolved per-user broker home, and whatever identity::zax_user_credential::fetch returns. That fetch is a stub today (always "not available"), so in practice user_jwt/refresh_token arrive empty and the broker falls back to its own cached refresh token, then interactive OIDC.

    zax-anchor: boot-3-start-up — src/subscribers/ai_broker_launch.rs
  5. The broker starts its own child

    ControlService::start_up sets ZAX_DEMO_HOME, stages the pushed credential into env, picks the LLM leg's identity (ZAX_AGENT_ID, default codex) and upstream, then spawns ai-broker-mon --llm-proxy as a plain child process — it inherits the already-dropped user, so no second privilege drop happens here.

    zax-anchor: boot-4-spawn-llm-proxy, boot-5-listening, boot-6-started-up — ai-broker/mon/src/control/service.rs
  6. Agents get pushed, not diffed

    The daemon walks its own discovery inventory, maps each client label to a broker agent id, and opens a fresh short-lived connection per agent to send RegisterAgent. It does not track what it already sent — the broker owns dedup (registered: HashSet<String>) and the accept filter (default {codex}, widened via ZAX_CONTROL_AGENTS).

    A rejected start_up (protocol-version mismatch, or no reply at all) aborts the handshake here — the daemon never pushes agents to a broker it couldn't start. zax-anchor: boot-7-register-agent — src/subscribers/ai_broker_launch.rs
  7. First sight writes config

    An accepted, not-yet-registered agent gets wired via its adapter: the broker writes (or, in stage mode, renders a ZIP for ai-protect to apply) an MCP server entry pointing at ai-broker-mon --mcp-server — a command the agent itself will launch later, as its own MCP subprocess. That launch, and everything it exchanges with the gateway, is Diagram 02.

    zax-anchor: boot-8-agent-registered — ai-broker/mon/src/control/service.rs
  8. Two watchers start immediately, not after the handshake

    ensure_credential_watcher and ensure_config_apply_watcher are called right after the spawn succeeds (see the diagram's dashed loop) — they don't wait on the handshake thread. Both are plain 3-second polls today (a stand-in for the daemon's event-driven services::watcher): one watches a credential-request touch-file the broker uses to ask for a fresh credential near expiry; the other watches every user's config-staging/*.zip, relevant only when ZAX_CONFIG_SINK=stage.

    zax-anchor: watcher-credential-request, watcher-config-apply — src/subscribers/ai_broker_launch.rs

When ai-protect talks to the broker

Four independent triggers decide it — two are events the daemon reacts to immediately (push), two are conditions the daemon has to notice itself (poll). There's no fifth path: the broker can never open a connection back to the daemon.

Why two of these are polls, not pushes

The control transport is one-shot and daemon-initiated only (listener.rs: "the broker never holds a live reverse channel"). So the broker can't hand the daemon a credential request or a config ZIP directly — it can only leave something for the daemon to find: a touched file, a dropped ZIP. Both watchers are plain polling threads today, a deliberate stand-in for promoting them to the daemon's event-driven services::watcher later.

Config hand-off, and writing it without a race

What ai-protect actually receives depends on the broker's config_sink:

write (default)

The broker writes the agent's config file itself, as the console user. ai-protect receives no bytes at all — only the ConfigReport already shown in AgentRegistered above: which file, and whether it was wired, unchanged, or removed.

stage (ZAX_CONFIG_SINK=stage)

The broker renders the config instead of writing it, and drops the real content in a ZIP under that user's ~/.ai-broker/config-staging/. ai-protect is then the one that writes it to disk.

// config-staging/codex-<ts>.zip → manifest.json {"agent":"codex", "os_user":"umesh", "files":[{"path":"/Users/umesh/.codex/config.toml", "entry":"files/0"}]} // + one zip entry per file (the rendered content itself)

Two independent guards keep that write from racing anything, one per side of the socket:

Broker side — one mutex, however many connections

Every accepted control connection runs on its own async task, but all of them share exactly one ControlService behind an Arc<Mutex<…>>. So when the daemon's initial discovery push and a later rescan-triggered push land at the same moment — genuinely possible, since on_agent_rescan spawns a fresh thread per event — the two register_agent calls simply serialize on that lock. The in-memory dedup set (registered) and the proxy handle never see a concurrent mutation.

zax-anchor: concurrency-broker-mutex — ai-broker/mon/src/control/listener.rs
ai-protect side — one watcher, an atomic write, and two gates

Only one config_apply_watcher thread ever exists (an AtomicBool guard in ensure_config_apply_watcher makes a second broker restart a no-op to start it again), and it walks users' staging dirs sequentially — never two applies in flight at once. Each file write then goes through write_atomic_under (temp file + rename, so it's atomic regardless of anything else touching that path), gated by containment (the target must resolve under that same user's home — a ZIP can never write outside the directory it was found in) and an explicit allowlist (today: only .codex/config.toml — a hostile or malformed manifest naming ~/.ssh/authorized_keys is rejected outright).

zax-anchor: watcher-config-apply — src/subscribers/ai_broker_launch.rs

02 MCP leg — the tool-call relay

What happens once the agent actually runs, and spawns ai-broker-mon --mcp-server the way its config was wired to in Diagram 01: how it discovers upstream MCP servers, and how one tools/call reaches a real server and comes back.

Scope

This is entirely the agent's doing — ai-protect and the daemon are not involved at all once the config is wired. The agent (Codex, say) spawns this relay itself, over stdio, the same way it would spawn any local MCP server. Everything below happens as the console user; there is no privilege boundary in this leg.

Who runs as whom

Agent (Codex CLI, etc.)

console user

Already running as whoever is using the machine — this leg never touches a privileged process.

ai-broker-mon --mcp-server

same as the agent

A plain child of the agent's own process. No CreateProcessAsUserW, no setuid — it inherits the agent's identity directly, because the agent that spawned it is already the right identity.

Sequence

Walkthrough

  1. The agent spawns the relay itself

    Codex (or whichever agent) launches ai-broker-mon --mcp-server as a plain stdio subprocess — the same way it would launch any local MCP server, because that's exactly what its config says to do (wired back in Diagram 01, step 8). Nothing about this crosses a privilege boundary.

    zax-anchor: mcp-1-spawn — ai-broker/mon/src/bridge.rs
  2. Discovery: a Vector read, not a gateway call

    After the same sdk_init pipeline the LLM leg uses (OIDC → register → activate → token-exchange), the relay calls list_brokers — this asks Vector (the registry) which MCP servers this tenant can route to. Each one comes back with its brokered endpoint already rendered; the relay composes nothing itself.

    zax-anchor: mcp-2-list-brokers — ai-broker/mon/src/bridge.rs
  3. Every upstream handshakes concurrently, and a failure just drops it

    For each broker, ZaxClientSession::for_broker_url connects (a no-op — streamable HTTP holds no live socket), then sends a signed initialize and list_tools, each bounded to 15 seconds. Total startup is bounded by the slowest upstream, not their sum — and a stalled or failing one is dropped, never fatal to the relay.

    zax-anchor: mcp-3-handshake-upstream — ai-broker/mon/src/bridge.rs
  4. One flat, namespaced tool list

    Every connected upstream's tools get merged into one list the agent sees, each renamed <server>_<tool> so two servers can both have a tool called search without colliding. A live VM run found 14 configured upstreams, 11 connected, 233 tools aggregated this way.

  5. stdin in, one task per request, one writer for stdout

    The agent's requests arrive as newline-delimited JSON-RPC on stdin. Each line is dispatched onto its own task — so a slow tool call never blocks tools/list behind it — but exactly one task owns writing to stdout, serializing every reply so two concurrent tool calls can never interleave half-written JSON.

    zax-anchor: mcp-4-serve-stdio — ai-broker/mon/src/bridge.rs
  6. tools/call relays through the gateway, and failures stay inside the result

    The relay looks up which upstream owns the requested (namespaced) tool, locks that upstream's live session, and sends a signed tools/call POST to the same gateway URL used at handshake — the RFC 9421 signature, the triple-JWT X-Zax-Authorization header, and a fresh x-zax-trace-id go on every call, exactly like the LLM leg. Any failure — timeout, upstream error — becomes {isError: true} in the JSON-RPC result, never a JSON-RPC protocol error, so the agent sees "this tool failed," not "this server crashed."

    zax-anchor: mcp-5-tools-call-relay, mcp-6-signed-post — ai-broker/mon/src/bridge.rs, ai-broker/sdk/src/forwarding/mcp/session.rs

03 LLM leg — the reverse-proxy inference call

The proxy from Diagram 01 is already listening. Here's what happens to one real inference call the agent sends through it — and the sleight of hand at its center: the agent thinks it's talking to api.anthropic.com; the bytes never go there directly.

Scope

Covers one request from the agent hitting https://127.0.0.1:<port>/<token>/v1/messages to the response streaming back. The token+TLS gate at the front door is Diagram 01's subject; this is what happens once a request gets past it.

Who runs as whom

Agent

console user

Configured to send its LLM calls to the local proxy's origin instead of the provider directly (e.g. ANTHROPIC_BASE_URL). Its own provider credential travels unchanged.

ai-broker-mon --llm-proxy

same as --control, from Diagram 01

The same child process Diagram 01 spawned. Holds one signing context, fixed to one agent + one upstream at spawn time.

Sequence

Walkthrough

  1. The agent's own credential travels unchanged

    Whatever bearer token or API key the agent authenticates to the provider with rides through should_drop_request_header untouched — the ZAX identity is layered on as a separate X-Zax-Authorization header, never mixed with or replacing the provider auth. The broker never reads or mints a provider credential.

  2. The proxy builds a request to the REAL provider

    llm_proxy::forward constructs a plain reqwest request against {upstream}{path} — e.g. https://api.anthropic.com/v1/messages — on the SDK's signing client. At this point, as far as the code building the request is concerned, that really is where it's going.

    zax-anchor: llm-1-proxy-handler, llm-2-forward — ai-broker/mon/src/llm_leg.rs, ai-broker/sdk/src/forwarding/llm_proxy.rs
  3. ZaxMiddleware intercepts before anything leaves the process

    It requires activation to already be complete (a live instance JWT + HMAC key) — refusing immediately with "Stage 2 (activation) not complete" if not — computes the RFC 9421 signature over the original URL, gets a fresh triple JWT, and only then rewrites the request's scheme/host/port to the gateway's. The original host is preserved verbatim in the Host header — a standard reverse-proxy pattern — so the signature covers what the caller actually asked for, not what the wire ends up carrying.

    zax-anchor: llm-3-middleware-rewrite — ai-broker/sdk/src/forwarding/middleware.rs
  4. Same signing shape as the MCP leg, different rewrite strategy

    Both legs sign with RFC 9421 + the triple JWT and land at the gateway. The MCP leg (Diagram 02) already knows the gateway URL — Vector handed it one per upstream — so it POSTs there directly. The LLM leg doesn't: the agent's config only ever named the real provider, so the middleware has to rewrite the destination in flight rather than being given it up front.

  5. The response streams back essentially unchanged

    Framing headers (content-length, transfer-encoding, content-encoding, connection) are stripped and recomputed, but the body streams straight through — this is what lets a streaming completion keep streaming, rather than being buffered whole.

Message schema — the rewrite, before and after

04 Credential lifecycle & renewal

Superseded — no more request-flag file or PushCredential message

credential-request (a touched flag file) and the socket's PushCredential/CredentialApplied exchange are both gone. ai-broker now recomputes status.json.credential_requested fresh on every tick (a pure function of the cached JWT's expiry), and ai-protect edge-triggers on its false→true transition to refetch and rewrite broker.json — see Diagram 09. The four-tier precedence below (env → sidecar → refresh-token → interactive OIDC) is unchanged; only how a fresh credential arrives at tier 1 changed.

The user JWT the broker signs with doesn't live forever. Two independent triggers feed the exact same renewal machinery: the broker noticing its own credential is aging, and every proxy (re)spawn re-running a four-tier precedence to decide which credential to actually use.

Scope

This is Diagram 01's PushCredential/CredentialApplied exchange (mentioned there, not detailed) plus what happens on both sides of it: what makes the broker ask in the first place, and what a fresh proxy spawn actually does with whatever shows up.

Sequence

The precedence a fresh spawn actually runs

Every --llm-proxy spawn — at bootstrap, at mid-life renewal, or after --recover — runs the exact same four tiers, in this order, stopping at the first one that yields a usable JWT:

  1. 1. Env — pushed by ai-protect this session

    ZAX_USER_JWT / ZAX_REFRESH_TOKEN, staged by push_credential above. Usually empty today, since the daemon-side fetch is a stub.

  2. 2. The sidecar's cached JWT

    ~/.ai-broker/.credentials.json — whatever the last successful init settled on, persisted for exactly this reuse. Checked for freshness (a 300-second buffer before its claimed expiry) before being trusted.

  3. 3. Refresh-token renewal — no browser

    If a refresh token is available (from either tier above), the SDK calls the IdP directly to mint a new access token. This is the tier that keeps a long-running broker credentialed for real, without ever popping a browser — if the IdP actually issues a refresh token for this client (gated on the tenant granting the offline_access OIDC scope).

  4. 4. Interactive OIDC — last resort

    Opens a browser for a fresh login. The only tier a headless/unattended respawn (like this mid-life bounce) can't complete on its own — which is exactly why tiers 2–3 matter: they're what let renewal happen without a human present.

Whatever it settles on gets persisted back

The resulting JWT, its expiry, and any refresh token are written back to the sidecar — so the next spawn's tier 2 has something fresh to try, and the maintainer's own wake-up timer (tied to that same expiry) knows when to fire again.

05 Config ownership — write vs. stage

Superseded — there is no more "write" mode, and no ZIP

The direct-write config-sink mode is retired: on the --control path, ai-broker never writes an agent's config file itself anymore, in either mode. It reports a ConfigDelta (a JSON object naming only the paths to change) in status.json; ai-protect merges it into the real file — generically, for TOML or JSON targets — preserving every path the delta doesn't mention. No ZIP, no manifest, no config-staging/ directory. See Diagram 09. (The standalone Claude-Desktop bootstrap mode — ai-broker-mon with no arguments — is untouched by this and still writes Claude's config directly; it doesn't go through --control at all.)

Back in Diagram 01, step 8 said the broker "writes (or, in stage mode, renders a ZIP for ai-protect to apply)." Here's the one thing that actually differs between those two modes — and the one thing that's identical, which is easy to assume isn't.

Scope

register_agent's config_sink setting (env ZAX_CONFIG_SINK, default write) decides who ends up touching the agent's real config file on disk. Both modes share everything up to that decision; they only diverge at the last step.

The one difference

Why stage exists at all

Write mode is simpler and synchronous — good enough as long as the broker is trusted to write directly into a user's config. Stage mode exists for the opposite premise: ai-protect wants to be the single writer of every agent config on the box, broker-authored or not, so the same containment/allowlist gate and the same write_atomic_under primitive that already guards every other config write in the daemon also guards this one. The broker computes what should be written; ai-protect still decides whether to actually write it.

The zip is deliberately minimal

stage_zip writes manifest.json ({agent, os_user, files:[{path, entry}]}) plus one files/N entry per file, uncompressed (Stored — these are tiny text files, and it means the daemon needs no zlib dependency to read them back), and chmods it 0600 on Unix. os_user is a courtesy cross-check only — Diagram 01's watcher trusts the staging directory's actual owner, not this field, as the authoritative identity.

zax-anchor: config-1-register-agent-branch, config-2-stage-zip — ai-broker/mon/src/control/service.rs

07 Full component & trust-boundary map

Every earlier diagram zoomed into one mechanism. This is the zoom-out: every process, every remote service, and every boundary — privilege and network both — that the six diagrams above ever crossed, on one page.

The whole system

What's the same across every leg

One SDK, four independent identities

--mcp-server and --llm-proxy both link zax_sdk and both run the same register → activate → exchange pipeline — but each registers under its own agent identity (a Codex MCP leg and a Codex LLM leg are two separate registrations), not a shared one.

The gateway is the only thing that talks to the real world

Neither leg ever dials a real MCP server or LLM provider directly. Every brokered byte passes through the ZAX gateway, which is what makes inspection, policy, and attribution possible in the first place.

Diagram-by-diagram, this map is: privilege drop + spawn (01), the --mcp-server leg's traffic (02), the --llm-proxy leg's traffic (03), how the signed identity itself gets renewed (04), how agent config gets written (05), and which of all this differs on Windows (06).

08 Where ai-protect and ai-broker can — and can't — break each other

Both sit on the same agent, both touch the same agent's config, and every tool call passes through both. That sounds like a recipe for collisions. In practice most of it is structurally impossible — but one real gap isn't, and it gets wider as more agents get enabled.

Scope

Codex, concretely, since it's the one agent actually wired today (accepted_agents defaults to {codex}). The shape generalizes to any future agent that has its own native "which MCP identities may I use" hardening surface.

The two files, and the one thing that reads both

Can it actually break the other?

interactionverdictwhy
enforce_mcp allow/block policy CAN break ai-broker Any non-empty allow or block list — even one an admin wrote for unrelated servers — makes Codex's managed allowlist authoritative. "zax" isn't auto-included on either side, so an admin who's never heard of the broker can silently disable it. No longer silent, though: ai-protect now pushes the resolved decision — including whether "zax" survives it — to the broker as an Advisory control message, and the broker mirrors it to ~/.codex/advisory.json. The exclusion still happens exactly the same way; it's now visible next to the broker's own config instead of only inside a root-owned file.
Per-MCP-server block/audit hook rule CAN break ai-broker (over-broad) The broker presents as one server, "zax", no matter how many real upstreams sit behind it. A rule aimed at one specific upstream tool can only match/block at the "zax" level — everything behind the broker, or nothing.
config_apply_watcher (stage mode only) CAN break ai-broker (self-inflicted) In stage mode ai-protect's own watcher is the only thing that ever writes [mcp_servers.zax] — see Diagram 05. A stalled or paused watcher means the broker's own wiring never lands, with no error on the broker's side to say why.
Widening accepted_agents multiplies the first risk Every newly-enabled agent that ships an equivalent native "which MCP identities may I use" hardening feature inherits the same silent-exclusion shape — worth checking per agent before enabling it.
ai-broker writing requirements.toml CANNOT happen Root-owned, mode 0644. The broker always runs as the console user, never root — the OS itself refuses the write. Not a convention; a permission bit.
ai-protect's hook install racing ai-broker's config write CANNOT happen For Codex, ai-protect never writes ~/.codex/config.toml — its hook and MCP-policy writes both land in requirements.toml only. Two different files, so there's no read-modify-write race to have in the default (write) config-sink mode.
ai-broker disabling ai-protect's hooks or policy CANNOT happen No code path in ai-broker touches requirements.toml, the hook-enforcement subscriber, or any policy state. It has nothing to remove or overwrite even if it wanted to.
The asymmetry is the point worth remembering

ai-protect can veto ai-broker in three concrete ways, at every granularity from "block one call" to "disable the whole leg." ai-broker cannot touch ai-protect's enforcement at all, by construction — different file, different owner, different permission bits. Enforcement always wins; the advisory only changes how the broker finds out, not what happens.

The enforce_mcp row is the only one of the three with a mitigation today — advisory.json covers the case ai-protect can compute in advance (the allow/block resolution). The other two — an over-broad per-server rule, and a stalled config_apply_watcher — still fail exactly as silently as before; they'd need their own advisory to close the same gap.

09 The file protocol — broker.json / status.json

This is what actually runs today, replacing the Unix-socket / named-pipe control channel diagrams 01, 04, and 05 documented. No persistent connection exists anymore: ai-protect and ai-broker (ai-gateway) each write one file, full-snapshot, for the other to watch — independently, on their own poll loop.

Scope

The two files' schemas (shared via the ai-types crate's broker module, so a rename is a compile error on both sides), the write/watch loop on each side, and the two things ai-protect does in reaction to a status.json change: refetch a credential, and merge a config delta into an agent's real config file.

10 AI Gateway crate split

From the 2026-08-26 design meeting's whiteboard: the AI Gateway (product name; behaviorally still "ai-broker") decomposes into named components — BrokerJsonManager, Agent Manager, StatusJsonManager, Credential Manager, per-agent Listeners, and the SDK. Each whiteboard box now maps to its own crate, plus one shared infra crate the whiteboard doesn't name. ai-broker-mon is left as a thin orchestrator binary that wires the rest together.

Built 2026-08-26

The mechanical split landed the same day it was whiteboarded: six new crates (ai-gateway-broker-json, ai-gateway-status-json, ai-gateway-credential-manager, ai-broker-paths, ai-gateway-listener, ai-gateway-agent-manager), control/service.rs deleted, ai-broker-mon/bootstrap.rs/recover.rs/control/{watcher,sim_daemon}.rs rewired onto them. 75 tests migrated or added across the new crates, all passing; cargo clippy clean across every touched crate; the full workspace (including the unrelated ai-warden daemon, at 2345 tests) still builds and passes together.

Crate summaries

ai-gateway-broker-jsonbroker-json/

Watches broker.json for real changes (first sight, a path switch, or a genuine mtime change — BrokerJsonWatcher::changed) and parses it into the shared ai_types::broker::BrokerFile schema. No agent logic, no state beyond "have I seen this file before." 4 tests.

ai-gateway-status-jsonstatus-json/

The write half of the file protocol: serializes a StatusFile and writes it out, creating parent directories as needed. No owner-chown step — ai-broker already runs as the target user by the time it writes this. 1 test.

ai-gateway-credential-managercredential-manager/

Owns the .credentials.json sidecar and the user JWT only — load/save, the 300s freshness buffer, and the env-var push/clear that downstream code reads. The instance JWT and triple JWT stay inside ai-broker-sdk; this crate was briefly considered for all three layers and deliberately kept narrow. 9 tests.

ai-broker-pathspaths/

Shared filesystem conventions — home-dir resolution, the Claude config/settings paths, the MITM CA dir, the --llm-proxy shutdown-flag and token paths, per-OS Claude Desktop binary lookup, backup-file naming. Not a whiteboard box; factored out because Agent Manager, Listener, and the orchestrator binary all needed the same ~20 functions. 4 tests.

ai-gateway-listenerlistener/

The actual traffic path: the shared LLM reverse proxy (llm_leg), the CONNECT-MITM forward proxy for knob-less agents (forward_proxy + mitm), and the stdio MCP relay (bridge). Deliberately does not depend on Agent Manager — where it needs per-agent-adapter knowledge (registration identity, forward-proxy launch hints) it takes an IdentityFn/HintsFn function pointer supplied by the caller instead, so the crate graph stays acyclic. 23 tests.

ai-gateway-agent-manageragent-manager/

The one true hub, matching the whiteboard: AgentManager::apply reconciles a fresh BrokerFile into a StatusFile — protocol-version check, pushing credential changes, spawning/renewing the shared proxy, and driving all 18 agent adapters (agents/, moved wholesale, unchanged). The only crate that talks to Credential Manager, Listener, and the SDK's adapters in one place. 12 tests.

ai-broker-sdksdk/ (unchanged)

Registration flow, RFC 9421 request signing, RFC 8693 token exchange, and forwarding to Optimus. Keeps the instance-JWT activation lifecycle and triple-JWT caching in-house — the two JWT layers Credential Manager doesn't own. Already its own crate before the split; untouched by it.

ai-broker-monmon/ (thinned)

What's left once everything above moved out: the CLI, the standalone Claude-Desktop bootstrap mode (bootstrap.rs, recover.rs — a flow the whiteboard doesn't cover), and control/ — now just watcher.rs (polls BrokerJsonManager, hands snapshots to AgentManager::apply, writes the result via StatusJsonManager) and sim_daemon.rs. control/service.rs, the old reconciler, is deleted — fully superseded by Agent Manager. 22 tests.
