AI Broker — Design Record

Brokering AI coding agents' MCP and LLM traffic through the ZAX gateway, from an endpoint component shipped inside ai-protect, on managed Mac and Windows laptops. Beyond Claude: a per-agent adapter model covering fourteen agents, a multi-provider LLM path (reverse-proxy + CONNECT-MITM forward-proxy legs), and the identity/auth model both legs sit on. The SDK, proxy, bridge and adapters are portable Rust; the host-integration hooks are OS-specific — see Platforms.

Context and goal

The AI Broker makes an unmodified Claude Desktop route its outbound traffic through the ZAX gateway, so Zscaler can broker it. Two independent legs:

  • MCP leg — tool calls to tenant MCP servers, discovered from the vector broker catalog rather than configured locally.
  • LLM leg — Anthropic API inference calls.

It is a Rust port of the Python zax-sdk-python/demo/claude-desktop-agent, moved out of demo territory and into ai-protect so it can eventually ship as a ZCC component daemon. The port is not a rewrite — module names and control flow deliberately mirror cli.py, mcp_bridge.py and friends so the two can be diffed.

v2.0 — beyond Claude. What began as a Claude-Desktop broker is now agent-general. A per-agent adapter model registers the broker's MCP server into fourteen agents' native configs, gated by a product enablement allowlist (Claude, Gemini, ChatGPT/Codex, Copilot). The LLM leg grew a second mechanism — a CONNECT-MITM forward proxy for agents with no base-URL knob — and this revision documents the identity/auth both legs depend on, plus a live end-to-end result that located the real remaining blocker (a gateway capability grant, not code).

Key constraint the port had to solve

The Python SDK monkey-patches httpx, so any outbound call is transparently signed and routed. Rust has no such seam. The design answer: the SDK's signed reqwest_middleware client is the routing — every path that must be brokered explicitly holds that client. Nothing is transparent, which is more code but a far more auditable data path.

Placement and build isolation

The broker lives under ai-protect/ai-broker/ as two new Cargo workspace members, following the precedent already set by ui and endpoint-ext: a workspace member that is not a dependency of the daemon.

Why this shape

  • The daemon runs as root. Anything in its build graph is attack surface running with full privilege. The broker pulls in an HTTP server, a JSON-RPC loop, and OIDC — none of which belong there.
  • It sidesteps a blocked build. ai-protect depends on the private GitHub crate ai-types, which can't be fetched in every environment. Because the broker crates are self-contained, cargo build -p ai-broker-mon works where a full build doesn't.
  • It matches the eventual shipping model. ZCC's master daemon launches component daemons; the warden launching ai-broker-mon is the same relationship one level down.

Platforms — Mac & Windows

The broker targets managed macOS and Windows laptops (Linux is detected but not a shipping target). The portable core — the SDK, the loopback LLM proxy, the CONNECT-MITM forward proxy, the stdio MCP bridge, and the per-agent adapters (paths resolved through dirs::home_dir() / env) — runs identically on both. What differs is a small set of host-integration hooks: launching the desktop app, elevating for a privileged cleanup, supervising child processes, and protecting on-disk key material. Several of those are macOS-only in the current tree and are enumerated here as Windows work.

Design principle — portable core, per-OS edges

OS specificity is confined to the host-integration edges (launch, elevation, supervision, key perms), each behind a cfg gate; the brokering data path is identical on both. So "add Windows" is a bounded set of edge implementations, not a second port — and the shape mirrors ai-protect itself (root on macOS, LocalSystem on Windows).

Process model — one exe, several modes

ai-broker-mon is a mono-executable. Mode is selected by flag; the run modes (--mcp-server, --llm-proxy, --llm-forward-proxy, --control, --sim-daemon, --recover) are mutually exclusive, and recovery-only flags refuse to fall through to the bootstrap. Two diagnostics (--agents, --configure-llm) are read/apply utilities that exit immediately:

InvocationRoleWho starts itLifetime

--controlDaemon control listener — start_up / register_agent / push_credential over a Unix socketThe warden daemon (or --sim-daemon)Long-lived; supervised

One binary means one artifact to build, sign, notarize and ship — and it lets a mode re-spawn itself: paths::resolve_self_command() canonicalizes current_exe(), and that absolute path is what gets written into Claude's config, because Claude Desktop spawns children from its own working directory.

Testing harness — --sim-daemon

The broker's real driver is the ai-protect daemon over the control socket. To exercise the broker without a full daemon — which, on a host that already runs one (e.g. a ZCC-managed ai-protect), would collide on the IPC socket, hooks and enrollment — ai-broker-mon --sim-daemon plays just the control-driver slice. It reuses the real control::protocol types (so it can't drift from the contract) and, as the invoking non-root user, does exactly what the daemon subscriber does for a Codex smoke test:

  1. spawn ai-broker-mon --control --socket <path> (inherits the user — no privilege drop),
  2. drive start_up — credentials/attribution from env (ZAX_USER_JWT, ZAX_REFRESH_TOKEN, ZAX_BOUND_USER[_ID], ZAX_TENANT, ZAX_DEMO_HOME; all optional — absent ⇒ the broker falls back to its refresh token / OIDC, as in the real flow),
  3. drive register_agent(codex),
  4. idle so the --llm-proxy stays up for LLM-leg testing; reap the broker on Ctrl-C.

It touches none of ai-protect's daemon machinery (no IPC socket, storage, enrollment, discovery, or hook install), so it can run alongside a real ai-protect without interfering. It covers interface #1 (start_up) and interface #2 (register_agent) end to end against a live broker + proxy.

Scope — what it deliberately does not simulate

Hooks: none. Hooks are ai-protect's event/telemetry path (AI tools shelling out to the client on events); the broker never consumes them, so there is nothing hook-shaped for the broker side to receive. Real agent discovery: no — it hardcodes a single register_agent(codex), so it does not run scan_inventory(), the label→broker-id map, or the broker's filter/dedup across multiple agents. It simulates the result of discovery for one agent, not the act. (The harness lives in the ai-broker-mon crate, which doesn't link the daemon, so it can't call ai-protect's scanner; it could instead push the broker's own is_installed() adapters to exercise the multi-agent filter/dedup path — a possible extension.)

Agents & the adapter model

v1.1 wired Claude by hand. v2.0 replaces that with a per-agent adapter seam (mon/src/agents/) — one AgentAdapter per agent that knows how to detect it, where its config lives, and how to point its MCP (and, where possible, LLM) traffic at the broker and undo it. bootstrap drives wire_installed_mcp() over every enabled+installed agent; recover drives unwire_other_agents(). The config surfaces mirror ai-protect's own discovery schema (utils/discovery/schema.rs), so the broker writes exactly the shape the daemon already reads.

Capability vs enablement — two independent axes

Capability (supports_mcp / supports_llm_base_url / supports_llm_forward_proxy) is what an adapter can technically do. Enablement (ENABLED_AGENTS = Claude, Gemini, ChatGPT/Codex, Copilot) is the product allowlist of what bootstrap actually wires. All fourteen ship adapter code; non-enabled agents ship dark. An agent is wired only when enabled && installed && supports_* — so "enable an LLM leg" is a one-line flag flip once its mechanism is verified.

Deliberately not adapters

VS Code is scoped to login/subscription, not MCP, per product direction. OpenClaw / Amp / Aider have no MCP config surface in ai-protect's discovery schema — there is nothing to write.

Bootstrap sequence

Bootstrap is idempotent by design — every step is an ensure_* that no-ops when already satisfied. The single exception is deliberate: force_reauth() deletes the credential sidecar on every run, so OIDC always re-runs fresh.

Two one-time chores run first. migrate_legacy_home() renames a pre-existing ~/zax-demo to the hidden ~/.ai-broker (an atomic same-filesystem move, so the cached JWT and .llm_upstream aren't orphaned by the rename); it is skipped when $ZAX_DEMO_HOME is set explicitly. On macOS, cleanup_legacy_managed_mcp() removes any stale managed-mcp.json — its exclusive mode is incompatible with Claude Desktop's Code tab — prompting a macOS admin dialog to do so.

Ordering that matters

capture_original_upstream() runs before ensure_user_settings_policy(). Otherwise the proxy would snapshot its own address as the forward target and loop. The captured value lands in .llm_upstream, which is also what makes a clean restore possible later.

Likewise the LLM proxy starts after OIDC, so it reuses the just-cached JWT instead of racing a second interactive sign-in.

The MCP leg

Rust has no MCP server crate, so the stdio JSON-RPC server the agent talks to is hand-rolled in bridge.rs — newline-delimited JSON on stdin/stdout, protocol version 2024-11-05. Upstream servers are driven through the SDK's ZaxClientSession. The same bridge serves any agent that spawns --mcp-server from its config (§Per-agent integration), not just Claude — the diagram uses Claude Desktop as the concrete example.

Verified against the dev tenant: 214 tools advertised from 11 of 11 brokers (three legitimately expose zero tools and are reported rather than hidden), with the Claude config SHA-256-identical before and after a --mcp-server run — the mode only reads Claude's files, and a full run left stderr at 0 bytes, proving nothing but JSON-RPC touched the stream.

Design choices in the relay

  • Namespaced tool names <server>_<tool> — the server component is the broker label (slug, falling back to name then id), and the session map is keyed by that same label. Multiple upstreams coexist in one flat MCP surface; collisions keep the first and log a warning.
  • Errors as results. A JSON-RPC error would make Claude treat the whole server as broken. isError: true keeps the session alive and lets the model react to a single failed call.
  • Sessions stay open per upstream, so mcp-session-id survives across calls.
  • Concurrent handshakes — startup cost is the slowest upstream, not their sum.
  • Catalog-driven. Brokers come from vector at init — list_brokers() does a POST {api}/vector/v1/sdk/brokers, and each broker arrives with a fully-rendered gateway_url (https://<gateway>/<slug>/mcp). The gateway (Optimus) brokers the traffic but has no catalog endpoint of its own. config.yaml's mcp_servers list is a legacy fallback used only if the fetch returns nothing.

The LLM leg — multi-provider

Every brokered LLM call ends the same way — at the gateway's reverse face in front of the real provider. What differs is how the agent's traffic gets there, and that splits into two mechanisms by whether the agent exposes a base-URL knob.

MechanismHow the agent reaches the gatewayBase-URL knob?Agents
Reverse proxy (base-URL)agent's *_BASE_URL → local proxy → gatewayrequiredClaude (live), Codex (gated), Devin (capable)
Forward proxy (CONNECT-MITM)agent's egress → local CONNECT proxy (MITM) → gatewaynone neededCopilot, Cursor, Windsurf, Gemini-OAuth

Reverse-proxy leg (base-URL agents)

An axum reverse proxy on 127.0.0.1:8788 (override: ZAX_LLM_PROXY_PORT). The agent is pointed at it — Claude via ANTHROPIC_BASE_URL, Codex via a [model_providers.zax] table + model_provider="zax". Requests are re-issued through the SDK's signed client, so they exit via the gateway.

The transport is provider-agnostic. forward() prepends any upstream origin to the request path and ZaxMiddleware signs + routes to the gateway; only the defaults were Anthropic-specific. So --llm-proxy --upstream https://api.openai.com --port 8789 runs an OpenAI proxy from the same binary — the SDK forward test already exercises a non-Anthropic upstream.

Upstream resolution is layered and defensive — resolve_llm_upstream():

  1. ZAX_LLM_UPSTREAM env override, else
  2. the captured .llm_upstream state file, else
  3. https://api.anthropic.com

Two guards then run unconditionally: if the candidate points at the proxy's own origin it is discarded (loop guard), and if upstream_is_safe() rejects it as cleartext off-host it is discarded too. Either way it falls back to the Anthropic default rather than failing.

"Reverse" is deliberate: Claude has no proxy configured — it believes 127.0.0.1:8788 is the Anthropic API, and the destination is ours (from config), not named in the request. The ZAX gateway one hop later is a forward proxy, so the leg runs a reverse and a forward proxy back-to-back. That is why the gateway needs no route for /v1/messages: our proxy re-addresses each request into the absolute-form the gateway forward-proxies, with the Host header preserved so it still lands on the real origin. A forward failure returns 502 with a zax_llm_proxy_error body.

Forward-proxy leg (knob-less agents)

Copilot, Cursor, Windsurf and Gemini's OAuth path have no base-URL knob. For them --llm-forward-proxy (port 8790) runs a local CONNECT proxy: it answers CONNECT host:443 with 200, terminates TLS with a leaf minted on the fly for that SNI by a local ai-broker CA (the agent trusts it via NODE_EXTRA_CA_CERTS), then the decrypted inner request re-enters the same reverse handler (llm_leg::build_app) with upstream = https://<connect-host> — so the SDK re-signs and routes to the gateway, reusing the reverse leg's SSE-safe streaming.

Why local MITM (D1), not a relay to Optimus's own forward face (D2)

Optimus attributes identity from the SDK's signed request headers (X-ZAX-Authorization / RFC-9421 signature). A raw request forward-proxied straight to Optimus carries none of that — its forward-proxy auth is only a static proxy_auth_token, so per-user ZAX identity would be lost. Hence the proxy must terminate TLS locally, re-sign, and chain to the gateway. Two CAs: the local ai-broker CA the agent trusts vs. the cloud Optimus CA (never exposed to the agent). mitm::LocalCa mints/persists the CA key 0600 and per-SNI leaves; unit-tested.

Forward proxy — gated, three open edges

HTTP/2: ALPN is pinned to http/1.1 for now (a client insisting on h2 fails). e2e: compile-verified + CA/resolver unit-tested, not yet run against a live agent+gateway. Env injection: nothing sets HTTPS_PROXY/NODE_EXTRA_CA_CERTS for a user-launched CLI — the proxy currently just logs what each installed agent needs. Bootstrap does not start it yet.

Optimus is both a forward and a reverse proxy

The gateway decides its role per connection on a shared listener. A CONNECT request → its forward face (CONNECT + optional TLS interception), for app/browser traffic that can't be pointed at a base URL. A host-matched request → its reverse face — an API gateway in front of ~21 providers (config/providers/*.yaml, matched by domain + uri-path), including all four priority endpoints: Anthropic, OpenAI (/v1/chat/completions + /responses), Google (incl. the Gemini CLI's cloudcode-pa.googleapis.com), and GitHub Copilot. ai-broker deliberately uses a local forward proxy + the gateway's reverse face, precisely to keep per-user identity (above). See the companion message-flow diagrams.

Caveat — brokered ≠ inspected to full depth

Optimus's deepest role-tagged prompt extraction (the ai_metadata pipeline) fires only for OpenAI + Anthropic, string-valued content, today. Other providers are still brokered and inspected, but via the array-aware inline content-guard fallback — less granular.

Identity, auth & credentials

The central identity decision

The broker registers as Claude Desktop, not as itself. sdk_init() passes agent_metadata.software_path pointing at the installed Claude Desktop binary, and the SDK derives everything from that app: name and version from Info.plist, a hash of the executable, and the Developer-ID code signature (Anthropic PBC).

So the tenant sees a governed Claude Desktop, which is the thing security policy is actually about — not an anonymous relay. Nothing about identity is configured in init.yaml.

Binary discovery is per-OS and best-effort: macOS walks /Applications then ~/Applications reading CFBundleExecutable; Windows picks the highest-versioned app-* directory under %LOCALAPPDATA%/AnthropicClaude. Linux returns None.

The six-stage SDK pipeline

Both child modes enter through sdk_init(), which runs the vendored SDK's pipeline (sdk/src/startup.rs). It splits across two control-plane hosts under api.<cloud> — vector (register + broker catalog) and bumblebee (activate + token-exchange) — before the traffic ever reaches the gateway.

StageCallResult
1 · CONFIG—Shipped init.yaml plus the per-agent overrides
2 · AUTHENTICATEOIDC (browser)zax_user_jwt — skipped when a token is supplied
3 · REGISTERPOST {api}/vector/v1/sdk/agents:register + :statusAgent identity; 10 s poll, 300 s timeout
4 · ACTIVATEPOST {api}/bumblebee/v1/activationsinstance_jwt + HMAC material
5 · EXCHANGEPOST {api}/bumblebee/v1/token-exchangeRFC 8693 → the triple JWT (X-ZAX-Authorization)
6 · FORWARD—Build the signed, gateway-routing client

Stages 4–6 all sit downstream of REGISTER, so an unapproved (pending) registration fails sdk_init() and takes both legs with it. Server-side this is solved with an auto-approval policy (bumblebee-admin) that stamps x-agent-auto-approval so vector approves inline — the dev tenant returns status="approved" on poll #1. The policy carries no version or hash dimension, which matters because the broker registers as Claude Desktop and derives software_hash from its auto-updating binary; without it, every Desktop update would open a fresh pending window.

Which identity carries the caps — instance vs agent type (open)

The pipeline mints identity at three granularities: REGISTER yields an agent_id (a registered agent record — e.g. 1cffd6be-…), ACTIVATE an instance_id / instance_jwt (a specific activation instance), and token-exchange the triple JWT whose intersected_caps are minted from this instance_jwt × this zax_user_jwt. So the caps are carried per-instance, per-user — the instance sense, not the abstract agent type.

The nuance: because the broker registers as Claude Desktop, the software identity has a type-flavoured component (the app it impersonates), and approval carries no version/hash dimension — so the effective identity is "this user's Claude Desktop on this device." And the admin-granted set that intersected_caps is intersected against lives entirely server-side (Bumblebee / dashboard), which the broker never sees. So where a grant is scoped — per agent_id, per user, per device, or per agent-type/policy across the tenant — is a gateway-side question not answerable from the broker code; the broker only observes the intersected result in its own triple JWT. Worth pinning down on the gateway side.

Credential flow

ModeCredential behaviourUser-visible
bootstrapDeletes the sidecar, runs full interactive OIDC, caches the resultBrowser opens
--mcp-serverLoads .credentials.json, passes the cached JWT into InitOptionsSilent
--llm-proxySame cached pathSilent

This is what makes per-session spawning viable: Claude Desktop starts a fresh bridge for every Code session, and none of them may block on a browser. The tradeoff is that the cache is the single point of freshness — hence REFRESH_BUFFER_SECONDS = 300, refreshing before expiry so the bridge never presents an already-dead JWT to the gateway.

The cached token lasts ~24 hours, so a cache miss — and with it a browser window from a process the user never launched — is a roughly daily event; whether a human must act then depends on the IdP session, not the broker (see Open issues). And the sidecar is written only after the whole pipeline succeeds, so a run that registers and then waits for approval caches nothing. In production both concerns are moot: the harness supplies AID_USER_JWT and the SDK never runs OIDC.

Credential renewal — three tokens, three owners

Three JWTs are in play, with different lifetimes and different machinery keeping each alive:

TokenLifetimeRenewed bySelf-renews?
user JWT zax_user_jwt~24 hOIDC; cached in the sidecarNo — re-runs interactive OIDC on expiry
instance JWT~24 h (its exp)InstanceJWTManager background task — re-POST /activations at exp − 300 sYes
triple JWT~1 hjwt_util token-exchange; in-memory cache keyed by sha256(user|instance), refreshed exp − 300 sYes — while its inputs stay valid
Can the user JWT be self-renewing?

Not today. Unlike the instance JWT, nothing renews the user JWT without a browser: oidc_login keeps only the resulting JWT (no refresh_token), the sidecar persists only zax_user_jwt + zax_expires_at, and there is no grant_type=refresh_token path anywhere. When the cache goes stale the loader "will run interactive OIDC"; in a headless process oidc_login instead warns "inject a new ZAX_USER_JWT" and fails.

It could be made so, via standard OIDC refresh: (1) request offline_access in the scope, (2) capture the refresh_token, (3) persist it in the sidecar, (4) add a refresh path (a background loop like InstanceJWTManager, or refresh-on-use). Caveats: the IdP governs it — refresh tokens expire, rotate and can be revoked, and session/MFA policy may still force periodic interactive re-auth — and a stored refresh token is a durable bearer secret needing tighter protection than a 24 h JWT.

So there are three ways to survive the ~24 h user-JWT expiry without a browser prompt — the same problem solved from opposite ends:

ApproachWho renewsStatus
Interactive OIDCthe user (browser)current behaviour
AID_USER_JWT handoffZCC / the daemon supplies itdesigned, not wired — the intended production path
Refresh-token self-renewalthe broker itselfnot built; feasible with the four steps above + IdP support

Bound user id vs user JWT

A recurring confusion — they are different kinds of thing. The bound user id (ai-protect's enrolled users.id) is a stable identifier — a name, not a secret, doesn't expire, not verifiable on its own. The user JWT is a signed, ~5-minute credential — a bearer secret, self-verifiable, and the input that mints the triple JWT. The id usually appears as a claim inside the JWT, so you can read the id from a JWT but never the reverse: an id can't become a JWT without the user authenticating. This is why "the daemon knows the bound user" isn't enough to skip OIDC.

The AID_USER_JWT handoff — designed, not built

The intended production model has the resident daemon inject the ZAX user JWT so the SDK skips OIDC (a root daemon can't open a browser). Status:

LayerProvide-JWT-from-ZCCEvidence
SDK✅ designedStartupOptions.zax_user_jwt — supplied ⇒ skips OIDC
ai-broker-mon❌ not wiredsdk_init reads its own cached sidecar; no AID_USER_JWT read
daemon (ai_broker_launch)❌ TODO.env("AID_USER_JWT", …) is commented-out

And ai-protect cannot currently obtain that user JWT. It holds a device credential (wdc_) + the bound-user id, and it discovers other agents' tokens presence-only — but it has no client for the ZAX control plane (no Vector/Bumblebee/oidc_login code; that lives entirely in the broker SDK). So closing the handoff needs a capability that doesn't exist yet: either the backend mints a broker user token from the device identity, or SSO-enroll is extended to capture a broker-scoped ZID token. Until then, ai-broker-mon doing its own OIDC is the only working path.

TLS trust and how the agent authenticates

Transport to the dev/private gateway is server-authenticated TLS: the gateway presents a leaf chaining to the private Zscaler Agentic Root CA (config/ZaxDevRoot.crt), which the SDK adds on top of the native / webpki roots — without it a bare client fails the handshake with unknown-issuer. Public hosts (api.anthropic.com, the prod endpoints) validate against the native store. The loader trusts every config/*.crt, plus an optional forwarding.ca_bundle PEM path (null by default) for an enterprise CA — so ZaxDevRoot.crt is the only cert file shipped today, but not the only trust anchor in play.

There is no TLS client certificate — the link is not mTLS. The agent proves who it is at the application layer: an RFC 9421 HTTP message signature (signature / signature-input) plus the triple JWT in X-ZAX-Authorization. The only private key the broker holds is the P-256 activation keypair in the per-agent home, used for AID activation and request signing, never for TLS. (Diagram 2's gateway leg is labelled accordingly.)

⚠️ Corporate TLS interception breaks the gateway leg but not the control plane. The symptom is telling: REGISTER/ACTIVATE succeed against api.<cloud> (public roots) while the broker list or a tools/call fails to connect. Diagnose with openssl s_client -connect gateway.<cloud>:443 | openssl x509 -noout -issuer — an issuer like CN=Bad Server Certificate is the inspection layer substituting its rejection cert, and no client-side CA bundle fixes it. Exempt the host or stop the interceptor.

Reproduce it

This exact sequence is codified in ai-broker/scripts/verify-llm-gateway.sh (sourcing the step-harness common.sh): it runs the ZCC preflight, starts the proxy, sends the no-key and — when OPENAI_API_KEY is set — keyed probes, and prints the broker's forward/status lines. The key is read from the environment and kept out of ps/logs. The manual steps below are the same thing, spelled out:

# Build (from the ai-protect repo root)
cargo build -p ai-broker-mon

# Prerequisite — confirm the gateway host is NOT being TLS-intercepted by ZCC
echo | openssl s_client -connect gateway.zsagenticdev.ai:443 \
     -servername gateway.zsagenticdev.ai 2>/dev/null | openssl x509 -noout -issuer
#   ZCC off → issuer=CN=Zscaler Agentic Root CA          (real cert — test valid)
#   ZCC on  → issuer=CN="Bad Server Certificate ..."     (intercepted → stop ZCC)

# Run the LLM leg as a localhost proxy for the OpenAI/Codex provider
ZAX_DEMO_HOME="$HOME/.ai-broker" \
  target/debug/ai-broker-mon --llm-proxy --upstream https://api.openai.com --port 8789
#   six-stage init runs; a stale cached JWT triggers an interactive OIDC browser login

# The proxy terminates TLS with a locally-minted leaf (mitm.rs's CA) and gates every
# request on a per-install token as the leading path segment — read it once the
# token file appears (it's written just before the proxy starts listening):
TOKEN="$(cat "$HOME/.ai-broker/llm-proxy.token")"
PROXY="https://127.0.0.1:8789/$TOKEN"

# Probe 1 — no key: proves the request reaches the provider through the gateway.
# -k skips verifying our own freshly-minted, self-signed local CA (fine here; pass
# --cacert "$HOME/.ai-broker/mitm-ca/mitm-ca-cert.pem" instead for a stricter check).
curl -sSk -X POST "$PROXY/v1/chat/completions" \
     -H 'content-type: application/json' \
     -d '{"model":"gpt-4o-mini","messages":[{"role":"user","content":"ping"}]}' \
     -w '\nHTTP %{http_code}\n'

# Probe 2 — real key: the key rides the Authorization header, forwarded UNCHANGED to the
# provider; the ZAX identity is layered on separately (X-ZAX-Authorization + RFC 9421 sig)
read -rs OPENAI_API_KEY && export OPENAI_API_KEY       # prompt without echo / no shell history
curl -sSk "$PROXY/v1/responses" \
     -H "Content-Type: application/json" \
     -H "Authorization: Bearer $OPENAI_API_KEY" \
     -d '{"model":"gpt-5.4-mini","input":"write a haiku about ai","store":true}' \
     -w '\nHTTP %{http_code}\n'
unset OPENAI_API_KEY

# Watch the broker's own view (forward target + status)
tail -f ~/.ai-broker/logs/zax.log
#   [forward] POST https://api.openai.com/v1/responses → gateway=gateway.zsagenticdev.ai:443
#   [llm]     POST /v1/responses -> 200
Prerequisite — shut off ZCC for any Optimus test

Zscaler Client Connector intercepts the gateway host and makes the broker's request fail misleadingly (502 on a TLS deny cert, or an HTTP 403 block page) whether or not the broker works. Stop ZCC — or allow-list the gateway host — before testing, and confirm with the openssl cert check above (real issuer = Zscaler Agentic Root CA).

Open — what do the capabilities gate, then?

Forwarding succeeds with intersected_caps=[], so caps do not gate basic LLM forwarding on the dev gateway. Either enforcement is permissive in dev, or caps gate governance (prompt inspection / policy / logging) rather than transport — in which case traffic may be relayed but not brokered when caps are empty. Confirm with the gateway/dashboard team (Open issue 8).

Daemon integration

The warden reaches the broker through one subscriber, src/subscribers/ai_broker_launch.rs, on the settings.received trigger — the same frame settings_apply consumes. The ai_broker setting is object-valued, matching the net_egress and scan_governor precedent.

The control plane — as built

Reconcile only starts the process; the integration proper runs over a Unix control socket (newline-JSON, contract in ai-broker/mon/src/control/protocol.rs). On a successful spawn the subscriber drives the following off-thread (start_up may block on OIDC, so it must not stall the settings tick):

  • start_up (control_handshake) — passes the bound-user identity + per-user home + the ZAX credential (from identity::zax_user_credential::fetch, a stub returning "unavailable" today, so the broker falls back to refresh-token → OIDC).
  • register_agent × N (push_discovered_agents) — ai-protect's real scan_inventory() mapped to broker ids (client_label_to_broker_id, incl. vscode → copilot) and pushed; re-fired on agentcfg.rescan / inventory.rescan / the periodic scan tick. The broker filters (default: codex) and dedups.
  • credential-request watcher — polls the broker's credential-request flag; on a near-expiry touch it fetches + pushes a fresh credential (push_credential).
  • config-staging apply watcher — sweeps each user's ~/.ai-broker/config-staging/ and applies the broker's staged config ZIPs as the owning OS user (write_atomic_under + fchown), so ai-protect is the single writer of agent config.

Because the broker crate is kept out of the daemon build graph, the subscriber can't link protocol.rs — it hand-mirrors the same JSON. Supporting cast: settings_store (the ai_broker.enabled toggle), triggers/registry (subscriber registration), bound_user + identity/zax_user_credential (identity / credential source), identity/home + utils/atomic_write (per-user, owner-scoped applies), and utils/discovery (the inventory scan). So the ai-protect side is one hub module (ai_broker_launch.rs) plus this cast — see the integration note's "ai-protect side — as built".

Remaining blockers before this ships
  1. Run as the bound user. The daemon is root/LocalSystem; the broker edits ~/.claude/settings.json, binds loopback and launches GUI apps. It must run in the logged-on user's session — per-session on multi-user hosts. Privilege drop is platform-specific.
  2. Credential source. The identity handoff is now wired — start_up carries user_jwt / refresh_token so the SDK can skip interactive OIDC (a root daemon can't open a browser). What's missing is the source: identity::zax_user_credential::fetch is a stub returning "unavailable", so the broker still falls back to refresh-token → OIDC. Live testing surfaced two IdP/gateway-side gaps too: offline_access must be enabled on the zax.client OIDC client before a refresh token is issued (the code now requests it only when advertised), and codex must be added to Vector's allowed frameworks before the proxy can onboard (register currently 400s).
  3. Per-user home. Point ZAX_DEMO_HOME at the bound user's ~/.ai-broker rather than the daemon's. (The subscriber's TODO comment still writes the old ~/zax-demo — stale relative to the current default.)

As written it spawns in the daemon's own context — workable for a rootless dev run, wrong for production. The broker crates now build and test clean in isolation (105 tests green), but the subscriber itself lives in the daemon crate, which still needs the private ai-types dependency to compile — so it isn't exercised where that dep is unavailable.

Open issues

1 · The LLM leg cannot currently be opted out of

Bootstrap writes ANTHROPIC_BASE_URL into ~/.claude/settings.json — the user-level file shared with the Claude Code CLI. Testing MCP brokering therefore also redirects every terminal Claude session's inference through the proxy.

There is no flag for this today. Options: add --no-llm, skip ensure_env_base_url(), or run bootstrap under a throwaway HOME. Worth deciding before the first run, since the write backs up and then overwrites.

2 · An empty tenant catalog makes the test inconclusive

Upstream MCP servers come from list_brokers() against vector. If the dev tenant's broker catalog is empty the bridge starts cleanly, advertises zero tools, and proves nothing. Confirm the catalog is populated before treating a run as a pass.

3 · Registration is not locally reversible

sdk_init() performs registration/activation against the dev registry, minting a server-side agent identity. Because force_reauth() wipes the sidecar every bootstrap, each run re-registers. No amount of local cleanup undoes this — the dev tenant accumulates records.

And no (agent_id, release_id) handle is persisted, so every bridge spawn re-runs REGISTER too — harmless while vector is idempotent per agent (same agent_id, fresh registration_id), but a pending-approval window would multiply pending agents.

4 · Teardown — resolved since the first draft

The earlier gap (no uninstall or restore mode) is closed: reversal is now the built-in --recover mode described below, which replaced the external claude-recover.py. It still cannot undo the tenant-side registration (issue 3).

5 · Config is written before brokering is proven

Bootstrap patches settings.json (step 5) but doesn't reach sdk_init() / OIDC until step 7. A failure in between exits with ANTHROPIC_BASE_URL pointing at a proxy that never started — Claude Code broken until --recover. The fix is to gate the base-URL flip on wait_for_llm_proxy succeeding; the MCP registration writes are harmless by comparison.

6 · The bridge blocks on the whole of sdk_init before answering "initialize"

Claude allows 30 s (MCP_TIMEOUT); anything that makes stages 2–5 slower shows up as a failed MCP server. The frequent trigger is a stale sidecar → interactive OIDC: the cached JWT lives ~24 h and is treated stale 300 s early, so roughly once a day a Claude-spawned bridge opens a browser. Measured over 17 round-trips, 14 completed in 0.16–0.63 s (the IdP cookie was still valid — browser opens, redirects, nobody notices), but 3 needed a human and took 13.6 / 16.1 / 16.6 s; add MFA or an unattended machine and the budget is gone.

One fix covers it: answer initialize immediately with zero tools, run sdk_init() in the background, then push notifications/tools/list_changed when brokering comes up (needs capabilities.tools.listChanged, not yet advertised). Moot in production, where the harness supplies AID_USER_JWT.

7 · The LLM leg has no fail-open / fail-closed policy

If brokering is unavailable the proxy simply fails. Whether it should fall through to the captured upstream unbrokered or refuse outright is a product decision — the daemon already treats this class as an explicit tenant setting (net_egress.fail_closed).

8 · Capability semantics — what does intersected_caps gate?

token-exchange returns intersected_caps=[], yet LLM forwarding still succeeds end-to-end — a real 200 through the gateway on 2026-08-13 (Live verification). So empty caps is not the blocker earlier drafts assumed; that block was ZCC intercepting the gateway host. Open question for the gateway/dashboard team: are caps unenforced on the forward path in dev, or do they gate governance (inspection / policy / logging) rather than transport — i.e. is traffic relayed-but-not-brokered when caps are empty? Gateway/dashboard-side; no ai-broker change.

9 · Forward-proxy env-injection for user-launched CLIs is unsolved

Nothing sets HTTPS_PROXY + NODE_EXTRA_CA_CERTS for a CLI the user starts in their own shell. Options: a shell-profile shim, a wrapper launcher, or ai-broker launching the CLI. A product-architecture decision, not just wiring. Until then the proxy only logs the env each agent needs. Related: HTTP/2 interception (ALPN pins h1 today).

10 · Codex LLM leg is gated; Gemini has no clean base-URL knob

Codex's config-write is verified against a real config; flipping supports_llm_base_url=true needs one live-Codex check of the redirect + wire_api (blocked on issue 8). Gemini's OAuth Code-Assist path has no base-URL knob, so it rides the forward-proxy leg with the other knob-less agents.

11 · Windows host-integration hooks are unimplemented

The portable core runs on Windows, but the macOS-only edges (see Platforms) have no Windows counterpart yet: launching the desktop app (open -b → start/ShellExecute), the parent-orphan watchdog (getppid → job object / parent-handle wait), --recover process teardown (pgrep/signals → taskkill/Win32), the classic Claude config path (~/Library/… → %APPDATA%\Claude\), and the local MITM CA key perms (chmod 0600 → NTFS ACL). Each is a bounded, cfg-gated edge — not a second port — but until they land, a Windows run bootstraps and brokers yet can't auto-launch the app, self-supervise on reparent, or fully tear down.

Recovery path

ai-broker-mon --recover reverses the bootstrap's edits — the teardown the other three modes lack. It began as the external scripts/claude-recover.py (now deleted) and was folded into the binary so one signed artifact both sets up and tears down. The core decision is unchanged: surgical removal over wholesale restore, because ~/.claude.json is live application state — project history and sessions — not static config. Restoring a 20-minute-old backup of it would lose real work.

Two refinements landed with the port into Rust. Process teardown runs first, before any config file is touched: pids are found with pgrep -f ai-broker-mon, confirmed by executable name (ps -o comm=) and with self excluded — since --recover is itself an ai-broker-mon process — then SIGTERM'd, given a 500 ms grace, and SIGKILL'd if they survive. Killing a live proxy up front is what lets the ANTHROPIC_BASE_URL decision below reason about a quiet port rather than misreading its own still-running proxy as someone else's. And the cached-JWT sidecar is now removed by default (--keep-credentials opts out), so a recovered machine doesn't carry a stale identity forward.

ai-broker-mon --recover --dry-run                 # report only; writes nothing
ai-broker-mon --recover                            # repair (sidecar removed)
ai-broker-mon --recover --keep-credentials         # repair but keep the cached JWT
ai-broker-mon --recover --purge-home --clean-backups

recover.rs carries 15 unit tests covering the decision points above — a clean machine (no spurious writes), a fully polluted config with unrelated keys preserved, corrupt JSON restored from the older pristine backup, the ANTHROPIC_BASE_URL ownership branches, and the MCP_TIMEOUT restore. It cannot undo the tenant-side registration, and it cannot fix Claude Desktop's own cached UI state — hence the "quit and reopen" instruction it prints.

v2.0 adds a multi-agent step. Alongside the Claude repair, recover fans out unwire_other_agents() over every installed non-Claude agent, removing the broker's MCP entry via each adapter (honoring --dry-run). Claude keeps its dedicated path because it restores the user's prior ANTHROPIC_BASE_URL / MCP_TIMEOUT rather than merely deleting keys — a distinction the adapters' coarse recover() can't express.

What recovery still can't reach

Only the per-agent home is consolidated; backups are not. .bak.<ts> and .pre-recover.<ts> sit beside each file they copy, so a bootstrap-then-recover cycle can leave up to six files across three directories outside the state dir. Two consequences: --purge-home only deletes the resolved state dir, so it can't sweep those scattered backups; and --clean-backups covers the three Claude paths but misses init.yaml.bak.<ts> inside the state dir. A user tidying $HOME can delete the very snapshot --recover depends on — which is also why resolve_home keeps reading the legacy ~/zax-demo location: a pre-rename install must still surface its .llm_upstream, or recovery would delete ANTHROPIC_BASE_URL instead of restoring it.
