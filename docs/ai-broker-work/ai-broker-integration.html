AI-Broker × AI-Protect · Integration Interface

Wiring ai-broker-mon into ai-protect

The downstream path — Claude & Codex → local proxy → Optimus → inference — is verified. This note scopes the upstream half: the control interface between the ai-protect daemon and ai-broker-mon. It identifies the gap against three required calls, and proposes the contract to close it. Draft, to be folded into the design record.

Scope

Three calls are needed across the ai-protect ↔ ai-broker boundary:

  1. StartUp — when ai-protect starts, it calls the broker's start_up() to do bootstrap work: load config, load cached credentials, start the local proxy.
  2. Agent Discovered — when ai-protect detects an agent installed on the machine, it calls register_agent(metadata) with the fields the broker's workflow needs.
  3. Config notification (broker → ai-protect) — when the broker has configuration to hand back for an agent, it calls an ai-protect function with the agent details.

What exists today

The entire integration is one file: src/subscribers/ai_broker_launch.rs. On each settings.received frame it reads ai_broker.enabled and spawns / supervises ai-broker-mon as a child process — fire-and-forget. Three properties of the current design shape every gap below:

  • ai-broker-mon is a binary, not a library. There is no mon/src/lib.rs and no pub fn start_up / register_agent; it is deliberately kept out of the daemon's build graph ("the same relationship ZCC has with its component daemons"). ai-protect therefore cannot call broker functions in-process.
  • The broker self-discovers. agents::wire_installed_mcp filters its fourteen adapters by each adapter's own is_installed() on-disk probe. ai-protect's own agent discovery (tasks/ai_agents/*) is never handed to it.
  • The broker writes agent configs itself. configure_mcp / configure_llm mutate ~/.claude/settings.json, ~/.codex/config.toml, etc. directly. It never returns config to anyone.
Today's model in one line

"Daemon spawns the process; the process does everything itself." The three interfaces describe a bidirectional control plane — which did not exist when this analysis was written. Even the launch path was scaffold: three TODO(ai-broker) markers (run-as-bound-user, AID_USER_JWT handoff, per-user ZAX_DEMO_HOME) were unwired, so it ran in the daemon's root context.

Since this analysis — the control plane is built

The fire-and-forget model above is superseded. ai_broker_launch.rs now drives a real control plane over a Unix socket or Windows named pipe (start_up + register_agent + credential push + config staging-apply). The next section documents the ai-protect side as built; the gap table below is kept as the original analysis. The run-as-bound-user privilege drop is now built and verified end-to-end on Windows (see the callout below) — the credential source (a stub) remains open.

The ai-protect side — as built

The whole ai-protect half of the integration is one subscriber module — src/subscribers/ai_broker_launch.rs — plus a small supporting cast. It is control-driven, not fire-and-forget: it spawns ai-broker-mon --control and talks to it over a Unix control socket (newline-JSON, contract in ai-broker/mon/src/control/protocol.rs).

Activation chain

daemon boot
  → triggers/registry.rs registers ai_broker_launch::SUBSCRIBERS   (the wiring)
  → heartbeat fetches tenant config
  → "settings.received" fires → on_settings_received() reads ai_broker.enabled
  → reconcile(true) → spawn_broker()  (ai-broker-mon --control --socket …)
  → control_handshake(): start_up  →  push_discovered_agents(): register_agent×N
  + ensure_credential_watcher()  + ensure_config_apply_watcher()

The literal entry point is triggers/registry.rs (it registers the subscriber); the activation switch is the tenant ai_broker.enabled toggle arriving on settings.received. Everything then happens inside ai_broker_launch.rs.

What the module does

  • Reactive lifecycle — reconcile(enabled) spawns/supervises/stops one broker child per the ai_broker.enabled toggle (idempotent; reaps + respawns).
  • Interface #1 — start_up — control_handshake() connects and sends bound-user identity + per-user home + the ZAX credential (from zax_user_credential::fetch, a stub today) as inputs.
  • Interface #2 — register_agent — push_discovered_agents() runs ai-protect's real scan_inventory(), maps each client label → broker id (client_label_to_broker_id, incl. vscode → copilot), dedups, and pushes; re-fired on agentcfg.rescan / inventory.rescan / the periodic scan tick.
  • Interface #4 — credential renewal — the credential-request watcher polls the broker's flag; on a near-expiry touch it fetches + pushes a fresh credential (push_credential).
  • Interface #3 — single-writer config — the config-staging apply watcher sweeps each user's ~/.ai-broker/config-staging/, and applies staged ZIPs as the owning OS user (write_atomic_under + fchown), making ai-protect the sole config writer.

The process boundary + shared contract

The wire contract now lives in a dedicated serde-only crate, ai-broker/protocol (lib zax_control_protocol), linked by both the broker and the daemon — so a renamed field/variant is a compile error on both sides, not the old hand-mirrored-JSON drift. It's the only ai-broker crate in the root-daemon build graph; mon/sdk (HTTP/OIDC/TLS surface) stay out, preserving the isolation. A PROTOCOL_VERSION handshake in start_up makes the broker refuse a version-mismatched daemon (fail fast on mismatched binaries).

Control transport now built for Windows too (named pipe) — and the privilege drop is verified end-to-end

The control socket was originally Unix-only (Rust std gates std::os::unix::net to unix). That gap is closed: the transport seam (control/transport.rs) now carries a Windows arm — a named pipe (\\.\pipe\…), DACL-hardened, with the same duplex-stream API the Unix side exposes, plus sim_daemon and the daemon-side connector widened to match. zax_control_protocol stayed transport-agnostic throughout, as designed.

Beyond the transport: the SYSTEM→user privilege drop (spawn_broker_as_console_user / platform::windows_session) is now verified working on a real Windows VM — a genuine Windows service (session 0, LocalSystem) correctly crosses into the active console user's session via CreateProcessAsUserW, confirmed by process ownership (ai-broker-mon.exe running as the logged-in user, not SYSTEM). Getting there surfaced two real bugs, both fixed in src/platform/windows_session.rs / src/subscribers/ai_broker_launch.rs:

  • Missing .exe suffix. AI_BROKER_BIN is the bare cross-platform name "ai-broker-mon" (no extension, since Unix doesn't need one). The plain-spawn fallback tolerates that — Rust's Command resolves via lpCommandLine, which Windows auto-extends with .exe — but CreateProcessAsUserW's lpApplicationName-based resolution does not auto-extend, and failed with ERROR_FILE_NOT_FOUND even though the file plainly existed at that path. Fixed by appending std::env::consts::EXE_SUFFIX.
  • Stale session could win over the active one. active_session_ids() enumerated WTSActive/WTSConnected/WTSDisconnected sessions with no ordering, and every caller picked the first session whose token query succeeded — so a merely-disconnected leftover session (e.g. an admin's earlier RDP login) could beat the genuinely active user if it happened to enumerate first. Fixed by sorting WTSActive first.

Two smaller correctness fixes landed alongside, neither of which was the actual blocker but both worth keeping: an explicit cwd instead of relying on CreateProcessAsUserW's undocumented NULL-cwd fallback, and a LoadUserProfileW call before CreateEnvironmentBlock (per Microsoft's own guidance for this exact SYSTEM→user pattern).

The gap, interface by interface

Required callClosest thing todayThe gap
1 · StartUp
start_up(ctx)		 do_bootstrap() — reached only by spawning the process No callable entrypoint; no request/response or readiness signal back to ai-protect; no way to pass context in. The inputs it needs — bound user, AID_USER_JWT, ZAX_DEMO_HOME — are exactly the three unwired TODO(ai-broker).
2 · Agent Discovered
register_agent(meta)		 Nothing. Broker self-detects via is_installed() No entrypoint; no call site in ai-protect's discovery path to invoke it; no agreed metadata schema; no story for update / removal / idempotency. The ownership model must flip from "broker scans" to "ai-protect tells broker."
3 · Config notification
broker → ai-protect		 Inverted. Broker writes agent config to disk itself No ai-protect-side "apply this agent config" API; no config schema; and it collides with ai-protect's existing config writer (policy-IR → native config + hook_installer). Two writers of the same files, no defined owner or merge rule.

The foundational gap

There is no transport or contract between the daemon and the broker beyond "launch the exe." All three needs are RPC-shaped, and two directions are required. Because the broker is not linkable by design, these cannot be in-process function calls — they must be an IPC / RPC protocol. ai-protect already has an IPC framework (Unix socket / Windows named pipe, used for hooks and clients), but the broker is not an IPC peer today and there is no message schema for any of the three. That duplex channel + typed messages is the thing that actually needs designing; the three "functions" are just its methods.

Two second-order gaps fall out of the transport decision:

  • Lifecycle. register_agent implies a long-lived service ai-protect calls repeatedly over time. Today's broker is "bootstrap once at enable, then proxy." It has to expose a control endpoint and stay reconcilable.
  • Source-of-truth split. The three interfaces implicitly re-divide responsibility: ai-protect owns discovery (#2) and config application (#3); the broker owns brokering. The code does not reflect that yet (the broker still discovers and writes), so it must be made explicit or the two will fight over the same files.

Proposed message contract

A typed control protocol over ai-protect's existing IPC. The broker gains a thin service layer behind it, keeping the binary boundary (and the build isolation) intact.

MethodDirWhenPayload (sketch)Returns

register_agent daemon → agent detected / changed / removed agent_type, version, install path, config paths, state accepted / unsupported

Payload shapes are sketches — pinning the two schemas (register_agent metadata and report_agent_config body) is part of the work, not settled here.

Open decisions

1 · Who owns the agent config file? — RESOLVED: single writer = ai-protect

Decided and built (pending live validation). The broker no longer writes agent config directly. In stage mode (ZAX_CONFIG_SINK) it renders the config and drops a ZIP at a per-user staging dir (~/.ai-broker/config-staging/, entries + a manifest.json); ai-protect watches and applies it as the owning OS user — containment under that user's home, a path allowlist (only .codex/config.toml today), and an O_NOFOLLOW-safe write + fchown via write_atomic_under. So ai-protect is the single writer. Commits: broker 270b86cc, daemon a446454d (4 apply unit tests + a broker socket smoke). Remaining: a live daemon run on the research VM, then flip the default from write to stage; and defining the merge rule when policy-IR / hook_installer and a staged config target the same file.

2 · Transport & framing

Reuse ai-protect's IPC socket/pipe with a new message type, or a dedicated broker control socket? Either keeps the broker un-linked. Needs a framing + versioning choice (the schemas will evolve — endpoint-first rollout, like net_egress).

3 · Discovery ownership

If ai-protect drives discovery via register_agent, the broker's adapter is_installed() probes become a fallback (or are retired). Decide whether the broker trusts ai-protect's "installed" truth outright, or reconciles it against its own probe.

4 · Multi-user / session model

start_up runs per bound-user session (the broker child is per session on multi-user hosts). The control channel and the supervised-child map are keyed by session — the TODO(ai-broker) that today assumes a single child.

5 · LLM-leg identity — shared instance JWT vs per-agent · path routing chosen

The gap. There is one shared --llm-proxy, and its identity is fixed at spawn (ZAX_AGENT_ID → one sdk_init → one instance JWT → one signing client). So every agent's LLM traffic is signed with the same instance JWT. The triple JWT grants the intersection of instance ∩ user caps — the user JWT is legitimately shared (same human), but a shared instance JWT flattens any per-agent capability scoping and loses per-agent attribution at Optimus.

Blocking question (to Bumblebee/gateway). Does intersected_caps actually narrow by agent_type / registered agent, or are the instance-side caps install/user-scoped (identical regardless of agent)? If install-scoped, sharing is correct and nothing more is needed. If agent-scoped, we need a per-agent instance JWT on the LLM leg.

Chosen mechanism if agent-scoped — per-agent path routing (not per-agent proxy processes). The agent points its base URL at http://127.0.0.1:<port>/<agent>/v1; the proxy makes the leading path segment the agent selector — parse it, look up that agent's signing context (its own instance/triple JWT) + provider upstream from a per-agent map, strip the prefix, forward the remainder. One process holds N signing contexts (each with its own instance-JWT renewal), instead of N proxy processes on N ports. The prefix selects identity and upstream at once (/codex → OpenAI, /claude → Anthropic); an absent/unknown segment falls back to the default context so /v1/… still works. Recorded in code: the proxy_handler note in llm_leg.rs and ControlService::configure_shared_llm_leg.

Today. The single proxy is configured for Codex (ZAX_AGENT_ID=codex, upstream OpenAI), so Codex-only testing already uses the Codex instance JWT via a plain …/v1 base URL — the path prefix only matters once a second agent shares the proxy. Note: the loopback proxy is ambient-authority for the bound user, so the path prefix is an identity selector any local process could invoke — lock the socket/loopback scope down when this lands. Commit: df7808e1.

Next steps

  1. Define the IPC control contract (message types + framing + versioning) over ai-protect's existing IPC, replacing spawn-and-forget.
  2. Give ai-broker-mon a thin service layer (start_up, register_agent, outbound report_agent_config) behind the control listener; keep the binary boundary.
  3. Pin the two schemas (#2 metadata, #3 config body) and resolve the config-ownership question vs the policy engine first.
  4. Wire the three TODO(ai-broker) (bound user, JWT handoff, home) as the inputs to start_up.
Testing the interface without a full daemon — --sim-daemon

The broker side of steps 1–2 is built, and there is a harness to drive it: ai-broker-mon --sim-daemon plays the daemon's control-driver slice — it spawns the broker (as the invoking non-root user), drives start_up (credentials from env) and register_agent(codex) over the real control::protocol, and idles so the LLM proxy can be exercised. It touches none of ai-protect's machinery (no IPC socket, storage, enrollment, discovery, hooks), so it runs safely alongside a real ai-protect (e.g. a ZCC-managed one). It stands in for the daemon side only; it simulates neither hooks (not part of the broker interface) nor real agent discovery (it hardcodes Codex rather than scanning + mapping + filtering the installed set). Commit 8122422c; details in the design record's Process model → Testing harness.

Initial wiring — Codex only, Claude excluded

The first pass wires Codex only. Claude is deliberately left untouched: it is the agent actively used to design and build this work, and a broken Claude config would interrupt that. Once the Codex path is proven end-to-end through the interface (register_agent → report_agent_config → applied), extend to Claude and the remaining agents. This mirrors the existing rule that Claude is excluded from the broker's install/retarget path.
