1 · StartUp call COVERED

"When AI Protect starts, it should call our start_up function which will set up anything we need at bootstrap — loading config, loading cached credentials, start local proxy, etc."

Built

  • The call exists. ControlService::start_up runs over a Unix control socket (ai-broker-mon --control); the daemon's launch subscriber connects and calls it when the broker is spawned.
  • It does the bootstrap work. It applies the daemon-supplied inputs (bound user, per-user home, credential env), then starts the local LLM proxy — whose sdk_init loads config and cached credentials.
  • Credential loading with real precedence. supplied JWT → refresh-token renewal (no browser) → interactive OIDC, with the pushed credential threaded via env→sidecar. Plus a mid-life renewal path (request-flag → file-watch push → leg bounce).

2 · Agent Discovered → register_agent(metadata) COVERED

"When AI Protect detects an agent is installed, it should call register_agent with the metadata we need."

Built

  • The call + metadata exist. register_agent over the control socket, with RegisterAgentParams (agent_type, version, install_path, config_paths, state).
  • Discovery-driven, not one-shot. The daemon pushes the full discovered set (from utils::discovery::scan_inventory, mapped to broker ids) at launch and on agentcfg.rescan / inventory.rescan / schedule.tick.scan — so agents found after launch are caught too.
  • Broker owns the policy. A configurable filter (ZAX_CONTROL_AGENTS, default {codex}) drops the rest; a registered-set dedups (register on first sight, ignore repeats, forget on Removed); wiring is per-agent via the adapter.
  • Right identity + visibility. Each agent registers under its own binary/name (not a hardcoded Claude), and every decision is logged with the UI name: DROPPED / ACCEPTED / REGISTERED as 'Codex CLI'.

3 · Config Update Notification to AI Protect BUILT · PENDING LIVE

"When we have to return configuration for an agent to AI Protect — an AI-Protect function that we call with the agent details."

Resolved as a single-writer via file-drop + watch (mirrors the credential flag/watch): the broker renders config and drops it as a ZIP; ai-protect watches and applies it — so ai-protect is the sole writer of agent config. Both sides are built; the live daemon run is the remaining validation.

Built — broker side

  • ConfigSink mode (ZAX_CONFIG_SINK: write default | stage). In stage, register_agent renders the config (compute without writing, toml_cfg::render_mcp_server / AgentAdapter::stage_mcp) and writes $ZAX_DEMO_HOME/config-staging/<agent>-<ts>.zip (0600) with a manifest.json {agent, os_user, files[{path, entry}]} — and does not touch the agent config.

Built — ai-protect side (single writer)

  • A per-user config_apply_watcher polls every user's staging dir (identity::home::all_user_homes) and applies each ZIP as the owning OS user: containment (target must be under that user's home) → allowlist (only .codex/config.toml today) → write via utils::atomic_write::write_atomic_under (O_NOFOLLOW-safe under the home + fchown to the user — the vetted hook_installer primitive). Success deletes the ZIP; failure → .zip.failed.
  • Multi-user: the staging-dir owner is authoritative; a ZIP in user X's dir can only write X's own allowlisted config, owned by X — no escalation. bound_user (ZAX) is irrelevant here; config is keyed by OS user.

Remaining

  • Live validation on the research VM (the apply watcher runs in the root daemon, unverified live), then flip the default to stage — that makes ai-protect the single writer in production.
  • Promote both watchers to services::watcher; extend the allowlist as more agents enable.
Config-ownership decision — RESOLVED

The integration note's open decision #1 is settled: ai-protect is the single writer; the broker renders config and stages it, ai-protect applies it as the owning user.
