Windows E2E Runbook

Everything needed to reproduce or continue the Windows end-to-end test of the ai-broker: where the executables, configs, and logs live (dev laptop and VM), the diagnostic commands that actually cracked each problem, the defects found and fixed, and the completed-vs-remaining test checklist.

1 · Test topology

Two machines: the dev laptop (builds, holds the git clone) and the disposable VM EC2AMAZ-VRAE5E8 (Windows Server 2025, runs everything). The laptop's clone is mounted into the VM's RDP session via subst Z: …\ai-protect + drivestoredirect:s:Z:, so the VM reads it at \\tsclient\Z\ — no S3 relay needed. Two VM accounts: Administrator (elevation for sc.exe / process inspection, reached via runas from inside umesh's session) and umesh (the non-admin console user the broker must drop to — must be the Active RDP session).

Why defect 9 survived so long — three layers of masking

Worth internalising, because the next bug of this shape will hide the same way:

  1. The runtime failure is quiet. A failed apply is a WARN line plus a .zip.failed rename. Nothing fails loudly, nothing retries visibly.
  2. The unit test excused it. write_atomic_with_owner_reassigns_ownership_when_privileged tolerated Err(e) if e.kind() == PermissionDenied, believing it was accommodating a non-elevated runner. But io::Error::from_raw_os_error(5).kind() is PermissionDenied — so the real bug and the benign environment case were indistinguishable by kind() alone. They are trivially distinguishable by raw_os_error(): the privilege check builds a custom error (None), while SetSecurityInfo yields a real OS error (Some(5)). The test now asserts that, so this can never be excused again.
  3. The skip-guard added in commit 04888e50 excused it too. can_reassign_ownership_here() probes by calling set_owner_by_path — which carried the same defect — so it returned false even on an elevated runner, meaning the nine guarded tests would have skipped forever. That "fix" was papering over a genuine defect while appearing to accommodate an environment limitation.

The lesson: a test that tolerates an error class is only as good as its ability to distinguish the error it means to excuse from every other error that lands in the same class.

Environment traps that cost real time (not code bugs)
  • Stale binary after redeploy — sc.exe stop is async and a SYSTEM process shrugs off a non-elevated Stop-Process; the copy then fails or silently keeps the old exe. Always: stop → force-kill → verify empty → copy → hash-compare.
  • PS 5.1 reads BOM-less UTF-8 as ANSI — an em-dash's bytes decode into a curly quote, which PS treats as a string terminator: parse errors in a script that looks fine. Keep .ps1 files pure ASCII.
  • runas ≠ logged on — a runas shell creates no WTS session; the drop needs a real console/RDP login. And this VM allows only ONE concurrent RDP session (a second login kicks the first), so: log in as umesh, elevate inside that session via runas /user:…\administrator powershell.exe.
  • Console-blocked mock server — QuickEdit select froze the python console, wedging every handler thread. Always redirect its output to a file.
  • Interleaved script output — pipeline-object tables render after later Write-Host lines; when a check "looks empty", rerun it alone.
  • Secret hygiene — one OpenAI key was exposed via an unmasked Read-Host (now -AsSecureString in path-a-curl.ps1) and rotated. Keys go in the caller's Authorization header only; never on a command line.

6a · Open defects found by testing (not yet fixed)

Both trace to the same line — wait_for_llm_proxy's blocking 20-second wait, called synchronously from inside start_up's control handler.

A · ready=false misreported on the cold path

wait_for_llm_proxy allows Duration::from_secs(20). Observed: daemon spawned the broker at 21:40:58, gave up at 21:41:20 with "local LLM proxy spawned but did not report listening in time" — and the proxy reported listening at 21:41:25, five seconds past the deadline. So the daemon latched a false negative for something that was healthy moments later.

Why the deadline is sometimes too tight: this run needed a fresh OIDC round. The cached credential was near expiry, and with offline_access ungranted by the IdP (temp workaround #2) there is no refresh token, so the only renewal path left is interactive login. The 20 s budget fits the warm path (valid cached credential → proxy up fast → ready=true, as seen the night before) but not the cold one.

B · head-of-line blocking on the control channel

The same 20 s wait stalls every other control request behind it. Two pushes of the identical code path, minutes apart:

pushobservedackedelapsed
organic, during start_up21:41:01.86284721:41:20.37426118.5 s
manual, channel idle21:55:29.51382021:55:29.5141870.4 ms

The tell is what the slow ack landed beside: start_up ← ready=false at 21:41:20.374015 — 246 µs earlier. The credential push could not complete until start_up released the channel. That is a circular wait: start_up waits on the proxy → the proxy needs a credential → the broker requests one → the daemon's push is queued behind start_up.

Benign today only because the credential source is a stub, so nothing useful was being delayed. With a real credential source this would actively defeat the push's purpose — the credential would exist but arrive ~19 s late, after the proxy had already fallen back to interactive OIDC.

One fix addresses both

Stop letting start_up block the control service: either return promptly with a pending/not-ready status and have the daemon re-poll for readiness, or move the wait off the control-handling path so the listener stays free to serve concurrent requests.

C · no periodic self-heal for a broker that dies unexpectedly

Decided by reading the code before testing anything, then verified empirically rather than trusted: ai_broker_launch::reconcile() — the only function that reaps a dead broker and respawns it — has exactly one call site in the entire source tree, inside on_settings_received. The periodic scan-tick handler (on_agent_rescan) only checks guard.is_some(), never has_exited() — so it can push discovered agents at a broker it believes is running while that broker is actually dead.

Confirmed live: after --recover killed the broker (see §7), it stayed dead for a full 90 seconds of polling with ai_broker.enabled still true and the mock still serving the same config version — exactly as predicted, because reconcile() never got called. The moment CONFIG_VERSION was bumped and a new settings frame arrived, it respawned within one heartbeat.

The consequence for production: a broker killed by anything — a crash, an AV false-positive, OOM, an admin fat-fingering a kill — stays dead indefinitely if the tenant's ai_broker settings don't change, since reconcile is edge-triggered on a config-version change, not merely on receiving a heartbeat response. At the 600 s default cadence that is already a real window; if the tenant simply never touches this setting, the window is unbounded.

Not filed as a fix here — it may be an intentional trade-off (avoiding a spurious respawn loop if the broker is failing fast for some other reason) rather than an oversight, and that's a product call, not a test-runbook one. Worth a decision either way: e.g. reap-and-respawn on the periodic scan tick too, or on every heartbeat regardless of version, or a dedicated liveness timer.

D · the nobody-logged-on fallback can leave a permanent, self-inflicted zombie broker

The nobody-logged-on negative case (§7) exercised the SYSTEM-context fallback for real — see the full account there — and it surfaced something more consequential than the fallback path itself: the degraded broker it spawns does not fail fast, and does not self-correct once a user logs back in. My own prediction going in was wrong, worth saying plainly: I expected the fallback broker's interactive-OIDC attempt to hit oidc.rs's bounded deadline and exit. It never does, because it never even gets there.

What actually happens, confirmed from the fallback broker's own log (readable only from an elevated shell, since its home resolved to C:\Windows\system32\config\systemprofile\.ai-broker — the documented, by-design consequence of broker_home() having no console user to resolve, not the systemprofile bug fixed on day 1): it reaches start_up, correctly reports "NO user credential available — will use a cached refresh token if any, else interactive OIDC", configures the LLM route mapping, and successfully completes register_agent(codex) — MCP wiring succeeds independently of the credential path entirely. There is no [auth] launching interactive OIDC line, ever — not in this run, nor in four earlier occurrences of the identical signature found in the same log dating back to Aug 19. The LLM proxy — and whatever would trigger a real OIDC attempt — appears to initialize lazily, on first actual use; since nothing running as SYSTEM in session 0 ever sends it real LLM traffic, that path simply never fires. The broker doesn't crash, hang, or time out. It becomes a stable, indefinitely-running zombie: alive, responsive on its control socket (it even answered a later periodic agent-rescan push, already registered — ignoring push), genuinely MCP-wired, confirmed via Get-Process -IncludeUserName as NT AUTHORITY\SYSTEM — and permanently incapable of serving an LLM request (Get-NetTCPConnection -LocalPort 8788 came back empty the entire time).

And per finding C, nothing fixes this on its own. Once the zombie exists, reconcile() only ever asks "is it dead?" — never "is it in the wrong session?" — so even after the correct user logs back in and a fresh settings frame arrives, it sees guard.is_some() && !has_exited() and does nothing. Confirmed directly: with the zombie still alive, a forced version bump produced 90 seconds of silence, zero redrop attempt. The only way out was manual — Stop-Process on the SYSTEM-owned pid from an elevated shell — after which the very next settings frame correctly reaped the now-genuinely-dead entry and dropped a proper broker into the user's session.

Net effect for production: any window where nobody is logged on when a settings frame lands — a reboot before anyone signs back in, a scheduled restart overnight, a kiosk/shared machine between shifts — can leave the box in a state where ai_agents.mcp_servers reports the agent as wired (register_agent succeeded) while the LLM leg is silently, permanently dead, and nothing in telemetry distinguishes this from a healthy broker short of noticing the missing 8788 listener. This compounds finding C rather than standing apart from it: the same missing "is this broker actually correct, not just alive" check is the root cause of both.

Elevation is not a single axis — the suite cannot be green in one run

Windows testing here has tests pulling in opposite directions, and no single cargo test invocation satisfies both:

  • Needs elevation: the eight permission_apply tests and app_capture's write_user_config_creates_config_on_clean_profile — they reassign file ownership, which requires SeRestorePrivilege. Guarded, so they skip cleanly when unprivileged.
  • Needs non-elevation: mcp_probe::helper's a_user_owned_forged_settings_file_does_not_open_the_gate. Its fixture needs a file owned by the calling user, but an elevated admin token's default owner for new objects is BUILTIN\Administrators — which is_admin_owned correctly trusts. So elevated, it asserts against a genuinely admin-owned file and fails while the product is behaving exactly as designed.

Current state: non-elevated is green (1869/0, 8 skips) and is what CI sees; elevated is 1868/1 with that one known failure. The real fix for the odd one out is to set the owner SID explicitly rather than inherit the token default — feasible now that handle-based reassignment works.

And the meta-lesson, which cost a full misdiagnosis: before skipping a test on an environment claim, confirm it actually passes in an environment that satisfies the claim. A guard never observed to unblock is indistinguishable from a permanently disabled test — and here the guard, the probe it called, and the fixture were all broken at once, so nothing objected.

Observed but unexplained — proxy-child panics in the broken era

logs\llm-proxy-child.log accumulated 3 panics and 4 stack overflows, the panics being failed to spawn thread: Os { code: 1450 } "Insufficient system resources". A healthy proxy writes nothing to this file (it logs via tracing to zax.log; only panic output reaches stdout/stderr), so every line in it is a crash.

Not reproducible. Cleared the file, restarted the service, proxy came up listening — file stayed empty. So these date from the era before the broker_home fix, when the child was dying repeatedly. But the root cause was never identified: exit code 2, which is what the daemon actually observed then, matches neither a Rust panic (101) nor a stack overflow (0xC00000FD), so these crashes are a separate phenomenon from the failure we fixed. Thread exhaustion plus stack overflow is the signature of a spawn storm — and note start_llm_proxy spawns <self> --llm-proxy, so a --llm-proxy process reaching that path would recurse. Recorded rather than closed: if it is a latent threading bug it can resurface under different conditions.

Worth noting these were only ever visible because of the child stdout/stderr redirect added while chasing the earlier bug. Without it they went to a void.
