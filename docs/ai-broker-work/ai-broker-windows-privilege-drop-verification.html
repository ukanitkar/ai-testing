Windows Privilege-Drop Verification

The SYSTEM daemon → active-user-session broker spawn (CreateProcessAsUserW) was exercised end-to-end on a real disposable Windows VM. Two real bugs surfaced and were fixed; two defensive-but-non-blocking improvements landed alongside. This records the fixes, the exact scripts used to redeploy/verify, and the final confirmed result.

repo ai-protect branch feat/ai-broker-beyond-claude base 21541f0e + uncommitted fixes privilege drop verified end-to-end on Windows

1 · What was being tested

Path B from the Windows handoff doc: an elevated SYSTEM daemon (installed as a real Windows service, so it genuinely runs in session 0) receives ai_broker.enabled=true from the mock device plane and must spawn ai-broker-mon as the logged-in console user (umesh), not as SYSTEM — proving spawn_broker_as_console_user / platform::windows_session::run_in_user_session actually crosses the session boundary via WTSQueryUserToken → CreateEnvironmentBlock → CreateProcessAsUserW.

2 · Four fixes, in the order they landed

#FixFileWas it the actual blocker?
1Explicit cwd (the broker's own directory) instead of None for CreateProcessAsUserW's lpCurrentDirectoryai_broker_launch.rsNo — still a correct defensive fix, kept
2LoadUserProfileW called before CreateEnvironmentBlock, per Microsoft's own guidance for exactly this SYSTEM→user pattern (new PrivilegeScope for SeRestorePrivilege/SeBackupPrivilege, RAII LoadedProfile unload guard)windows_session.rsNo — still correct, kept
3The real bug: AI_BROKER_BIN is the bare cross-platform name "ai-broker-mon" (no .exe) — fine for the plain-spawn fallback (resolves via lpCommandLine, which Windows auto-extends), fatal for CreateProcessAsUserW's lpApplicationName resolution (no auto-extend) → ERROR_FILE_NOT_FOUND on a file that plainly existed. Fixed with std::env::consts::EXE_SUFFIX.ai_broker_launch.rsYes
4Second real bug: active_session_ids() had no session-state ordering, so a stale disconnected session (an admin's leftover RDP login) could win over the genuinely active user if it happened to enumerate first. Fixed by stable-sorting WTSActive first.windows_session.rsYes
How fix #3 was actually found

Two theories (cwd, then LoadUserProfileW) were tried and rebuilt/redeployed without resolving the identical ERROR_FILE_NOT_FOUND — confirmed each time by comparing the deployed binary's SHA-256 against the freshly-built one, ruling out a stale-copy false negative. What actually cracked it was a temporary diagnostic log line printing the exact app/cmdline/cwd strings reaching CreateProcessAsUserW — which showed app="C:\Users\umesh\work\ai-broker-mon", no extension. The diagnostic was removed once the cause was confirmed.

3 · Verification scripts

Two scripts drove the final redeploy-and-check cycle on the VM, both reachable from the RDP session via the Z: drive redirection (subst-mapped to this ai-protect clone) at \\tsclient\Z\commands\.

commands/fix3.ps1 — redeploy + retest

# Redeploy the session-priority-fix build of the daemon (WTSActive now beats a
# stale WTSDisconnected session) and re-test the AiBrokerTest SYSTEM service
# privilege-drop path.
# Run this from an elevated PowerShell on the VM.

$expectedHash = "92DE3EC705C074F827D02A1C3A12CD9401035E242DA579173B1AA7CA2C3C2806"

Write-Host "Stopping AiBrokerTest service..."
sc.exe stop AiBrokerTest

Write-Host "Killing any leftover daemon/broker processes..."
Get-Process zscaler-ai-protect, ai-broker-mon -ErrorAction SilentlyContinue | Stop-Process -Force
Start-Sleep -Seconds 2

$leftover = Get-Process zscaler-ai-protect, ai-broker-mon -ErrorAction SilentlyContinue
if ($leftover) {
    Write-Host "ERROR: processes still running, aborting:" -ForegroundColor Red
    $leftover | Format-Table Id, ProcessName, SI
    exit 1
}
Write-Host "Confirmed clean." -ForegroundColor Green

Write-Host "Copying fixed binary from Z: ..."
Copy-Item "\\tsclient\Z\target\release\zscaler-ai-protect.exe" "C:\Users\umesh\work\zscaler-ai-protect.exe" -Force

$actualHash = (Get-FileHash "C:\Users\umesh\work\zscaler-ai-protect.exe" -Algorithm SHA256).Hash
if ($actualHash -ne $expectedHash) {
    Write-Host "ERROR: hash mismatch after copy!" -ForegroundColor Red
    Write-Host "  expected: $expectedHash"
    Write-Host "  actual:   $actualHash"
    exit 1
}
Write-Host "Hash confirmed: $actualHash" -ForegroundColor Green

Write-Host "Checking mock device plane on :8080..."
try {
    $health = curl.exe -s http://127.0.0.1:8080/health
    if ($health -ne "ok") { throw "unexpected response: $health" }
    Write-Host "Mock device plane is up." -ForegroundColor Green
} catch {
    Write-Host "WARNING: mock device plane not reachable ($_). Restart it before continuing:" -ForegroundColor Yellow
    Write-Host '  & "C:\Program Files\Python312\python.exe" -u "\\tsclient\Z\ai-broker\scripts\dev_device_plane.py" --port 8080 *> "C:\ai-broker-test\device-plane.log"'
}

Write-Host "Starting AiBrokerTest service..."
sc.exe start AiBrokerTest
Start-Sleep -Seconds 5

Write-Host "`n--- ai-broker-mon.exe owner (the actual test) ---" -ForegroundColor Cyan
Get-Process ai-broker-mon -IncludeUserName -ErrorAction SilentlyContinue | Select-Object Id, ProcessName, UserName, SI

Write-Host "`n--- latest broker-launch log lines ---" -ForegroundColor Cyan
Select-String -Path "C:\ProgramData\ZscalerAIProtect\daemon.log" -Pattern "launched ai-broker-mon|could not start ai-broker-mon" |
    Select-Object -Last 4

commands/check-both.ps1 — confirm the split-privilege result

# Check both the daemon and broker processes together — confirms the
# split-privilege result end-to-end: daemon should be SYSTEM/session 0,
# broker should be the active console user/session (e.g. umesh/3).

Get-Process zscaler-ai-protect, ai-broker-mon -IncludeUserName -ErrorAction SilentlyContinue |
    Select-Object Id, ProcessName, UserName, SI

4 · Confirmed result

This is the whole point of Path B

A LocalSystem daemon running in the kernel's true session-0 isolation correctly identified the active (not merely connected/disconnected) console user and handed the broker off into that user's own session — the split-privilege model this subsystem exists to prove, now demonstrated on real Windows rather than only reasoned about from the source.
