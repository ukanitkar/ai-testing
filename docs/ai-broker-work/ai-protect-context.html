1 · What this is

ai-broker (under ai-protect) makes AI coding agents route their MCP tool traffic and LLM inference through the ZAX gateway ("Optimus") so Zscaler can broker it. Crates:

  • ai-broker/mon — bin ai-broker-mon, the mono-exe (bootstrap, --mcp-server, --llm-proxy, --control, --sim-daemon, --recover).
  • ai-broker/sdk — lib zax_sdk (OIDC → register → activate → token-exchange, RFC 9421 signing).
  • ai-broker/protocol — lib zax_control_protocol, the shared daemon↔broker wire contract (serde-only; the only ai-broker crate the root daemon ai-warden links). Carries PROTOCOL_VERSION — start_up refuses a version-mismatched peer.

The daemon side is one subscriber, src/subscribers/ai_broker_launch.rs: it spawns + supervises the broker and drives the control socket (start_up → register_agent). Goal on Windows: run the daemon elevated (SYSTEM) and prove it launches ai-broker-mon as the logged-in user (umesh), which then does OIDC and stands up the LLM proxy.

3 · The two backends (why B exists)

ai-protect talks to two independent backends. Keeping them straight is the key to the full-daemon test:

(a) Device plane
ai-platform

<server-url>/endpoint/v1/* — heartbeat, config, events. This is the only source of ai_broker.enabled — it arrives via GET /config → settings.received. No local file sets it. B mocks this.

(b) Control plane + gateway
ZAX / Optimus

api.<cloud> (Vector register, Bumblebee activate) + gateway.<cloud> (Optimus). From init.yaml cloud: dev → api.zsagenticdev.ai. The broker (as umesh) talks to this — real dev backend, not mocked.

So the full daemon path is: B flips the broker on → the daemon (C) spawns the broker as umesh → the broker does the real OIDC + onboarding against (b) and stands up --llm-proxy.

5 · Windows Path A — quick --llm-proxy smoke

Fastest "does it build + run + LLM leg works on Windows" check. User-space, no daemon, no privilege drop. Skip to §6 if you want the full daemon path.

  1. Pull: git checkout feat/ai-broker-beyond-claude && git pull (tip 4471de7f+).
  2. Build: cargo build -p ai-broker-mon (MSVC toolchain).
  3. Config prereq: --llm-proxy needs config.yaml + init.yaml under %USERPROFILE%\.ai-broker\ (else "run bootstrap"). Copy the two small files from a working macOS ~/.ai-broker/; init.yaml must be cloud: dev.
  4. ZCC OFF — else it TLS-intercepts the gateway host → synthetic 502 masks the real result.
  5. Run (registers as Codex → agent_type=other): 
    $env:ZAX_AGENT_ID = "codex"
.\target\debug\ai-broker-mon.exe --llm-proxy --upstream https://api.openai.com
    Complete the OIDC browser login yourself. (Omit ZAX_AGENT_ID → registers as custom, also allowed.)
  6. Approve — Windows mints a different agent_id (identity includes the host). Grab it from %USERPROFILE%\.ai-broker\logs\zax.log (registered agent_id=…), then approve (§8).
  7. Fire a call (key stays out of history). The proxy now terminates TLS with a locally-minted leaf (same CA mitm.rs uses for the forward-proxy leg) and requires a per-install token as the leading path segment — -k skips verifying our own self-signed CA (fine for a local smoke test; use --cacert %USERPROFILE%\.ai-broker\mitm-ca\mitm-ca-cert.pem instead of -k for a stricter check), and $TOKEN comes from %USERPROFILE%\.ai-broker\llm-proxy.token: 
    $K = Read-Host "OpenAI key"
$TOKEN = Get-Content "$env:USERPROFILE\.ai-broker\llm-proxy.token"
curl.exe -sSk "https://127.0.0.1:8788/$TOKEN/v1/responses" `
  -H "authorization: Bearer $K" -H "content-type: application/json" `
  -d '{\"model\":\"gpt-5.4-mini\",\"input\":\"pong\"}' -w "`n[http %{http_code}]`n"
Remove-Variable K
    Expect 200 with a pong. A 401 with no forwarded body means the token was missing or wrong, not a gateway/provider rejection.

6 · Windows Path B — full daemon → broker as umesh (the goal)

This exercises B + C: an elevated (SYSTEM) daemon receives ai_broker.enabled=true from the mock device plane and spawns ai-broker-mon as umesh (not SYSTEM), so the broker can do per-user OIDC.

To actually exercise the privilege drop, the daemon must be SYSTEM

C only crosses into the user session when running_as_service() is true (session 0 / SYSTEM). If you run the daemon as an elevated admin in your own console session, running_as_service() is false and it just plain-spawns the broker in that same session (still works, but does not test CreateProcessAsUser). Launch as SYSTEM via PsExec -s -i (Sysinternals) or install it as a Windows service. Be logged in at the console as umesh so there's an active session to drop into.

Steps (PowerShell)

1 · Build both binaries and co-locate them. spawn_broker resolves ai-broker-mon.exe from the daemon exe's own directory, so they must sit side by side.

cargo build -p ai-warden          # zscaler-ai-protect.exe (the daemon)
cargo build -p ai-broker-mon      # ai-broker-mon.exe (the broker)
# put ai-broker-mon.exe next to zscaler-ai-protect.exe:
Copy-Item .\target\debug\ai-broker-mon.exe (Split-Path (Get-Command .\target\debug\zscaler-ai-protect.exe).Source)

2 · Start the mock device plane (B) — this is what turns the broker on.

python ai-broker\scripts\dev_device_plane.py --port 8080
# serves GET /endpoint/v1/config -> settings.ai_broker.enabled=true
# (AI_BROKER_ENABLED=0 to test the off path)

3 · ZCC OFF (the broker's real onboarding reaches Optimus).

4 · Run the daemon elevated as SYSTEM, pointed at the mock. --allow-unenrolled skips enrollment; --no-install-* keeps it from touching agent configs.

# from an admin prompt, via Sysinternals PsExec (SYSTEM + interactive):
psexec -s -i 1 -d "C:\path\to\zscaler-ai-protect.exe" daemon `
  --allow-unenrolled --storage http --server-url http://127.0.0.1:8080 `
  --no-install-exts --no-install-hooks

Flow: heartbeat → sees config_version mismatch → fetches /config → settings.received → ai_broker.launch reconcile(enabled=true) → spawn_broker → (SYSTEM) CreateProcessAsUser → ai-broker-mon --control --socket \\.\pipe\zscaler-ai-broker-control-… → daemon drives start_up + register_agent over the pipe.

5 · Verify the drop worked. In Task Manager (Details tab, "User name" column) or PowerShell, confirm ai-broker-mon.exe runs as umesh, not SYSTEM:

Get-CimInstance Win32_Process -Filter "Name='ai-broker-mon.exe'" |
  ForEach-Object { $_.GetOwner().User }   # -> umesh

Broker log: C:\Users\umesh\.ai-broker\logs\zax.log. Daemon log shows [ai-broker] launched ai-broker-mon in the user session. If no user is logged on, or the crossing fails, the daemon logs a warning and falls back to a SYSTEM spawn — the next settings tick re-reconciles.

6 · Drive OIDC + the LLM call as in Path A (§5, steps 5–7): complete the browser login (as umesh), approve the new agent_id (§8), then curl the proxy for a 200 pong.

Opt-in header that would auto-approve at register (x-agent-auto-approval). Off by default; we approve via the script instead. Leave off.

8 · The approval script

An agent is pending_approval after register; the LLM leg can't activate until it's approved. Approve with the admin tool (does an admin OIDC login, then transitions the agent):

<venv>/bin/python zax-sdk-python/script/approve_agent.py --agent-id <AGENT_ID>
Two gotchas

1. The script's route was stale (404 on …:transitionState) — fixed to the deployed route POST /vector/v1/admin/agent-operations/{id}/transition body {"status":"approved"}. That fix lives only in the macOS zax-sdk-python checkout (separate repo, uncommitted). On Windows either apply the same 2-line fix, or run the fixed script from macOS with the Windows agent_id — approval is out-of-band, it just needs the id + admin login + dev registry.

2. Needs the zax-sdk-python venv (zax_client/httpx/yaml) and script/admin.yaml pointed at dev. The agent_id is stable per host, so approve once out-of-band, then re-run — register returns approved immediately.

10 · Rules & gotchas

  • ZCC off for any call that reaches Optimus (else synthetic 502).
  • OIDC + API keys + passwords are yours to enter, not the assistant's — the assistant drives the build/wiring and hands you the exact commands; you do the interactive login and paste keys via Read-Host (never into shell history).
  • Provider API key goes in the caller's Authorization header (broker forwards it unchanged); the ZAX identity is a separate signed header the broker adds.
  • Scratch CODEX_HOME if exercising register/MCP wiring, so the real ~/.codex isn't touched.
  • The Windows VM is the intended, disposable test box for running the daemon (that's the point of Path B). Still pass --no-install-exts --no-install-hooks so it doesn't rewrite agent configs. Do NOT run the daemon on your real dev machine.
  • agent_id differs per host — the Windows registration is a new agent; approve its id.
