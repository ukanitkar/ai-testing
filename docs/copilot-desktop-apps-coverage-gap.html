"Copilot doesn't work" outside VS Code — findings

Written 2026-09-15, in response to a field report that "the Copilot work we have done works for VS Code, but not for GitHub app and Copilot app." Short answer: the report conflates three (really four) distinct surfaces that share the word "Copilot," only one of which our ai-gateway adapter (ai-gateway/agent-manager/src/agents/copilot.rs) ever targeted. This isn't a regression in existing code — it's a scope question, and one of the two named apps turns out to need a different kind of solution than a config key we got wrong.

Update 2026-09-15: the VS Code Copilot Chat question (row 2 below) was partially resolved, then reopened same-day on a generic env-var/CA-cert mechanism that needs live verification — see its own section for the current state. The GitHub Copilot app remains the other open surface.

The four surfaces, disambiguated

Surface What it actually is In our adapter's scope today?
GitHub Copilot CLI (copilot command, npm @github/copilot) The thing copilot.rs was built for Yes — this is "the Copilot work" that exists
VS Code's built-in Copilot Chat extension A separate code path inside VS Code itself No, and confirmed correctly so — vscode.rs has llm: LlmRouting::None, and the extension itself has no working redirect mechanism to target. See "VS Code's built-in Copilot Chat extension" below
GitHub Copilot app (github.com/features/ai/github-app) A brand-new, separate desktop application — "the only desktop experience for agent-driven development built natively on GitHub." Not the classic GitHub Desktop git client No — never targeted. See findings below; bringing it in scope needs new, riskier tooling
Microsoft 365 Copilot app (microsoft.com/.../download-copilot-app) A completely different Microsoft product (confirmed on Microsoft's own page: "a completely separate product from GitHub Copilot"). Talks to Outlook/Word/Excel/PowerPoint, not GitHub's Copilot backend Out of scope permanently — there is no shared backend to intercept. This is a category error, not a gap

VS Code's built-in Copilot Chat extension — reopened 2026-09-15

Investigated as the third surface in the table above, since it's the one most likely to be what the original "works for VS Code" report actually meant.

Our own code already treats this as out of scope, and correctly so. ai-gateway/agent-manager/src/agents/vscode.rs sets llm: LlmRouting::None and the adapter is dormant — "vscode" isn't in ENABLED_AGENTS. Discovery maps a vscode session to the copilot broker identity purely because "Copilot Chat is the agent behind the editor" (its own doc comment), but that's identity attribution only: copilot.rs's actual redirect mechanism writes to ~/.copilot/mcp-config.json / ~/.copilot/settings.json — the standalone CLI's home directory, which the VS Code extension never reads. docs/SYSTEM-OVERVIEW.md already flagged this: "the VS Code Copilot Chat extension's sessions stay opaque."

No working interception mechanism exists in the extension itself, either. Verified against the extension's own contributed-settings schema and a maintainer-tracked issue, not guessed:

  • github.copilot.advanced.debug.overrideProxyUrl / overrideCapiUrl are real settings, but their documented purpose is overriding the GitHub authentication proxy, not chat/inference traffic — and a confirmed GitHub issue shows github.copilot-chat ignores them entirely; only the older, separate inline-completion extension (github.copilot) honors them.
  • VS Code's supported customization path, BYOK (chatLanguageModels.json), is strictly additive — it registers a new selectable model next to Copilot's own in the model picker, requiring manual/pinned selection. It cannot redirect or intercept Copilot's own default traffic.
  • On this Mac, the extension isn't even installed (chatLanguageModels.json is []; no github.copilot-chat under ~/.vscode/extensions), consistent with nobody having wired a live config surface for it.

A subsequent AI-generated answer (Google AI Mode) claimed a github.copilot.advanced.requestHeaders field and a working debug.overrideProxyUrl redirect for Copilot Chat specifically — checked against the extension's real schema and found fabricated (requestHeaders isn't a real contributed setting at all) and contradicted by the issue above. Worth remembering as a caution on trusting AI-search answers for config specifics, not a new finding about the product itself.

Conclusion (as of the settings-only check above): the field report's "works for VS Code" almost certainly meant the copilot CLI run inside a VS Code integrated terminal — the one path our adapter genuinely brokers — not the Copilot Chat extension. This closes the open question below about which surface was originally tested, independent of the reopened question below about whether a different mechanism could still redirect the extension's own traffic.

Reopened: the generic env-var + CA-cert path is unresolved, not dead

The finding above only rules out Copilot Chat's own internal debug setting. It doesn't rule out the same generic mechanism our other adapters already rely on: HTTPS_PROXY/HTTP_PROXY env vars for redirection plus NODE_EXTRA_CA_CERTS for CA trust. Two authoritative-looking sources directly disagree on whether this works for VS Code Copilot Chat:

  • GitHub's own docs (docs.github.com/en/copilot/concepts/network-settings) document HTTPS_PROXY > https_proxy > HTTP_PROXY > http_proxy (in that priority order) as Copilot's supported proxy mechanism, and NODE_EXTRA_CA_CERTS as the supported CA-trust mechanism for a TLS-intercepting proxy.
  • Real user reports contradict it for this extension specifically: a GitHub issue states the Copilot agent ignores NODE_EXTRA_CA_CERTS outright, corporate-proxy-with-custom-CA setups are reported broken for Copilot Chat, and the practical workaround people actually use is a third-party extension (Win-CA) that bridges the Windows OS certificate store into VS Code's trust — broad OS-store trust, not the narrow per-agent NODE_EXTRA_CA_CERTS trust this codebase's own design deliberately favors elsewhere (see ai-gateway/listener/src/certs.rs's design doc).
  • Checking the open-source vscode-copilot-chat extension's own configurationService.ts directly: the only proxy-related setting it defines itself is the already-dead DebugOverrideProxyUrl. Nothing there proves or disproves whether its actual request code rides VS Code's generic extension-host proxy-agent layer (which reads http.proxy / env vars) — that would live in its networking code, not its config layer, and hasn't been checked yet.

Update 2026-09-17 — upgraded from "disputed" to "very likely not implemented," per Microsoft's own current design docs. The checks above were against the archived vscode-copilot-chat snapshot; the real, current code moved into microsoft/vscode itself (src/vs/platform/agentHost/, extensions/copilot/). Checking there directly:

  • agentHost/node/copilot/copilotAgent.ts has a real COPILOT_PROXY_ENV_KEYS list and an invokeWithTemporaryProxyEnvironment() helper — but it has exactly one call site in the whole repo, wrapping only the managed settings fetch (an enterprise's admin-configured Copilot policy — getManagedSettings(), the client-side pull for the "Configure custom models" flow above). Not chat/completion traffic.
  • agentHost/node/networkDiagnosticsService.ts's PROXY_ENV_KEYS (plus a COPILOT_PROXY_KERBEROS_SPN entry) is diagnostics-only — it reports what env vars are set, it doesn't configure anything.
  • The decisive piece — agentHost/node/claude/CONTEXT.md, a real Microsoft design doc, filed under "Deferred for later phases": "HTTP proxy support (HTTP_PROXY/HTTPS_PROXY env vars, VS Code's http.proxy setting, PAC files, proxy auth). The Phase 2 proxy talks to CAPI through ICopilotApiService, so any outbound proxying is inherited from whatever HTTP client that service uses. If the agent host needs to honor user proxy configuration we'll need an explicit agent/dispatcher injection point on ICopilotApiService... Track separately when we pick this up." No NODE_EXTRA_CA_CERTS mention anywhere in it.

Caveat kept honest: agentHost/"Phase 2" reads like newer, possibly still-landing work unifying Copilot/Claude/Codex agent hosting inside VS Code core — not confirmed to be the exact path today's stable, marketplace-installed Copilot Chat extension runs on. But four independent pieces of evidence now agree (this doc, the archived repo's proxy-free networking layer, the single-purpose scope of the one real proxy helper, and the earlier GitHub issue on overrideProxyUrl) — enough to move this from a genuine dispute to "very likely not implemented." A live test (point HTTPS_PROXY at the gateway's listener with NODE_EXTRA_CA_CERTS set, launch VS Code with a real Copilot Chat install, check the gateway log for interception — the same discipline as the diagnose-*.ps1 scripts) would still close it fully, but it's no longer a coin-flip.

Alternative under consideration: fork the open-source extension

Both vscode (MIT, github.com/microsoft/vscode) and vscode-copilot-chat (MIT, github.com/microsoft/vscode-copilot-chat) are open source. Unlike every mechanism above — all of which depend on hoping the vendor's unmodified binary happens to read a setting/env var we control — a fork gives certainty: we own the code, so it can be made to read a config file we write and route through our proxy/CA by construction, no "does it honor this" ambiguity.

That certainty comes at a materially different cost than anything else in this doc, worth deciding deliberately rather than building quietly:

  • Every existing adapter is non-invasive — a config-delta write into a file the vendor's own unmodified install already reads. This would instead mean replacing the vendor's installed extension with our own compiled build — a first for this codebase's adapter model.
  • Distribution: the Marketplace version would need to be blocked from reinstalling over ours, and our build installed as an unsigned .vsix (VS Code supports this via code --install-extension, but it's a different deployment path than anything else here). Recurring cost, not one-time.
  • Ongoing maintenance: Copilot Chat ships frequently. A fork needs rebasing onto every upstream release indefinitely, or it drifts stale and loses whatever features/fixes ship upstream.
  • Policy angle: this is a modified build of GitHub's own product, silently substituted on managed endpoints, using the real user's real Copilot entitlement against GitHub's real backend. Legally fine under MIT, but a deliberate product decision, not a quick fix — same category of decision as the GitHub Copilot app's live-DB write question above.

Feasibility, checked against the actual source (2026-09-15):

  • microsoft/vscode-copilot-chat is archived (last commit 5863f5a, 2026-05-20): "This project has been moved into the main VS Code repository... development continues at github.com/microsoft/vscode." Forking this specific repo means forking a dead snapshot — the real, currently-shipping code now lives inside the vscode monorepo itself. "Fork the extension" in practice means tracking microsoft/vscode going forward, not this smaller, easier-looking repo.
  • The request path is a single, clean choke point, not scattered. Everything funnels through IFetcherService.fetch() → fetchWithFallbacks() (src/platform/networking/node/fetcherFallback.ts) into one of three IFetcher implementations. The most promising is node/nodeFetchFetcher.ts, which already uses undici with dispatcher: agent.value where agent = new Lazy(() => new undici.Agent({ allowH2: true })) — swapping this for a undici.ProxyAgent with a custom CA (connect: { ca }) is a small, targeted change at one file, not a sprawling rewrite.
  • No proxy/CA/agent handling exists anywhere in this layer today — it currently just inherits whatever VS Code's Electron main process already patched into the global fetch. This is consistent with every other finding in this doc: there's genuinely nothing to configure our way into, because nothing here reads a proxy or CA setting at all.
  • No local config file mechanism exists anywhere in the extension — all configuration goes through IConfigurationService, a thin wrapper over vscode.workspace.getConfiguration. Reading a file we control would be a pattern added from scratch, not an extension of something already there.
  • Build is ordinary and small: esbuild (npm run build/compile), then vsce package → .vsix. Not a heavy toolchain problem.

None of this changes the trade-offs above (replacing a vendor binary, distribution/update conflicts, ongoing tracking of a much larger repo than first assumed, the policy question) — it just confirms the code-level part is small and precisely located, so the decision is really about the distribution/maintenance/policy cost, not implementation difficulty.

Alternative goal: disable/hide Copilot Chat entirely, instead of intercepting it

Everything above is about intercepting Copilot Chat's traffic. If the actual goal is closer to blocking it — same category as a policy "block suspicious skill" rule elsewhere in this codebase — VS Code has a real, documented, working answer today, unlike interception:

The master switch, confirmed against VS Code's own docs (code.visualstudio.com/docs/setup/copilot) plus an independent source, not guessed:

{
    "chat.disableAIFeatures": true
}

This is a VS Code core setting (not a Copilot-extension-internal one). Official description: "Disable and hide built-in AI features provided by GitHub Copilot, including chat and inline suggestions." Confirmed to both disable the functionality AND hide the UI (chat icon/panel gone), at user or workspace scope in the same settings.json every other setting discussed in this doc lives in. Writing it programmatically is the exact same JSON-merge pattern this codebase already uses for every other agent's config file — mechanically trivial, and unlike the interception question, it actually works today.

More granular pieces, for partial control instead of the master switch:

  • "github.copilot.enable": {"*": false} — inline completions only, confirmed real, doesn't touch chat.
  • "chat.commandCenter.enabled": false — hides only the Chat icon in the title bar; doesn't disable the underlying feature or other entry points.
  • No confirmed dedicated "chat only, keep completions" flag was found — chat.disableAIFeatures is all-or-nothing by design.

The caveat: a settings.json write is user-reversible. A user who knows the key exists can delete it and reload. For something a user can't casually undo, there's a real VS Code enterprise policy that fits:

AllowedExtensions (extensions.allowed) — registry-backed at HKLM\SOFTWARE\Policies\Microsoft\VSCode on Windows, machine or user scope, confirmed since VS Code 1.96. Confirmed behavior: "If you block an extension or version that is already installed, the extension is disabled." Omitting github.copilot-chat (and github.copilot) from the allowlist disables them even if already installed, greys out reinstall in the Extensions UI, and can't be undone from inside VS Code. Since the daemon already runs elevated on Windows, it could write this registry key directly — the same "one admin-scoped write, machine-wide" mechanism discussed for the proxy idea above, just applied to blocking instead of intercepting. No dedicated Group-Policy/registry backing was found specifically for chat.disableAIFeatures itself (it appears to be settings.json-only today), so AllowedExtensions is the stronger lever if durability against a user undoing it matters.

Delivering AllowedExtensions machine-wide, verified per platform (2026-09-16)

The value format itself, checked against VS Code's actual TypeScript source (not another docs summary): each entry is true/false, the string 'stable', or an array of version-pattern strings; keys can be a bare publisher id ("microsoft", wildcards that publisher) or a full publisher.extension-id. So a real allowlist that blocks Copilot but keeps everything else already installed on a given machine looks like:

{"continue.continue":true,"anthropic.claude-code":true,"vscodevim.vim":true}

It's a strict allowlist, not a denylist — anything omitted is blocked or disabled, installed or not. There is no way to say "block only Copilot."

Two real reliability caveats, found while verifying this, not just a docs read: - microsoft/vscode#242895: the value is capped at 1024 characters (at least via Windows REG_SZ), and a VS Code maintainer confirmed it directly: "1024 is way too short for an allow list, we can't implement that policy." A longer JSON allowlist can silently get ignored, no error. - microsoft/vscode#240834: an unresolved report that the policy didn't block installation at all in one setup — inconclusive (their config used HKEY_CURRENT_USER, possibly a misconfiguration), but open and unexplained.

Windows — GPO owns this registry path; Intune's native path is blocked by design. AllowedExtensions lands at HKLM\SOFTWARE\Policies\Microsoft\VSCode\AllowedExtensions, the namespace traditional Group Policy (Active Directory, ADMX-templated, no enrollment needed — inherent to domain join) has always owned. Cloud-only Intune's Settings Catalog/ADMX ingestion deliberately refuses to write anywhere under Software\Policies\Microsoft\*, specifically to avoid two management systems silently fighting over the same key in a hybrid AD+Intune environment — so pushing this policy the normal Intune-console way does nothing, no error. The real-world fix (EternalR00ted/intune-vscode-extension-policy) is an Intune Remediation: a SYSTEM-context PowerShell script pair that writes the registry key directly, sidestepping Intune's own restriction — functionally the same move our own daemon would make.

Can ai-protect (elevated) write this itself? Yes on Windows, confirmed; genuinely unverified on macOS — don't treat them as equivalent. - Windows: yes. LocalSystem has unrestricted HKLM write access, no OS barrier, and the Intune Remediation workaround above is existing, real-world proof a SYSTEM-context process writing this exact key works. Same privilege class and mechanics as every other config write this codebase already does. - macOS: delivery is a different mechanism entirely — an Apple Configuration Profile (.mobileconfig), not a plain file. Checked the real template shipped inside this Mac's own VS Code install (/Applications/Visual Studio Code.app/Contents/Resources/app/policies/com.microsoft.VSCode.mobileconfig, v1.131.0) directly rather than trusting the docs' stale filename (vscode-sample.mobileconfig doesn't exist; the real file is com.microsoft.VSCode.mobileconfig). Findings from reading it: - No blanket "disable AI" policy exists in the real schema — only granular keys (ChatAgentMode, ChatPluginsEnabled, Claude3PIntegration, Codex3PIntegration, CopilotNextEditSuggestions, CopilotReviewAgent, CopilotSessionSync, ChatHooks, ChatMCP, …). Confirms chat.disableAIFeatures has no policy equivalent — AllowedExtensions (present, empty string by default) remains the only real machine-wide lever. - No PayloadScope key is set in the shipped template at all. Sources disagree on what an omitted scope defaults to, so don't rely on it — add <key>PayloadScope</key><string>System</string> explicitly at the outer dict to force a device-wide (all-users) profile rather than a per-user one. - The profiles CLI can no longer install profiles at all, confirmed via man profiles on this machine: "Starting with macOS 11.0 (profiles tool 8.0 or later), this tool cannot be used to install configuration profiles. You should add your profiles using the System Settings Profiles preference pane." So installation is either a human double-click + admin auth in System Settings, or a real MDM push (Jamf/Intune-for-Mac/Workspace ONE) — not something our root daemon can script locally the way it writes every other config file in this doc.

Current state on this laptop, verified three independent ways: no AllowedExtensions policy, and no VS Code policy of any kind, is configured here at all — not "set to empty," genuinely absent. No com.microsoft.VSCode.plist exists under /Library/Managed Preferences/ (machine) or ~/Library/Managed Preferences/ (user); no cached reference to it anywhere in VS Code's own storage; defaults read com.microsoft.VSCode AllowedExtensions returns "The domain/default pair... does not exist," not an empty value. This machine is genuinely MDM-enrolled (AirWatch/ Workspace ONE — real com.airwatch.* and com.zscaler.aiprotect.plist managed-preference files are present) but that enrollment simply has never targeted VS Code.

The two open questions from the SIP/cache discussion above are now substantially resolved, by reading microsoft/vscode-policy-watcher's actual macOS source (src/macos/PreferencesPolicy.hh, PolicyWatcher.cc) rather than guessing: - No signature check, no separate validation API. It calls the standard CFPreferencesAppValueIsForced(key, appID) / CFPreferencesCopyAppValue — the exact same Apple API any macOS app uses for managed preferences. Nothing VS Code-specific stands between a plain plist and being read as policy. - It watches /Library/Managed Preferences/ directly via FSEvents — FSEventStreamCreate on that literal path. Combined with Apple's own documented CFPreferencesCopyAppValue search-path behavior (which independent sources confirm treats this directory as real, authoritative storage for MDM-delivered preferences, not a projected cache), a correctly-formatted file dropped there would very likely be picked up. - Still open: whether a live MDM check-in reconciles or sweeps away a foreign file it doesn't recognize as coming from a profile it pushed. No documentation found either way; no profile daemon was running on this machine at the time of checking to test it live. Architecturally the safe assumption is that an MDM only reconciles what it itself pushed — but that is an assumption, not a verified result.

A concrete test recipe exists to close the remaining gap — written for a disposable VM (snapshot first), not this real, managed laptop: write the plist directly, verify defaults read and VS Code's own startup log (grep -i policy ~/Library/Application\ Support/Code/logs/*/main.log) pick it up, then (optional, needs a sandbox MDM tenant) force a check-in and see whether the manual file survives or gets reconciled against a real MDM-pushed payload. Not yet run; results pending.

Alternative: replace Copilot with Continue and/or the Claude Code extension

Rather than intercepting or blocking Copilot Chat, a different question: can another already-installed VS Code extension cover what Copilot provides, end to end — pointing at our local proxy, understanding/summarizing code, generating and pushing changes, and integrating with inline autocomplete? Checked ~/.vscode/extensions/anthropic.claude-code-2.1.273-darwin-arm64/extension.js directly (static analysis of the real shipped bundle):

  • Proxy-awareness is real and structural, not assumed. The bundle contains HTTPS_PROXY, HTTP_PROXY, NODE_EXTRA_CA_CERTS, and ANTHROPIC_BASE_URL as literal strings, sitting in the same table as unmistakably-CLI-internal names (CLAUDE_STREAM_IDLE_TIMEOUT_MS, MAX_THINKING_TOKENS, MAX_MCP_OUTPUT_TOKENS) — the extension bundles the same core engine as the CLI, not a separate reimplementation. child_process/spawn(/execFile( are all present too.
  • One unambiguous, decisive line: vscode.workspace.getConfiguration ("http").get("proxy"), used to set a behindProxy flag. Net read: neither extension alone is a clean single-swap replacement for everything Copilot Chat plus Copilot's inline suggestions do. Continue is the closer single-extension fit (proxy, autocomplete, and agent mode are all first-class and confirmed); Claude Code is the stronger fit specifically for interception and heavy agentic work, since it's already proven in this product rather than merely documented, but it does not touch autocomplete at all. A realistic setup likely pairs them — Continue for the autocomplete role Copilot currently owns, Claude Code (already brokered) for the deep agentic work — rather than picking a single replacement.

Forward-looking idea: wiring Continue as a real, brokered agent

The port our gateway's listener binds to is chosen dynamically at runtime (ports::candidates()'s retry list) and threaded through to each agent's config at render time — every existing Llm:: shape already assumes this. So "configure Continue to use the local proxy" is not a static value to hand-type into ~/.continue/config.yaml; it means making Continue a real target of that same pipeline. Recorded here as a next step, not built:

  1. A new continue.rs agent adapter (parallel to copilot.rs / devin.rs) — an AgentSpec with install_dirs: &[".continue"], targeting config.yaml.
  2. A new Llm:: render shape. Every existing shape (Env, ProxyPath) writes a scalar at a fixed nested key. Continue needs a model entry appended/upserted into a models array by name ({name, apiBase, roles}) — a different write pattern than anything config_render.rs does today.
  3. YAML file support may not exist yet. Everything seen in apply_config_delta/config_render so far has been JSON/TOML-oriented (.vscode/mcp.json's JSONC comment-preservation was already flagged as a follow-up elsewhere). config.yaml being YAML, not JSON, may need the file-merge machinery itself extended — needs confirming, not assumed.
  4. BaseUrl-style semantics fit better than ForwardProxy. Continue's apiBase redirects straight to a local URL with no CA/CONNECT-tunnel involved, matching the intent of Llm::BaseUrl far more than the ForwardProxy shape Devin/Copilot CLI use — but the array-upsert mechanic above is new regardless of which routing variant it hangs off.

Incidental finding, not a gap: the separate continue.dev VS Code extension (unrelated to GitHub Copilot, present on this machine) does support a custom proxy endpoint and headers via its config.json's apiBase / requestOptions.headers fields — confirmed against Continue's own docs. Noted only to show the gap is Copilot Chat specifically refusing this pattern, not that no VS Code extension can support it.

The embedded SQL text is real (it's the literal shipped code, not a paraphrase or inference), so the schema itself can be trusted as accurate. But nothing here is GitHub-published or GitHub-supported: no commitment it stays stable across an update, and the docs/byok.md reference below is a comment pointing at an internal doc we don't have, not something we read ourselves.

  • The binary's embedded SQL migration history is readable, and it names the design. A code comment reads: "BYOK (Bring Your Own Key) tables. Stores user-configured model providers and the models they expose to the app... See plan in docs/byok.md... for the full design." This is the real, first-party, named feature — not a coincidental field we happened to find.
  • model_providers is literally the same table as byok_providers. A later migration in the same embedded history runs ALTER TABLE byok_providers RENAME TO model_providers. The baseUrl field found in the original investigation is the BYOK storage, post-rename — we had already found the right field, without knowing at the time it was a named, designed feature rather than an internal implementation detail.
  • The full pre-rename schema is recoverable from the binary, giving a real, confirmed shape to build against instead of a guess: sql CREATE TABLE byok_providers ( id TEXT PRIMARY KEY NOT NULL, name TEXT NOT NULL, type TEXT NOT NULL CHECK (type IN ('openai','azure','anthropic','ollama','foundry_local','custom')), base_url TEXT NOT NULL, wire_api TEXT NOT NULL DEFAULT 'completions' CHECK (wire_api IN ('completions','responses')), auth_kind TEXT NOT NULL DEFAULT 'api_key' CHECK (auth_kind IN ('api_key','bearer_token','none')), headers_json TEXT NOT NULL DEFAULT '{}', -- + created_at, updated_at ); CREATE TABLE byok_models ( id TEXT PRIMARY KEY NOT NULL, provider_id TEXT NOT NULL REFERENCES byok_providers(id) ON DELETE CASCADE, model_id TEXT NOT NULL, -- + wire_model, display_name, max_prompt_tokens, max_output_tokens, … ); type='custom' with auth_kind='none' is exactly the shape a local, no-auth endpoint needs — a session then selects it via a sessions.model = 'byok:<provider_id>:<model_id>' string, confirmed from the same embedded SQL. Secrets are kept out of the DB entirely, in the OS keychain under byok:<provider_id>:apiKey / ...:bearerToken.
  • Update 2026-09-17 — the URL override is confirmed at the runtime code level, not just the schema. Read the actual BYOK provider source now that it's visible in microsoft/vscode (extensions/copilot/src/extension/byok/vscode-node/openAIProvider.ts and anthropicProvider.ts): both hardcode a default ('https://api.openai.com/v1', 'api.anthropic.com'), but that constant backs only getModelsBaseUrl() — the "fetch models" convenience button. The actual completion request (createOpenAIEndPoint()) builds its URL from model.url, the value stored in the provider's own row. So even a type='openai' (not just type='custom') provider's real inference call uses whatever URL is actually configured, not the hardcoded default — the runtime path genuinely uses stored config, not just the schema allowing it in theory.
  • Two distinct BYOK mechanisms exist — only one is reachable from a local proxy. GitHub's enterprise admin console has its own, separate "Configure custom models" flow (AI controls → Copilot), confirmed entirely server-side: the admin's key and endpoint are held by GitHub's platform and pushed down to clients through it. That one is useless for us — GitHub's servers can't reach a 127.0.0.1 loopback listener. The relevant one is the per-device byok_providers table above, confirmed to work "without a signed-in GitHub account" and be "global per app install" — evaluated locally, by the app itself.
  • No file, CLI, or programmatic path is documented for the per-device version — confirmed against GitHub's own how-to doc, GUI-only (Settings → Model providers → Add provider). Automating it without user interaction still means either a direct DB write or driving the actual GUI once per device; nothing changed about that part of the risk below.

The enterprise flow's actual parameters, and where inference calls really go

Enumerated directly from GitHub's admin how-to doc (enable-custom-models), not summarized loosely — every field the flow exposes:

Provider Supported URL configurable?
OpenAI, Anthropic, xAI Yes — key entered, then a "fetch models" button queries the provider server-side No URL field described — implies a fixed, known endpoint per provider
AWS Bedrock, Google AI Studio Listed as supported Not detailed in what this doc surfaced
Microsoft Foundry Yes Yes — explicit "Deployment URL" field, manually entered, plus manual per-model "Model ID" entries (no auto-fetch)
OpenAI-compatible providers Listed as supported Genuine documentation gap — this category needs some base-URL field by definition, but the fetched page doesn't describe one anywhere. Not confirmed either way.

Other fields: Name (text, "shown in the model picker" — the source of the "under the enterprise name" label), API Key (text, with an explicit least-privilege-scoping recommendation), and Access scoping ("Allow for all organizations" or per-organization checkboxes, only available once a model is set to "Enabled").

Whether actual inference calls get relayed through GitHub's own backend is architecture-inferred, not directly confirmed by any doc — worth holding to a lower confidence bar than everything sourced from gh search code above:

  • Enterprise custom models: very likely relayed through GitHub's CAPI backend for every real inference call, not just the one-time model-list fetch. Basis: the provider API key is entered once, centrally, and never described as being handed to client machines — a client that never holds the credential can't call OpenAI/Anthropic/xAI directly itself, so GitHub's own backend is almost certainly the one making that outbound call and relaying the response. Reasoned from the security model (least-privilege key scoping, key held centrally), not a quoted statement that calls are proxied.
  • Personal/per-device BYOK (the byok_providers/model_providers table above): the opposite architecture — the key lives in the local OS keychain, and the flow is documented to work "without a signed-in GitHub account." No reason for GitHub's servers to be in the loop at all; the client almost certainly calls the configured provider (or a local type='custom' endpoint) directly. Same confidence caveat: reasoned, not quoted.
  • Either way, this doesn't change the operative conclusion for our purposes: the enterprise flow is unreachable from a local proxy because the calling machine is GitHub's servers, not the endpoint; the per-device flow is reachable in principle (§ above) precisely because the call originates locally, whichever exact path it takes to get there.
  • A real dependency for that plan, confirmed via GitHub's own docs: the two BYOK tiers are additive by default (enterprise-pushed models and personal BYOK entries coexist in the same model picker), but there's a one-directional admin kill-switch specifically over the personal side — a policy literally named "Bring Your Own Language Model Key in VS Code." If an org has disabled it (a plausible move for exactly the security-conscious orgs likely to care about this doc), personal BYOK is unavailable org-wide, before any DB-write question even applies. Worth checking that policy's state as an early step in any rollout, not an afterthought discovered after the write already "succeeded."

Why a direct write still isn't a "wrong path" fix

  • The DB is open and actively written to right now — two running instances of the app on this machine, with the WAL file growing during the investigation. Writing into it from outside the app risks corruption, or being silently overwritten by the app's own next commit, unless done with real SQLite transaction discipline (and ideally the app's own cooperation — e.g. writing only while it's confirmed not to be mid-write, which nothing in our current tooling attempts).
  • No existing code path fits. Every adapter in this repo assumes a mergeable JSON/TOML file (ConfigDelta → config_render → apply_config_delta's file merge). None of that machinery knows how to address a database row.
  • The schema is now confirmed from the shipped binary itself, not guessed — but that is not the same as GitHub-published or GitHub-supported. The update above replaces "nothing indexed publicly describes this schema" with a real, extracted one, which meaningfully lowers the guessing risk named in the original finding. It does not remove the stability risk: this came from strings on a private binary, not a formal doc or open-source repo, so nothing commits GitHub to this shape staying the same release to release, and writing outside the app's own code still bypasses whatever validation/side effects the real "Add provider" flow performs.

Recommended paths forward

  1. Don't attempt a live-DB write without explicit product sign-off, admin privilege notwithstanding. Root/LocalSystem removes the permissions barrier, not the concurrency hazard — the write still races the app's own live process for the same file, can be silently overwritten by its next flush, and skips whatever validation/keychain/cache-invalidation the real "Add provider" flow performs. The blast radius is a user-facing app's entire local state (sessions, workspaces, worktrees — this DB is not a small, single-purpose config file).
  2. The schema risk is now real and confirmed rather than unknown, which changes the shape of "new product design work," not its necessity. byok_providers/model_providers (same table, renamed) is a genuine, named, first-party feature with a confirmed shape — type='custom', auth_kind='none', base_url pointed at our local listener. Two realistic directions, same as before but on firmer ground: - Build careful, transaction-safe SQLite write tooling against this now- confirmed schema, with the same "narrow trust, confirm against live install, never guess a schema" discipline established elsewhere in this codebase — and still accept re-validation on every app update, since GitHub doesn't publish this schema and nothing commits it to staying stable. - Push for a supported, non-GUI way to provision the per-device BYOK provider (GitHub's own docs confirm none exists today — Settings UI only) rather than reverse-engineering the write. The enterprise "Configure custom models" flow is not a substitute — it's server-side and can't reach a 127.0.0.1 listener.
  3. VS Code claim — the "which surface was tested" question is resolved (almost certainly the CLI in a terminal), but the mechanism question is reopened, not closed. Copilot Chat's own internal debug settings are confirmed dead, and writing them via settings.json programmatically (mechanically trivial, same JSON-merge pattern used elsewhere here) would accomplish nothing. But the generic HTTPS_PROXY/HTTP_PROXY + NODE_EXTRA_CA_CERTS mechanism is unresolved — GitHub's own docs say it works, real user reports say it doesn't, and it needs a live test (see "Reopened" above) rather than a decision from secondary sources either way.
  4. If a live test confirms the extension can't be redirected, decide deliberately whether to fork vscode-copilot-chat (MIT, open source) rather than treat "no supported hook" as the end of the line — see "Alternative under consideration: fork the open-source extension" above. This is a heavier, different-shaped commitment than every other item in this doc (replacing a vendor binary instead of writing a config delta into one), so it needs the same explicit sign-off as the live-DB write question below, not a default yes.
  5. If the actual goal is blocking rather than intercepting, prefer chat.disableAIFeatures: true — a real, working, documented VS Code core setting today, unlike interception. Use AllowedExtensions (registry-backed) instead when the block needs to survive a user undoing it. See "Alternative goal: disable/hide Copilot Chat entirely" above.
  6. Microsoft 365 Copilot app: no further action recommended. Flag to whoever raised the original report that it's a different product with a different backend, not a coverage gap in this adapter.
