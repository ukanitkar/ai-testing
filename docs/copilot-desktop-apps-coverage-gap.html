"Copilot doesn't work" outside VS Code — findings

Written 2026-09-15, in response to a field report that "the Copilot work we have done works for VS Code, but not for GitHub app and Copilot app." Short answer: the report conflates three (really four) distinct surfaces that share the word "Copilot," only one of which our ai-gateway adapter (ai-gateway/agent-manager/src/agents/copilot.rs) ever targeted. This isn't a regression in existing code — it's a scope question, and one of the two named apps turns out to need a different kind of solution than a config key we got wrong.

Update 2026-09-15: the VS Code Copilot Chat question (row 2 below) was partially resolved, then reopened same-day on a generic env-var/CA-cert mechanism that needs live verification — see its own section for the current state. The GitHub Copilot app remains the other open surface.

The four surfaces, disambiguated

Surface What it actually is In our adapter's scope today?
GitHub Copilot CLI (copilot command, npm @github/copilot) The thing copilot.rs was built for Yes — this is "the Copilot work" that exists
VS Code's built-in Copilot Chat extension A separate code path inside VS Code itself No, and confirmed correctly so — vscode.rs has llm: LlmRouting::None, and the extension itself has no working redirect mechanism to target. See "VS Code's built-in Copilot Chat extension" below
GitHub Copilot app (github.com/features/ai/github-app) A brand-new, separate desktop application — "the only desktop experience for agent-driven development built natively on GitHub." Not the classic GitHub Desktop git client No — never targeted. See findings below; bringing it in scope needs new, riskier tooling

Talks to Outlook/Word/Excel/PowerPoint, not GitHub's Copilot backend Out of scope permanently — there is no shared backend to intercept. This is a category error, not a gap

VS Code's built-in Copilot Chat extension — reopened 2026-09-15

Investigated as the third surface in the table above, since it's the one most likely to be what the original "works for VS Code" report actually meant.

Our own code already treats this as out of scope, and correctly so. ai-gateway/agent-manager/src/agents/vscode.rs sets llm: LlmRouting::None and the adapter is dormant — "vscode" isn't in ENABLED_AGENTS. Discovery maps a vscode session to the copilot broker identity purely because "Copilot Chat is the agent behind the editor" (its own doc comment), but that's identity attribution only: copilot.rs's actual redirect mechanism writes to ~/.copilot/mcp-config.json / ~/.copilot/settings.json — the standalone CLI's home directory, which the VS Code extension never reads. docs/SYSTEM-OVERVIEW.md already flagged this: "the VS Code Copilot Chat extension's sessions stay opaque."

No working interception mechanism exists in the extension itself, either. Verified against the extension's own contributed-settings schema and a maintainer-tracked issue, not guessed:

  • github.copilot.advanced.debug.overrideProxyUrl / overrideCapiUrl are real settings, but their documented purpose is overriding the GitHub authentication proxy, not chat/inference traffic — and a confirmed GitHub issue shows github.copilot-chat ignores them entirely; only the older, separate inline-completion extension (github.copilot) honors them.
  • VS Code's supported customization path, BYOK (chatLanguageModels.json), is strictly additive — it registers a new selectable model next to Copilot's own in the model picker, requiring manual/pinned selection. It cannot redirect or intercept Copilot's own default traffic.
  • On this Mac, the extension isn't even installed (chatLanguageModels.json is []; no github.copilot-chat under ~/.vscode/extensions), consistent with nobody having wired a live config surface for it.

A subsequent AI-generated answer (Google AI Mode) claimed a github.copilot.advanced.requestHeaders field and a working debug.overrideProxyUrl redirect for Copilot Chat specifically — checked against the extension's real schema and found fabricated (requestHeaders isn't a real contributed setting at all) and contradicted by the issue above. Worth remembering as a caution on trusting AI-search answers for config specifics, not a new finding about the product itself.

Conclusion (as of the settings-only check above): the field report's "works for VS Code" almost certainly meant the copilot CLI run inside a VS Code integrated terminal — the one path our adapter genuinely brokers — not the Copilot Chat extension. This closes the open question below about which surface was originally tested, independent of the reopened question below about whether a different mechanism could still redirect the extension's own traffic.

Reopened: the generic env-var + CA-cert path is unresolved, not dead

The finding above only rules out Copilot Chat's own internal debug setting. It doesn't rule out the same generic mechanism our other adapters already rely on: HTTPS_PROXY/HTTP_PROXY env vars for redirection plus NODE_EXTRA_CA_CERTS for CA trust. Two authoritative-looking sources directly disagree on whether this works for VS Code Copilot Chat:

  • GitHub's own docs (docs.github.com/en/copilot/concepts/network-settings) document HTTPS_PROXY > https_proxy > HTTP_PROXY > http_proxy (in that priority order) as Copilot's supported proxy mechanism, and NODE_EXTRA_CA_CERTS as the supported CA-trust mechanism for a TLS-intercepting proxy.
  • Real user reports contradict it for this extension specifically: a GitHub issue states the Copilot agent ignores NODE_EXTRA_CA_CERTS outright, corporate-proxy-with-custom-CA setups are reported broken for Copilot Chat, and the practical workaround people actually use is a third-party extension (Win-CA) that bridges the Windows OS certificate store into VS Code's trust — broad OS-store trust, not the narrow per-agent NODE_EXTRA_CA_CERTS trust this codebase's own design deliberately favors elsewhere (see ai-gateway/listener/src/certs.rs's design doc).
  • Checking the open-source vscode-copilot-chat extension's own configurationService.ts directly: the only proxy-related setting it defines itself is the already-dead DebugOverrideProxyUrl. Nothing there proves or disproves whether its actual request code rides VS Code's generic extension-host proxy-agent layer (which reads http.proxy / env vars) — that would live in its networking code, not its config layer, and hasn't been checked yet.

Not settled either way. Needs a live test (point HTTPS_PROXY at the gateway's listener with NODE_EXTRA_CA_CERTS set, launch VS Code with a real Copilot Chat install, check the gateway log for interception — the same discipline as the diagnose-*.ps1 scripts) before this line item can be closed in either direction.

Alternative under consideration: fork the open-source extension

Both vscode (MIT, github.com/microsoft/vscode) and vscode-copilot-chat (MIT, github.com/microsoft/vscode-copilot-chat) are open source. Unlike every mechanism above — all of which depend on hoping the vendor's unmodified binary happens to read a setting/env var we control — a fork gives certainty: we own the code, so it can be made to read a config file we write and route through our proxy/CA by construction, no "does it honor this" ambiguity.

That certainty comes at a materially different cost than anything else in this doc, worth deciding deliberately rather than building quietly:

  • Every existing adapter is non-invasive — a config-delta write into a file the vendor's own unmodified install already reads. This would instead mean replacing the vendor's installed extension with our own compiled build — a first for this codebase's adapter model.
  • Distribution: the Marketplace version would need to be blocked from reinstalling over ours, and our build installed as an unsigned .vsix (VS Code supports this via code --install-extension, but it's a different deployment path than anything else here). Recurring cost, not one-time.
  • Ongoing maintenance: Copilot Chat ships frequently. A fork needs rebasing onto every upstream release indefinitely, or it drifts stale and loses whatever features/fixes ship upstream.
  • Policy angle: this is a modified build of GitHub's own product, silently substituted on managed endpoints, using the real user's real Copilot entitlement against GitHub's real backend. Legally fine under MIT, but a deliberate product decision, not a quick fix — same category of decision as the GitHub Copilot app's live-DB write question above.

Feasibility, checked against the actual source (2026-09-15):

  • microsoft/vscode-copilot-chat is archived (last commit 5863f5a, 2026-05-20): "This project has been moved into the main VS Code repository... development continues at github.com/microsoft/vscode." Forking this specific repo means forking a dead snapshot — the real, currently-shipping code now lives inside the vscode monorepo itself. "Fork the extension" in practice means tracking microsoft/vscode going forward, not this smaller, easier-looking repo.
  • The request path is a single, clean choke point, not scattered. Everything funnels through IFetcherService.fetch() → fetchWithFallbacks() (src/platform/networking/node/fetcherFallback.ts) into one of three IFetcher implementations. The most promising is node/nodeFetchFetcher.ts, which already uses undici with dispatcher: agent.value where agent = new Lazy(() => new undici.Agent({ allowH2: true })) — swapping this for a undici.ProxyAgent with a custom CA (connect: { ca }) is a small, targeted change at one file, not a sprawling rewrite.
  • No proxy/CA/agent handling exists anywhere in this layer today — it currently just inherits whatever VS Code's Electron main process already patched into the global fetch. This is consistent with every other finding in this doc: there's genuinely nothing to configure our way into, because nothing here reads a proxy or CA setting at all.
  • No local config file mechanism exists anywhere in the extension — all configuration goes through IConfigurationService, a thin wrapper over vscode.workspace.getConfiguration. Reading a file we control would be a pattern added from scratch, not an extension of something already there.
  • Build is ordinary and small: esbuild (npm run build/compile), then vsce package → .vsix. Not a heavy toolchain problem.

None of this changes the trade-offs above (replacing a vendor binary, distribution/update conflicts, ongoing tracking of a much larger repo than first assumed, the policy question) — it just confirms the code-level part is small and precisely located, so the decision is really about the distribution/maintenance/policy cost, not implementation difficulty.

Alternative goal: disable/hide Copilot Chat entirely, instead of intercepting it

Everything above is about intercepting Copilot Chat's traffic. If the actual goal is closer to blocking it — same category as a policy "block suspicious skill" rule elsewhere in this codebase — VS Code has a real, documented, working answer today, unlike interception:

The master switch, confirmed against VS Code's own docs (code.visualstudio.com/docs/setup/copilot) plus an independent source, not guessed:

{
    "chat.disableAIFeatures": true
}

This is a VS Code core setting (not a Copilot-extension-internal one). Official description: "Disable and hide built-in AI features provided by GitHub Copilot, including chat and inline suggestions." Confirmed to both disable the functionality AND hide the UI (chat icon/panel gone), at user or workspace scope in the same settings.json every other setting discussed in this doc lives in. Writing it programmatically is the exact same JSON-merge pattern this codebase already uses for every other agent's config file — mechanically trivial, and unlike the interception question, it actually works today.

More granular pieces, for partial control instead of the master switch:

  • "github.copilot.enable": {"*": false} — inline completions only, confirmed real, doesn't touch chat.
  • "chat.commandCenter.enabled": false — hides only the Chat icon in the title bar; doesn't disable the underlying feature or other entry points.
  • No confirmed dedicated "chat only, keep completions" flag was found — chat.disableAIFeatures is all-or-nothing by design.

The caveat: a settings.json write is user-reversible. A user who knows the key exists can delete it and reload. For something a user can't casually undo, there's a real VS Code enterprise policy that fits:

AllowedExtensions (extensions.allowed) — registry-backed at HKLM\SOFTWARE\Policies\Microsoft\VSCode on Windows, machine or user scope, confirmed since VS Code 1.96. Confirmed behavior: "If you block an extension or version that is already installed, the extension is disabled." Omitting github.copilot-chat (and github.copilot) from the allowlist disables them even if already installed, greys out reinstall in the Extensions UI, and can't be undone from inside VS Code. Since the daemon already runs elevated on Windows, it could write this registry key directly — the same "one admin-scoped write, machine-wide" mechanism discussed for the proxy idea above, just applied to blocking instead of intercepting. No dedicated Group-Policy/registry backing was found specifically for chat.disableAIFeatures itself (it appears to be settings.json-only today), so AllowedExtensions is the stronger lever if durability against a user undoing it matters.

Alternative: replace Copilot with Continue and/or the Claude Code extension

Rather than intercepting or blocking Copilot Chat, a different question: can another already-installed VS Code extension cover what Copilot provides, end to end — pointing at our local proxy, understanding/summarizing code, generating and pushing changes, and integrating with inline autocomplete? Checked against the two extensions actually installed on this Mac (continue.continue-2.0.0, anthropic.claude-code-2.1.273), not hypothetically.

Verified further below: the extension itself is proxy-aware in its own bundled code, not just inheriting this by luck.

Verified against the extension's actual bundled code, not guessed

Checked ~/.vscode/extensions/anthropic.claude-code-2.1.273-darwin-arm64/extension.js directly (static analysis of the real shipped bundle):

  • Proxy-awareness is real and structural, not assumed. The bundle contains HTTPS_PROXY, HTTP_PROXY, NODE_EXTRA_CA_CERTS, and ANTHROPIC_BASE_URL as literal strings, sitting in the same table as unmistakably-CLI-internal names (CLAUDE_STREAM_IDLE_TIMEOUT_MS, MAX_THINKING_TOKENS, MAX_MCP_OUTPUT_TOKENS) — the extension bundles the same core engine as the CLI, not a separate reimplementation. child_process/spawn(/execFile( are all present too.
  • One unambiguous, decisive line: vscode.workspace.getConfiguration ("http").get("proxy"), used to set a behindProxy flag. The extension actively reads VS Code's own core http.proxy setting — the exact thing Copilot Chat was confirmed not to do anywhere in its config layer (see the reopened section above). This is a real, structural difference between the two extensions, not a hope that one happens to inherit something.
  • Correction, made against this same evidence: an earlier pass in this investigation (secondary/web-search sourced, not checked against the real bundle at the time) claimed the extension registers its own ghost-text inline-completion provider. Checked directly — wrong. No registerInlineCompletionItemProvider / InlineCompletionItemProvider string exists anywhere in the bundle, and package.json's real command list (acceptProposedDiff / rejectProposedDiff) confirms the actual interaction model is a review/accept-reject diff workflow, not keystroke-level autocomplete. Same failure mode as the Google AI Mode doc earlier in this write-up, just from a web search this time instead of AI Mode — corrected the same way, by checking the real artifact rather than trusting the secondary source.

Net read: neither extension alone is a clean single-swap replacement for everything Copilot Chat plus Copilot's inline suggestions do. Continue is the closer single-extension fit (proxy, autocomplete, and agent mode are all first-class and confirmed); Claude Code is the stronger fit specifically for interception and heavy agentic work, since it's already proven in this product rather than merely documented, but it does not touch autocomplete at all. A realistic setup likely pairs them — Continue for the autocomplete role Copilot currently owns, Claude Code (already brokered) for the deep agentic work — rather than picking a single replacement.

Forward-looking idea: wiring Continue as a real, brokered agent

The port our gateway's listener binds to is chosen dynamically at runtime (ports::candidates()'s retry list) and threaded through to each agent's config at render time — every existing Llm:: shape already assumes this. So "configure Continue to use the local proxy" is not a static value to hand-type into ~/.continue/config.yaml; it means making Continue a real target of that same pipeline. Recorded here as a next step, not built:

  1. A new continue.rs agent adapter (parallel to copilot.rs / devin.rs) — an AgentSpec with install_dirs: &[".continue"], targeting config.yaml.
  2. A new Llm:: render shape. Every existing shape (Env, ProxyPath) writes a scalar at a fixed nested key. Continue needs a model entry appended/upserted into a models array by name ({name, apiBase, roles}) — a different write pattern than anything config_render.rs does today.
  3. YAML file support may not exist yet. Everything seen in apply_config_delta/config_render so far has been JSON/TOML-oriented (.vscode/mcp.json's JSONC comment-preservation was already flagged as a follow-up elsewhere). config.yaml being YAML, not JSON, may need the file-merge machinery itself extended — needs confirming, not assumed.
  4. BaseUrl-style semantics fit better than ForwardProxy. Continue's apiBase redirects straight to a local URL with no CA/CONNECT-tunnel involved, matching the intent of Llm::BaseUrl far more than the ForwardProxy shape Devin/Copilot CLI use — but the array-upsert mechanic above is new regardless of which routing variant it hangs off.

Incidental finding, not a gap: the separate continue.dev VS Code extension (unrelated to GitHub Copilot, present on this machine) does support a custom proxy endpoint and headers via its config.json's apiBase / requestOptions.headers fields — confirmed against Continue's own docs. Noted only to show the gap is Copilot Chat specifically refusing this pattern, not that no VS Code extension can support it.

The rest of this doc is about the GitHub Copilot app, since it's the one remaining case where "we should support this" is a coherent, open ask.

What was actually found (live install, this Mac, 2026-09-15)

/Applications/GitHub Copilot.app, home dir ~/.copilot/ (shared with the CLI's own home dir name, which is itself a little misleading — see below).

The files our adapter writes to don't exist on this real, actively-used install at all:

~/.copilot/
├── config.json              # app-level metadata only (firstLaunchAt, appTipShown, …) — NOT settings.json
├── data.db (+ -shm, -wal)   # SQLite, actively open — this is where real config lives
├── session-store.db
├── repo-metadata-cache.db
├── servers/                 # empty
├── ide/                     # empty
├── installed-plugins/       # empty
└── logs/, run/, session-state/, hooks/, media-cache/

No mcp-config.json. No settings.json. config.json only carries UI/app metadata (appTipShown, reasoningSummariesCleanupDone, …), nothing resembling an MCP registry or an LLM redirect.

The actual config lives in data.db (SQLite)

Two tables matter for the LLM leg:

CREATE TABLE model_providers (
    id TEXT PRIMARY KEY NOT NULL,
    name TEXT NOT NULL,
    type TEXT NOT NULL DEFAULT 'openai',
    settings_json TEXT NOT NULL DEFAULT '{}',
    account_id TEXT REFERENCES accounts(id) ON DELETE CASCADE,
    -- + created_at, updated_at
);

CREATE TABLE provider_models (
    id TEXT PRIMARY KEY NOT NULL,
    provider_id TEXT NOT NULL REFERENCES model_providers(id) ON DELETE CASCADE,
    model_id TEXT NOT NULL,
    wire_model TEXT,
    -- + display_name, max_prompt_tokens, max_output_tokens, wire_api_override, …
);

The live row, on this install:

model_providers:
  id             = github_copilot:eb941f95-68df-4c6a-873d-5a3f4c959166
  name           = GitHub Copilot
  type           = github_copilot
  settings_json  = {"authKind":"none","baseUrl":"","headersJson":"{}","wireApi":"responses"}
  account_id     = eb941f95-68df-4c6a-873d-5a3f4c959166

baseUrl is the field. It's a JSON key, inside a TEXT column, inside a SQLite row — not a file our apply_config_delta/JSON-merge machinery can touch. provider_models is empty (0 rows) on this install.

No MCP-server-definition table exists anywhere in the schema. The only MCP-adjacent tables are session-scoped event logs (session_managed_mcp_event_display_names, session_mcp_event_sources) — tracking, not configuration. This lines up with a public search finding (unverified against this app specifically, flagged as such) that MCP config for GitHub's newer surfaces has moved to a per-project file (<project>/.copilot/mcp-config.json), not the per-user-home file our adapter targets. Not confirmed against this exact app; the app's own worktree checkouts inspected during this investigation (under ~/work/zax/copilot-worktrees/) had no such file, but those may not be representative of where a real MCP config would land.

Why this isn't a "wrong path" fix

  • The DB is open and actively written to right now — two running instances of the app on this machine, with the WAL file growing during the investigation. Writing into it from outside the app risks corruption, or being silently overwritten by the app's own next commit, unless done with real SQLite transaction discipline (and ideally the app's own cooperation — e.g. writing only while it's confirmed not to be mid-write, which nothing in our current tooling attempts).
  • No existing code path fits. Every adapter in this repo assumes a mergeable JSON/TOML file (ConfigDelta → config_render → apply_config_delta's file merge). None of that machinery knows how to address a database row.
  • No stable, documented schema to build against. This app is new enough that nothing indexed publicly describes data.db's schema. Everything above came from inspecting a real, live install directly — the same discipline this codebase's own adapters insist on elsewhere (e.g. Devin's, Grok's, and Kiro's doc comments all cite "confirmed against a live install" or "UNVERIFIED" explicitly) — but it means the schema found here could change without notice on the app's next update, with no changelog to watch.

Recommended paths forward

  1. Don't attempt a live-DB write without explicit product sign-off. The corruption/silent-overwrite risk is real and the blast radius is a user-facing app's entire local state (sessions, workspaces, worktrees — this DB is not a small, single-purpose config file).
  2. If this surface is a real priority, treat it as new product design work, not a bugfix. Two realistic directions: - Build careful, transaction-safe SQLite write tooling specifically for this app, with the same "narrow trust, confirm against live install, never guess a schema" discipline already established elsewhere in this codebase — and accept it needs re-validation on every app update until GitHub documents the schema (if ever). - Wait for/push for the app to expose a supported external configuration surface (an env var, a CLI flag, a documented settings file, an IPC endpoint) rather than reverse-engineering its private database.
  3. VS Code claim — the "which surface was tested" question is resolved (almost certainly the CLI in a terminal), but the mechanism question is reopened, not closed. Copilot Chat's own internal debug settings are confirmed dead, and writing them via settings.json programmatically (mechanically trivial, same JSON-merge pattern used elsewhere here) would accomplish nothing. But the generic HTTPS_PROXY/HTTP_PROXY + NODE_EXTRA_CA_CERTS mechanism is unresolved — GitHub's own docs say it works, real user reports say it doesn't, and it needs a live test (see "Reopened" above) rather than a decision from secondary sources either way.
  4. If a live test confirms the extension can't be redirected, decide deliberately whether to fork vscode-copilot-chat (MIT, open source) rather than treat "no supported hook" as the end of the line — see "Alternative under consideration: fork the open-source extension" above. This is a heavier, different-shaped commitment than every other item in this doc (replacing a vendor binary instead of writing a config delta into one), so it needs the same explicit sign-off as the live-DB write question below, not a default yes.
  5. If the actual goal is blocking rather than intercepting, prefer chat.disableAIFeatures: true — a real, working, documented VS Code core setting today, unlike interception. Use AllowedExtensions (registry-backed) instead when the block needs to survive a user undoing it. See "Alternative goal: disable/hide Copilot Chat entirely" above.
  6. Microsoft 365 Copilot app: no further action recommended. Flag to whoever raised the original report that it's a different product with a different backend, not a coverage gap in this adapter.
