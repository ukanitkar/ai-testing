VS Code's built-in GitHub Copilot Chat extension — interception design and shipped implementation

This doc is the single record for one specific surface: the Copilot Chat extension built into VS Code (github.copilot-chat / github.copilot) — distinct from the standalone copilot CLI (github/copilot-cli, npm @github/copilot), which our ai-gateway/agent-manager/src/agents/copilot.rs adapter already brokers today, and distinct from the separate desktop GitHub Copilot app (github.com/features/ai/github-app), which has its own investigation elsewhere. Split out from the broader copilot-desktop-apps-coverage-gap.html write-up because this surface now has a resolved mechanism, a real shipped implementation, and a known open risk — enough to stand on its own.

Where this stands, as of 2026-09-20: the interception mechanism is source-confirmed and live-tested end to end against real, authenticated traffic (a real model reply round-tripped through the relay). It is now wired into the real ai-protect/ai-gateway product, shipped enabled: true. The one open gap — whether the mechanism's activating condition (enterprise: true on the account's auth provider) is ever true for a real customer account — is unresolved and explicitly accepted as a known risk, not silently glossed over.

1. Why this is a separate problem from the CLI

ai-gateway/agent-manager/src/agents/vscode.rs sets llm: LlmRouting::None and is dormant ("vscode" isn't in ENABLED_AGENTS) — deliberately, and correctly. Discovery maps a vscode session to the copilot broker identity purely for attribution ("Copilot Chat is the agent behind the editor," per its own doc comment), but copilot.rs's actual redirect mechanism writes to ~/.copilot/mcp-config.json / ~/.copilot/settings.json — the standalone CLI's home directory, which the VS Code extension never reads. The extension runs inside VS Code's own process, configured through VS Code's own settings.json, with its own independent code path for finding its API host. Nothing about brokering the CLI carries over to it.

2. Mechanisms ruled out before this one

Three independent leads were checked and closed, in order, before the mechanism below was found. Recorded briefly here since each answers "why not just do X":

  • The extension's own debug settings (github.copilot.advanced.debug.overrideProxyUrl / overrideCapiUrl) exist, but a confirmed GitHub issue shows github.copilot-chat ignores them entirely — only the older, separate inline-completion extension (github.copilot) honors them.
  • The generic HTTPS_PROXY/NODE_EXTRA_CA_CERTS mechanism every other adapter in this codebase relies on: GitHub's own docs document it as supported, but real user reports say the extension ignores NODE_EXTRA_CA_CERTS outright, and checking Microsoft's own current design doc directly (agentHost/node/claude/CONTEXT.md, filed under "Deferred for later phases") confirms proxy support for this traffic is not yet implemented — the one real call site for the extension's proxy-env helper wraps only the managed-settings fetch, not chat/completion traffic.
  • BYOK (chatLanguageModels.json) is strictly additive — it registers a new selectable model next to Copilot's own in the model picker, requiring manual/pinned selection. It cannot redirect or intercept Copilot's own default traffic.

3. The mechanism that works: github-enterprise.uri CAPI-discovery hijack

Traced end to end against the real, current microsoft/vscode source (src/vs/platform/agentHost/, not a guess or a summarized doc):

  1. github-enterprise.uri (product.json's defaultChatAgent.providerUriSetting, read in defaultAccount.ts's getEnterpriseUrl()) is parsed as a URL.
  2. Its protocol/hostname/port build a discovery request: ${protocol}//api.${hostname}${port}/copilot_internal/user. A consumer account with no enterprise URI set calls the same path against the fixed https://api.github.com/copilot_internal/user instead.
  3. That response's endpoints.api field becomes the CAPI host used for every subsequent chat/completion call. A code comment in githubEndpoints.ts states the key property directly: endpoints.api "is not derivable from the enterprise URI" — the client trusts whatever the discovery response says, verbatim, with no independent validation.

That last property is what makes the hijack possible: point github-enterprise.uri at a local listener, answer (or relay, rewriting only that one field) the discovery call, and every later CAPI request the extension makes goes to that listener instead.

VS Code (Copilot Chat)        our local listener              real api.github.com        real CAPI backend
        |                          |                                  |                          |
        |-- GET /copilot_internal/user -->|                            |                          |
        |                          |-- relay real request (real auth) ------------->|              |
        |                          |<---------------- real 200 response ------------|              |
        |                          |                            |                          |
        |                    [ rewrite ONLY endpoints.api to point back    |                          |
        |                      at our listener; pass everything else       |                          |
        |                      through unmodified ]                        |                          |
        |<-- 200 { endpoints: { api: "http://127.0.0.1:<port>" } } |                          |
        |                          |                            |                          |
        |----------------------------- POST /chat/completions -->|                          |
        |                          |-- relay/observe, forward to real CAPI --------------------------->|
        |                          |<----------------------------------------------- 200 { completion } |
        |<---------------- 200 { completion } -------------------|                          |

Note on this diagram: only the first hop (GET /copilot_internal/user, the discovery call) is actually a direct local call in the shipped listener. The second hop (POST /chat/completions, drawn above as "relay/observe, forward to real CAPI") is simplified for this diagram — the real listener does not call CAPI directly at all. §4 below covers why: it tunnels that leg through Optimus instead, for the same policy enforcement every other brokered agent gets. Don't read this diagram as the shipped shape; it's the mechanism in isolation, before Optimus enters the picture.

A known, separate hole in the same mechanism: GitHub's hosted MCP server uses a second, independent hardcoded literal (GITHUB_DOT_COM_COPILOT_API_BASE_URI = 'https://api.githubcopilot.com') in githubMcpDefinitionProvider.ts, not derived from endpoints.api. Redirecting CAPI discovery leaves that traffic (if the user has GitHub's hosted MCP server configured) going to the real host, untouched. "Hijack all inference calls" overstates it — this is a CAPI-chat/completion-specific lever.

3.1. The account-gate finding: the central limitation

Live-tested 2026-09-18 against a real, authenticated, actively-used GitHub account, with real test tooling (ai-gateway-simple relaying + rewriting endpoints.api, ai-protect-simple writing github-enterprise.uri into the real settings.json). Result across two attempts (a cold VS Code restart, then a full Copilot sign-out/sign-in): zero requests reached the listener either time. Chat worked completely normally, on whichever path it already had.

Traced to the exact source-level reason, not left as a guess:

private getEntitlementUrl(): string | undefined {
    if (this.getDefaultAccountAuthenticationProvider().enterprise) {
        // ... only here does the enterprise-derived URL ever get used ...
    }
    return this.defaultAccountConfig.entitlementUrl; // the hardcoded api.github.com default
}

getDefaultAccountAuthenticationProvider(): IDefaultAccountAuthenticationProvider {
    if (this.defaultAccountProvider) {
        return this.defaultAccountProvider.getDefaultAccountAuthenticationProvider();
    }
    return { ...this.defaultAccountConfig.authenticationProvider.default, enterprise: false };
}

For an ordinary VS Code install with no special defaultAccountProvider registered — the normal case, for every consumer sign-in — enterprise is a hardcoded false. github-enterprise.uri is never even read for this decision. Not caching, not session staleness — a structural gate a settings.json value cannot flip on its own. Reaching it for real needs a genuinely different, deeper mechanism (a distinct IDefaultAccountProvider, plausibly tied to signing in through an actual GitHub Enterprise-flavored flow) that no config write reaches.

3.2. Proving the mechanism anyway: vscode-enterprise-simple

Built specifically to test the relay-and-rewrite mechanism independent of the account-gate above, by reproducing exactly what defaultAccount.ts does when an account is flagged enterprise: true: derive the discovery URL from github-enterprise.uri with the same api.<hostname> formula, call it, then make a real CAPI request.

Run with a real, working Copilot bearer token (obtained via the genuine GitHub OAuth device flow — the same mechanism editor extensions use, run interactively with real user authorization; ai-gateway/scripts/get_copilot_token.sh and copilot_chat_call.sh, token.txt itself gitignored):

  • Step 1 (discovery): 401 Bad credentials — expected. This bearer token is the Copilot-specific one from the /copilot_internal/v2/token exchange, not the raw GitHub OAuth token discovery wants. A known token-type mismatch, not a failure of the mechanism.
  • Step 2: a genuine, authenticated GET {gateway_url}/models call — relayed to the real api.githubcopilot.com and back: 200 OK, a real 52KB model list. A listing endpoint, not inference — worth being precise about, since it doesn't by itself prove a real completion works.
  • Step 3 (the actual proof): a real POST {gateway_url}/chat/completions — relayed the same way: 200 OK, a genuine response from a real model (gpt-4o-2024-11-20 replied "Hello!" to the test prompt, with real token accounting — prompt_tokens: 14, completion_tokens: 2). An actual inference call, generated by a real model, round-tripped intact through the relay.

Net result: the relay-and-rewrite mechanism is proven correct with real, authenticated traffic, not just structurally plausible. The one remaining gap is exactly the account-gate one above — getting a real account's authentication provider flagged enterprise: true in the first place, which no config write reaches. If that gap is ever closed (a genuine GHE-flavored sign-in, or a different IDefaultAccountProvider), everything downstream of it is now known to work.

A narrower, separate gap worth stating plainly: "proven correct" above covers the CAPI leg (/models, /chat/completions), not the discovery leg's own rewrite. Step 1's 401 means the discovery call never got far enough to return a 200 with a real endpoints.api field — so the one thing this mechanism is actually named for (rewriting endpoints.api to point back at the listener) was never observed happening against a real response. What was live-tested on that leg is narrower than it sounds: the relay correctly forwards the request and passes a failure response through untouched when there's nothing to rewrite. That the rewrite itself works is established by reading githubEndpoints.ts and the two copilotApiService.test.ts tests (§3), not by watching it happen. Getting a real 200 here would need the other token — a raw GitHub OAuth token, not the Copilot-specific one either test tool acquires — which is a different OAuth flow neither script obtains today.

4. Architecture problem found when wiring this into the real product

The test tools above (ai-gateway-simple) make direct, real outbound HTTPS calls — that's how they could relay to api.github.com and api.githubcopilot.com themselves. The real ai-gateway listener does not work that way: Gateway::dial() always tunnels through the configured Zscaler cloud gateway ("Optimus"), never a direct outbound call. A destination/upstream field is a label — a Host/:authority value telling Optimus where to route the request server-side — never resolved, never dialled locally. Porting the test-tool mechanism verbatim into the real listener would have meant either bypassing Optimus for all Copilot traffic (losing policy enforcement on the actual LLM calls) or somehow tunneling the discovery call through Optimus too (pointless — it's account entitlement metadata, not agent traffic that needs inspection).

Resolved design: the discovery leg (/copilot_internal/user) is answered entirely locally — one real outbound call to api.github.com, then a rewrite of the single endpoints.api field — deliberately bypassing Optimus. Every other request (the real chat/completions traffic) still tunnels through Optimus via the existing, unmodified relay path, exactly like every other agent this codebase brokers. Both legs share one listener, one port — distinguished purely by request path.

                         ┌─────────────────────────────┐
 VS Code Copilot Chat ──▶│  ai-gateway listener (single │
                         │  port, path-dispatched)      │
                         │                               │

                         │    (rewrite endpoints.api)    │
                         │                               │
   /chat/completions,    │──▶ Optimus tunnel ──▶ policy ──▶ real CAPI

5. Shipped implementation (real ai-protect/ai-gateway, commit a47e68f0)

Landed on branch main-08272026-vscode-copilot, 2026-09-20, across three real crates:

  • LlmRouting::CopilotDiscoveryRelay { upstream, enabled } (ai-gateway/agent-manager/src/agents/mod.rs) — a new routing variant, deliberately minimal (mirrors BaseUrl's shape) since the config-render side reuses the existing Llm::ProxyPath shape unmodified.
  • ListenerTransport::CopilotDiscoveryRelay (ai-gateway/agent-manager/src/agent.rs) — plaintext, like Http (no CA needed), dispatched to a distinct listener kind. Spec::listener_transport() derives this automatically from the agent's declared LlmRouting variant rather than requiring a separate per-agent override, so the two cannot drift apart.
  • listener::kinds::copilot_discovery (ai-gateway/listener/src/kinds/copilot_discovery.rs) — the actual listener logic. Checks whether the request path is /copilot_internal/user; if so, makes the one real outbound HTTPS call (via hyper-rustls + hyper-util's client-legacy, pinned to the same aws-lc-rs crypto backend this crate already standardizes on) and rewrites the endpoints.api JSON pointer to the listener's own base URL; otherwise falls through to the exact same forward()/Optimus-tunnel primitive every other BaseUrl agent uses.
  • The vscode-copilot AgentSpec (ai-gateway/agent-manager/src/agents/vscode_copilot.rs) — registered and enabled in ENABLED_AGENTS, upstream api.githubcopilot.com, hints on the code command, VS Code app bundles, and the github.copilot-chat/github.copilot extensions.
  • The agent_configs.rs registry entry (ai-gateway/util/src/agent_configs.rs) — the root ai-warden daemon's own separate config-delivery registry (consumed directly by src/subscribers/ai_broker_launch.rs), pointing at the real per-OS VS Code settings.json and rendering github-enterprise.uri via the existing Llm::ProxyPath shape.

Verified with a full cargo test --workspace pass (3989 passed; only the two pre-existing, environment-specific failures remain — a real ai-protect daemon already running on the dev machine, unrelated to this change).

6. The open risk, shipped anyway by explicit product decision

The mechanism is confirmed correct end to end with real traffic. What is not independently verified is whether the activating condition — an account whose authentication provider is flagged enterprise: true — is ever true for any real customer account. Every live test so far has been against either a real consumer account (where the mechanism correctly never activates) or a synthetic reproduction of the enterprise code path (vscode-enterprise-simple), never a genuine GitHub Enterprise-flavored sign-in. That gap is real and currently open.

Given that, the default recommendation would be to ship this disabled until a real enterprise-flagged account can be tested against it. The explicit product decision, made deliberately, was the opposite: build it and enable it now (enabled: true in the shipped AgentSpec) rather than gating it behind a flag pending that verification. The doc comment on vscode_copilot.rs states this plainly, so the decision is legible to whoever reads the code next, not just this write-up.

7. Testing this on a real machine

vscode-enterprise-simple needs a real Copilot bearer token in its Authorization header for every call — regardless of whether the real ai-protect/ai-gateway pair is running. Two ways to get one:

  • Run ai-gateway/scripts/get_copilot_token.sh (real GitHub OAuth device flow, needs bash — WSL or Git Bash on Windows) wherever is convenient, then copy the resulting token.txt to wherever vscode-enterprise-simple will run (--token-file accepts any path).
  • Reuse an already-minted token.txt, provided it's still within its ~24h validity window.

For the mechanism itself to have anything to relay against, the real ai-protect/ai-gateway daemon needs to already be enrolled, running, and have detected VS Code + the Copilot Chat extension — i.e. it must have written github-enterprise.uri into the real settings.json before vscode-enterprise-simple is run without a --gateway-url override.

8. Alternatives considered, and why this one was chosen

  • Fork the open-source extension (microsoft/vscode, MIT) for certainty instead of hoping the vendor binary honors a setting. Rejected for now: replaces a vendor binary rather than writing a config delta into one (a first for this codebase's adapter model), needs ongoing rebasing onto a fast-moving upstream, and carries a distribution/policy cost well beyond anything else in this doc.
  • Block instead of intercept (chat.disableAIFeatures: true, or the more durable AllowedExtensions registry policy on Windows) — a real, working, documented lever today, but it answers a different question ("stop Copilot Chat from running at all") than the one this doc is about ("observe/relay its traffic").
  • Replace with another extension (Continue, the Claude Code extension) — neither is a clean single-swap replacement; Continue is proxy-aware and covers autocomplete, Claude Code is already a proven, brokered agent in this product but has no autocomplete surface. Orthogonal to intercepting Copilot Chat itself, not a substitute for it.
