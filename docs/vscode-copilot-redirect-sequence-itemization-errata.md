# Errata — `vscode-copilot-redirect-sequence-itemization.pdf`

That PDF was generated **2026-10-14** and is a hand-authored diagram with no
Markdown source in this repo, so unlike `crash_safety.pdf` it cannot be
regenerated by `scripts/render-doc-pdf.sh` — refreshing it means re-drawing
page 1 and losing the click-through badge links. This file records what has
changed since, so the PDF stays usable rather than being quietly wrong.

**The 16-step sequence itself is still correct.** Everything below is a
precondition or a caveat the itemization pages do not yet carry. Read the PDF
for the flow, this file for the deltas.

## 1. The diagram only became accurate after a bug was fixed (2026-10-15)

When the PDF was generated, a `redirect` rule **also installed a block filter**
at `ALE_AUTH_CONNECT` for the same destination + process —
`compute_filters_with_conflicts_and_labels` skipped only `RuleAction::Audit`
before deriving `permit = matches!(rule.action, RuleAction::Allow)`, so
`Redirect` fell through as a block. The diagram does not depict that step
because nobody knew it was there.

It mattered most where the redirect could not work at all: on a device without
the driver the redirect filter add fails ("no such callout") while the block
installs fine, so authoring a redirect rule **blocked** the agent's traffic —
the exact inverse of the diagram. Fixed in `ai-protect` commit `e86b59bc`
(`Redirect` now skipped alongside `Audit`, two tests pinning it). After that
fix the diagram's "connect → redirect → listener" path is the only thing that
happens, as drawn.

## 2. Steps 4→5 now have a second gate: listener liveness

The PDF's step 4 says `listener_mappings()` returns empty unless
`ZSAI_NETFLT_TEST_LISTENERS` is set. That is still true but no longer
sufficient. `net_egress::live_listeners` (added `ai-protect` `6d5f4901`) now
sits between step 4 and step 5 and drops any mapping whose `{pid, port}` is
not currently a listening IPv4 TCP socket. If the socket table cannot be read
at all, every mapping is dropped rather than trusted.

So **step 5 (`FwpmFilterAdd0`) does not happen** for a stale or invented
`{pid, port}`, where previously it would have. This is deliberate: a redirect
filter aimed at a dead port does not fail open — the agent's connect lands on
a closed port and is RST, severing traffic that would otherwise have reached
the real destination.

⚠️ **Practical consequence for anyone following the PDF on the test box:**
setting the env var to a made-up pid, or to a throwaway listener that has since
restarted on a new ephemeral port, now installs **no filter at all** and looks
identical to "the mechanism is broken". Start the listener first, read its real
pid and bound port, then set the variable and restart the daemon. Procedure:
`ai-protect`'s `driver/zsai-netflt/README.md`, "Exercising the CONNECT_REDIRECT
half end to end".

## 3. A rule needs four things, not three

The PDF's step 2 notes that the rule "already passed `action == Redirect` and
`constrains_scope()`". `constrains_scope()` now additionally requires
`redirect_agent` for a Redirect rule (`ai-protect` `e86b59bc`). Previously a
rule with a destination and a process but no `redirect_agent` passed every
check, warned about nothing, and installed nothing — the one malformed shape
an operator could not debug.

## 4. An inert rule now says why

Each of the silent `continue`s in `compute_redirect_filters` — unresolved
destination, no observed process, no live listener — now produces a
change-gated `redirect rule(s) installed no filter` warning naming the empty
dimension (`ai-protect` `1ff6e149`). The PDF depicts the success path only; if
you see no filter, that log line tells you which of the PDF's preconditions is
missing.

## 5. Destinations are IPv4-only, and that is indistinguishable from "not yet resolved"

`TargetKind`/`DnsMapping` carry `Ipv4Addr`, so only observed **A** records ever
produce a target. A destination the box reaches over IPv6 never resolves and
never gets a filter, and the daemon cannot tell that apart from "no DNS answer
observed yet" — nothing records AAAA. The driver registers a complete
`ALE_CONNECT_REDIRECT_V6` callout the daemon has no way to drive.

Real IPv6 coverage is **open** (it means v6 variants across all of
`net_egress`, including the block/allow path that shares those types). Only the
silence was fixed.

## Still accurate, no change

Steps 1, 3, 6, 7, 8, 9, 11, 13, 14, 15, 16 and the "NOT IMPLEMENTED" markings
on steps 4 and 10 and on step 12's `SIO_SET` half. The Tally page's headline —
that the missing `ListenerMapping` producer gates the whole daemon-driven
pipeline — also still holds; there are simply now two gates at that point
rather than one.
