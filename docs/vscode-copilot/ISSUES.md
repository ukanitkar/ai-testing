## Issue 2: ai-gateway broker never authenticates — "no usable OIDC config" (superseded by Issue 3)

- **Where**: DVM, real MSI install, device enrolled into `aigateway-i` (staging, ai-protect console/device-plane tenant).
- **What**: `ai-gateway`'s `debug-service.log` on every cold start: `WARN agent_manager: [agent-manager] the snapshot carried no usable OIDC config — a cold start with no cached credential cannot authenticate`. The gateway process runs and is healthy, but never authenticates to anything (Vector/Bumblebee/Optimus), so no agent ever gets wired.
- **Initial framing (now refined by Issue 3)**: `aigateway-i` is the **device-enrollment** tenant, separate from `aibroker-engineer` (`ukanitkar2@aibroker-engineer.zslogin.net`), the tenant Optimus actually recognizes for the gateway's own OIDC. The device-plane snapshot (`.broker.zip`) pushed to the gateway carried no `ai_gateway.{cloud,issuer}` at all, so the gateway had no issuer to even attempt a login against.
- **First workaround tried**: author `<broker owner home>/.zsai-gateway/init.yaml` (`cloud: prod`, `oidc.issuer: https://aibroker-engineer.zslogin.net/` — the exact values proven to work on the real macOS Optimus e2e run, per `ai-testing/docs/ai-gateway-dvm-local-device-plane.md`) as a local fallback layer (`src/subscribers/ai_broker_launch.rs`'s two-layer tenant resolution: pushed settings win, blank falls to `init.yaml`, never to a compiled default).
- **Outcome**: `init.yaml` was correctly read and merged (`.broker.zip`'s `tenant.cloud`/`tenant.oidc.issuer` confirmed correct via direct decompression), but the warning **still fires** — see Issue 3, the real reason why.

## Issue 3: `tenant_from_with`/`tenant_from_init` never merge `oidc.client_id` (or any other `Oidc` field) from either layer

- **Where**: `src/subscribers/ai_broker_launch.rs`.
- **The bug**:
  - `tenant_from_with` (lines ~756-774) builds `Oidc { issuer: or_local(&field("issuer"), &init.oidc.issuer), ..Oidc::default() }` — only `issuer` is ever merged from pushed `settings.ai_gateway` or `init.yaml`. `client_id`, `audience`, `scope`, `authorize_path`, `token_path`, `discovery_path`, `tenant_id_claim` always fall to `Oidc::default()`'s empty string, **no matter what either layer supplies**.
  - `tenant_from_init` (lines ~776-782) has the same gap for the local-only path.
  - The daemon's own `InitOidc` struct (lines ~717-721) doesn't even have a `client_id` field — `init.yaml` has no way to supply one locally today.
  - Meanwhile `AgentManagerConfig::oidc_is_usable()` (`ai-gateway/agent-manager/src/config.rs:138`) requires **both** `issuer` and `client_id` non-empty, and logs the Issue-2 warning when it fails.
  - There IS a sensible fallback — `or_default(&oidc.client_id, &defaults.client_id)` → `"zax.client"` — but it's in `ai-gateway/service/src/control/watcher.rs:232`, applied only when later building the actual OIDC request params, **after** `oidc_is_usable()` has already gated and logged the warning.
- **Net effect**: as currently written, `oidc_is_usable()` can never pass through the real tenant-config path (`init.yaml` or real backend push) — nothing upstream of the check ever populates `client_id`. This reproduces on a from-scratch DVM regardless of tenant/environment; it isn't specific to `aigateway-i`/staging.
- **Verified by**: decompressing `.broker.zip` directly after the Issue-2 `init.yaml` workaround — `tenant.oidc.client_id` was confirmed empty (`""`) despite `issuer` being correctly populated.
- **Fix landed**: commit `bd06897` adds `client_id` to `InitOidc` and merges it in both `tenant_from_with`/`tenant_from_init`, same precedence rule as `cloud`/`issuer`. New unit test `client_id_follows_the_same_override_rule`.
- **Confirmed working on the DVM**: rebuilt as ad-hoc `0.5.117-staging`, reinstalled, `init.yaml` updated to add `client_id: zax.client`. Decompressing `.broker.zip` after the restart shows `tenant.oidc.client_id: "zax.client"` correctly populated alongside the correct `issuer`.
- **The recurring warning is a red herring, not evidence the fix failed**: `ai-gateway/service/src/control/watcher.rs::run()` calls `AgentManager::new(manager_config(config, None))` **once, unconditionally, before ever reading `.broker.zip`** (line 55) — this bootstrap construction always has a blank `issuer` (no default exists for it) and therefore always logs the Issue-2 warning, on every cold start, regardless of config correctness. The *real* manager gets rebuilt immediately after with the actual file (line 89) and, in every observed log, does **not** log a second warning — consistent with that rebuild now passing `oidc_is_usable()` since the fix landed. Worth a follow-up cleanup (move or gate that bootstrap warning so it doesn't look like a live failure every single time), but not a functional bug.

## Issue 4: `vscode-copilot` is never a candidate in ai-broker's own discovery — folds into `copilot`, which then fails its own install-match

- **Where**: `src/subscribers/ai_broker_launch.rs::client_label_to_broker_id` (~line 1942) and `discovered_broker_agents()` (~line 1206).
- **What**: this is the discovery path that actually populates `.broker.zip`'s "agents" list (distinct from `zscaler-ai-gateway --agents`, which correctly reports `vscode-copilot installed=true` via its own, separate `BinaryHints`-based detection). `client_label_to_broker_id` explicitly folds VS Code's discovery signal into the **`copilot`** id, not a `vscode-copilot` one: `"copilot" | "vscode" => "copilot"`.
- **Symptom**: `daemon.log` repeats `"[ai-broker] agent 'copilot' is configured but no install matched: extensions [\"github.copilot\", \"github.copilot-chat\"], npm [\"@github/copilot\"], pypi [], apps [], commands []"` and `"discovery: no broker-known agents installed"` on every reconcile — even though VS Code and both Copilot extensions are genuinely installed on the DVM (confirmed earlier via `winget`/`code --list-extensions`, and via `--agents` showing `vscode-copilot installed=true`).
- **Root-caused**: `extension_metadata()` → `crate::tasks::ide::vscode::find_extensions()` (`src/tasks/ide/vscode.rs:76-96`, `collect_extensions`) only reads `<vscode home>/extensions/extensions.json` — the catalog of **marketplace-installed** extensions. VS Code 1.142 (confirmed on the DVM) ships `github.copilot`/`github.copilot-chat` as a **built-in** extension (version `0.69.0`) bundled inside VS Code's own install directory (`...\resources\app\extensions\`), which is **never registered in `extensions.json`** — built-ins and marketplace extensions are tracked completely differently by VS Code itself. So `find_extensions(["github.copilot", "github.copilot-chat"])` finds nothing, not because Copilot isn't installed, but because this detection code has no path for the built-in case at all. This predates this session — VS Code started bundling Copilot Chat as built-in relatively recently, and `src/tasks/ide/vscode.rs`'s detection wasn't updated for it.
- **Fixed (Windows/stock VS Code only)**: `src/tasks/ide/vscode.rs` — new `collect_builtin_extensions()`, producing the exact same `Extension` shape `collect_extensions()` does (same `name` convention: `publisher.name`, lowercased, matching the marketplace catalog's `identifier.id`). Wired into `find_extensions()`'s same cache-population loop, so **every** existing/future caller (`claude`, `codex`, `copilot`, …) benefits automatically — no per-agent special case.
  - **First attempt assumed `resources/app/extensions` sits directly under the install root — wrong.** Live-checked on the DVM: `%LOCALAPPDATA%\Programs\Microsoft VS Code\resources\app\extensions` doesn't exist at all. Windows' background updater stages the real build under an opaque **hash-named subdirectory** instead (`<root>\16507d91be\resources\app\extensions\copilot\package.json` — an in-place update even left a second stale hash dir, `2d0b7506a3`, coexisting). Fixed by checking both the direct layout and one level of hash-subdirectory indirection; a stale leftover hash dir just produces a harmless duplicate row.
  - Manifest field assumption (`name: "copilot-chat"`, `publisher: "GitHub"`) was confirmed correct against the real file — only the path was wrong.
  - Four unit tests: `a_builtin_extension_is_found_without_an_extensions_json_entry`, `a_builtin_extension_under_a_hash_named_update_subdir_is_found` (the real layout), `a_malformed_builtin_entry_is_skipped`.
- **Full live confirmation (2026-10-22, DVM, real backend)**: with this fix plus Issue 3's, the daemon's per-agent miss list no longer includes `copilot` at all, `.status.zip` showed `1 enrolling`, and the gateway log showed the real OIDC→Vector→Bumblebee→triple-JWT chain completing, ending in `agent 'copilot' WIRED — 2 config delta(s)`. See Issue 5 for what that actually wired (not quite the end goal).

## Issue 5: VS Code's presence only ever surfaces the `copilot` CLI id, never `vscode-copilot`'s own

- **Where**: `src/subscribers/ai_broker_launch.rs::client_label_to_broker_id` (~line 1950) and `discovered_broker_agents()` (~line 1206).
- **What broke**: after Issues 2/3/4 were all fixed and a real end-to-end enrollment finally completed on the DVM (real OIDC, real Vector registration, real admin approval via `approve_agent.py`, real triple JWT, `agent 'copilot' WIRED`), the actual config deltas landed in **`~/.copilot/settings.json`'s `proxyUrl`** and `~/.copilot/mcp-config.json` — the standalone CLI's own files. **`%APPDATA%\Code\User\settings.json` was never touched** — confirmed via direct `Test-Path`/`Get-Content`, still absent.
- **Root cause**: `client_label_to_broker_id` maps VS Code's discovery signal to `"copilot"` **only** — `"copilot" | "vscode" => "copilot"`. There is no branch that also surfaces `"vscode-copilot"` as its own discoverable id, so `discovered_broker_agents()` never puts it into `.broker.zip`'s agent list at all. The daemon has no code path that ever tries to enroll `vscode-copilot` under its own identity — only `copilot` (the CLI), borrowed via VS Code's presence as a stand-in signal.
- **Why this matters**: this is exactly the workaround `agents/vscode_copilot.rs` was moved off of earlier this session — "a real customer has no reason to have the GitHub Copilot CLI installed." Wiring `copilot`'s identity instead of `vscode-copilot`'s own is a real, working success (proves the whole OIDC/Vector/Bumblebee chain), but not the actual target.
- **Fixed**: `discovered_broker_agents()` now also pushes `"vscode-copilot"` as a second candidate whenever a folder's label is `"vscode"`, alongside whatever `client_label_to_broker_id` already returns (today, `"copilot"`) — both now get a chance to enroll from the same VS Code presence signal. Added `sources_for("vscode-copilot")` (same extension hints as `"copilot"` — the signal is identical, only which identity gets wired differs) and added `"vscode-copilot"` to the `ALL_BROKER_IDS` test fixture so the existing completeness tests (`every_live_agent_has_a_packaging_source`, `a_reported_identity_is_always_resolvable`, etc.) cover it automatically.
- **Live-confirmed on the DVM (2026-10-23, build 0.5.120)**: `daemon.log` shows `applied config delta llm for agent 'vscode-copilot' (1 file(s))` and `.status.zip` reporting `2 agent(s) serving` (both `copilot` and `vscode-copilot`). `%APPDATA%\Code\User\settings.json` now reads `{"http.proxy": "http://127.0.0.1:8806"}` — written directly by the daemon, no manual edit.
  - No second admin approval was needed: `vscode-copilot` and `copilot` register with Vector under the **same backend `agent_type`** (`"copilot"` — see the much-earlier commit `6e516e13`, "map to backend agent_type 'copilot'"), so the one approval already done for `copilot`'s registration covered both local identities once this fix let `vscode-copilot` start enrolling too.
  - `debug-service.log` confirms real interception is live: genuine VS Code/Copilot traffic (`telemetry.individual.githubcopilot.com`, `update.code.visualstudio.com`, `main.vscode-cdn.net`) routed through `dial_target=gateway.zsagentic.ai:443`, landing at the same real Optimus IP (`137.31.194.121`) confirmed earlier this session — under `vscode-copilot`'s own identity, not borrowed from the CLI.
  - **Exercised with a real Copilot Chat prompt (2026-10-23, 19:20 UTC)**: got a correct, useful response in VS Code's Chat panel, no visible error — confirms the `intersected_caps=[]` concern from Issue 2/3 does not block the actual LLM leg. The log did show one `tunnel ended: peer closed connection without sending TLS close_notify` + a client-reported `GitHub.copilot-chat/websocket.error` in the same window, but since the UI answer was clean, that was either a transparent reconnect or a secondary/non-critical channel, not the completion delivery itself. The full chain is confirmed working end to end.
- **Deliberately not generalized yet**, per 2026-10-22 decision to focus on vscode-copilot first: scoped to stock VS Code on Windows, the one editor+OS this session could verify against. `EDITORS` lists several more VS Code-family forks (Cursor, Windsurf, Trae, …) and macOS/Linux install roots are unresolved — extend `candidates` in `collect_builtin_extensions` if/when another editor is confirmed to ship extensions the same way, and there's a box to verify a non-Windows path against.
- **Net effect**: even with Issues 2/3 fully fixed (OIDC now usable), there's nothing in the discovered-agents snapshot for the gateway to act on yet on a modern VS Code install, so no real enrollment/OIDC attempt has been observed end-to-end on the DVM.

## Issue 6 (feature, not a bug): listener now bypasses Optimus for non-MCP, non-LLM traffic

- **Where**: `ai-protect`'s `ai-gateway/listener/src/kinds/https.rs` (`BYPASS_HOSTS`, `should_bypass_optimus`) and `ai-gateway/listener/src/server.rs` (`Prepared::bypassed`, `splice_bypassed`, `dial_direct`).
- **Why**: once Issue 5 was confirmed fully working, `debug-service.log` showed real VS Code/Copilot telemetry, update checks, and marketplace/CDN fetches all being MITM'd and relayed through Optimus identically to the actual Copilot Chat traffic — `telemetry.individual.githubcopilot.com`, `update.code.visualstudio.com`, `main.vscode-cdn.net`, `mobile.events.data.microsoft.com`, `*.applicationinsights.azure.com`.
- **Two options considered** (fully documented at `BYPASS_HOSTS`'s definition in the code itself):
  1. Client-side: write `http.proxy`'s sibling, `http.noProxy`, into VS Code's `settings.json` naming these hosts.
  2. Server-side (chosen): bypass at the plaintext CONNECT stage, before any MITM, splicing raw bytes directly to the real destination instead of relaying through Optimus.
- **Why (2)**: one list to maintain at the point traffic is actually observed, and it sidesteps re-encrypting traffic the gateway was never going to act on — this exact session's own capture showed a dropped tunnel + a client-reported `websocket.error` in this same traffic class (see Issue 5's last bullet). The accepted tradeoff: bypassed traffic gets zero visibility/audit on our side — deliberate for telemetry/update/CDN noise, and exactly why an LLM or MCP destination must never be added to the list.
- **Status**: landed (commit `a04ef5e8`), `cargo test -p ai-gateway-listener` green (180 tests, 6 new), full release build clean. Dispatched as ad-hoc `0.5.121-staging` for DVM verification — not yet confirmed live on the DVM as of this note.
