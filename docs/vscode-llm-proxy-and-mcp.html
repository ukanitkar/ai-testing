VS Code — LLM Proxy & MCP Handling, Windows vs macOS

Written 2026-09-16. Distills the VS Code-specific findings from this investigation into a single design reference, organized by topic rather than by investigation order. For the GitHub Copilot desktop app and the Microsoft 365 Copilot app (neither of which is VS Code), see copilot-desktop-apps-coverage-gap.html.

Summary

Inside VS Code, three AI surfaces matter: the built-in GitHub Copilot Chat extension, Continue, and the Claude Code extension. Copilot Chat has no viable, confirmed LLM-interception path today — its own settings are dead, and the generic env-var mechanism is disputed and unresolved. Continue and Claude Code both have real, working mechanisms. That asymmetry is the basis for the recommended posture in §5: block Copilot, run Claude Code and Continue instead — not as a workaround, but because it's the only combination with a working LLM-proxy story on both platforms today.

1. The three surfaces

Surface What it is LLM routing status
GitHub Copilot Chat (github.copilot-chat) VS Code's built-in AI chat/completions, from GitHub No working redirect. See §2.1
Continue (continue.continue) Open-source, config-file-driven AI extension Real, works via apiBase. See §2.2
Claude Code (anthropic.claude-code) Anthropic's extension, wraps the same engine as the claude CLI Real, already shipped in our gateway. See §2.3

All three are installed on the reference machine used for this investigation, alongside vscodevim.vim and a Zscaler monitor extension — relevant later for the AllowedExtensions allowlist in §5.

2. LLM proxy handling, per extension

2.1 GitHub Copilot Chat — no viable path today

  • github.copilot.advanced.debug.overrideProxyUrl / overrideCapiUrl: real settings, but documented as overriding the GitHub authentication proxy only, and a confirmed GitHub issue shows github.copilot-chat ignores them entirely. Dead end, not a live option.
  • BYOK (chatLanguageModels.json): additive only — adds a selectable model next to Copilot's own, never redirects Copilot's own default traffic.
  • The generic HTTPS_PROXY/HTTP_PROXY + NODE_EXTRA_CA_CERTS mechanism (the same one that works for other agents in this codebase): disputed, not settled. GitHub's own docs say it's supported; real user reports say the Copilot agent ignores NODE_EXTRA_CA_CERTS, and the practical community workaround is bridging the OS certificate store into VS Code's trust (broader than this codebase's narrow per-agent NODE_EXTRA_CA_CERTS design). Needs a live test — point HTTPS_PROXY at the gateway's listener with NODE_EXTRA_CA_CERTS set, launch a real Copilot Chat session, check the gateway log — before this can be called either way.
  • Forking is a considered but heavy alternative, not attempted: vscode-copilot-chat is MIT-licensed but archived (moved into the microsoft/vscode monorepo, 2026-05-20). The actual injection point is small and precise (src/platform/networking/node/nodeFetchFetcher.ts's undici Agent, swapped for a ProxyAgent + custom CA), but forking means tracking the much larger vscode repo going forward, replacing a vendor binary instead of writing a config delta into one, and a deliberate policy decision about running a modified build of GitHub's product against the user's real entitlement. Not something to build without explicit sign-off.

2.2 Continue — real, working, confirmed

~/.continue/config.yaml (macOS/Linux) or %USERPROFILE%\.continue\config.yaml (Windows) — same file, same schema, no platform-specific quirks found. apiBase + requestOptions.headers genuinely redirects a model's traffic to an arbitrary endpoint; confirmed against Continue's own docs, matching field-for-field.

name: Local Config
version: 1.0.0
schema: v1
models:
  - name: Local Proxy Chat
    provider: openai
    model: <model-id>
    apiBase: http://127.0.0.1:<PORT>/v1
    roles: [chat, edit, apply]
  - name: Local Proxy Autocomplete
    provider: openai
    model: <autocomplete-model-id>
    apiBase: http://127.0.0.1:<PORT>/v1
    roles: [autocomplete]

Not yet wired into ai-gateway, and this is real, scoped work, not a config tweak: 1. A new continue.rs agent adapter (parallel to copilot.rs/devin.rs). 2. A new Llm:: render shape — every existing shape writes a scalar at a fixed nested key; Continue needs a model entry appended/upserted into a models array by name, a genuinely different write pattern. 3. YAML file support may not exist in apply_config_delta/config_render today (everything seen so far is JSON/TOML-oriented) — needs confirming, not assuming. 4. Llm::BaseUrl-style semantics fit the intent better than ForwardProxy (a straight redirect to a local URL, no CA/CONNECT-tunnel involved).

Until this is built, the port ai-gateway's listener binds to is chosen dynamically at runtime and threaded through to every other agent's config automatically — there is no static port value to hand-type into Continue's config.yaml that would stay correct.

2.3 Claude Code extension — real, working, already shipped

No new work needed here — "claude" is already in ENABLED_AGENTS and is a real, shipped, brokered agent in this codebase today. Verified specifically for the VS Code extension (not just the bare CLI), against the actual installed extension bundle (anthropic.claude-code-2.1.273-darwin-arm64/extension.js), not assumed:

  • The bundle contains HTTPS_PROXY, HTTP_PROXY, NODE_EXTRA_CA_CERTS, and ANTHROPIC_BASE_URL as literal strings, in the same table as unmistakably-CLI-internal names (CLAUDE_STREAM_IDLE_TIMEOUT_MS, MAX_THINKING_TOKENS) — it bundles the same core engine as the CLI, not a separate reimplementation. child_process/spawn(/execFile( are all present too.
  • One decisive line: vscode.workspace.getConfiguration("http").get("proxy") — the extension actively reads VS Code's own core http.proxy setting, unlike Copilot Chat, which was confirmed to do nothing of the kind anywhere in its config layer.
  • Correction made during this same investigation: the extension does not register a ghost-text inline-completion provider (an earlier, secondary-sourced claim that didn't survive checking the real bundle). Its interaction model is a chat panel plus a review/accept-reject diff workflow. Relevant if VS Code's inline-autocomplete UX matters to the rollout — Claude Code doesn't provide it; Continue does (§2.2).
  • Not yet done: a live, dynamic traffic-capture test (point HTTPS_PROXY at the gateway, launch the extension, confirm interception in the gateway log). The static evidence above is strong, but it's static analysis, not a live test — the same discipline this doc applies to Copilot Chat should be applied here too before calling it fully closed.

3. MCP handling, per extension

3.1 VS Code's own native MCP surface

VS Code has its own built-in MCP support: .vscode/mcp.json (project scope) using a servers key (not mcpServers — a real, previously-noted difference from most other agents' convention). The file is JSONC (comment-carrying), which matters for any writer that does a strict JSON upsert.

ai-gateway/agent-manager/src/agents/vscode.rs already has an AgentSpec for this surface, but it is dormant — registered in build_adapters() but not in ENABLED_AGENTS, so it ships dark. Its own doc comment states the intent plainly: "exists to wire the editor's own MCP if we ever broker it independently." Enabling it is a real option already built, not something to design from scratch — but: - The comment-preserving JSON edit needed for a JSONC file is flagged elsewhere as its own follow-up, not yet built. - Unverified in this investigation: whether GitHub Copilot Chat itself consumes this same native mcp.json surface today, or has an entirely separate MCP registration path. Worth confirming directly before assuming enabling vscode.rs covers Copilot's MCP usage too — it may only cover extensions that opt into VS Code's native MCP API.

3.2 Continue's own MCP surface

Continue has its own, separate MCP registration — an mcpServers key in config.yaml, plugging into the same context-provider surface as @terminal/@codebase/etc. This is not the same surface as VS Code's native .vscode/mcp.json; the two are independent registries, the same "an agent can have more than one MCP surface" pattern already documented for other agents in this codebase (e.g. OpenClaw's native config vs. its mcporter registry vs. its plugin-bundle MCP). No adapter exists for this today — folding it in would be additional scope on top of the LLM-routing work in §2.2, not included in it automatically.

3.3 Claude Code's MCP surface

Not yet verified in this investigation. The bare claude CLI has its own MCP configuration (project/user-scope .mcp.json or equivalent), already handled by the existing claude adapter for the CLI case. Whether the VS Code extension reads that exact same file, or has an extension-specific MCP registration path of its own, hasn't been checked here — given §2.3 found the extension bundles the same core engine as the CLI, the same-file answer is plausible but not confirmed. Flag as a verification item before assuming MCP coverage carries over automatically from the CLI adapter to the extension.

4. Windows vs macOS — where the solution actually differs

The LLM-proxy mechanism itself (env vars, apiBase, http.proxy) showed no platform-specific quirks in this investigation — config.yaml's schema, the extension bundle's proxy-string references, and the general env-var approach are all identical cross-platform. The real platform divergence is entirely in policy/blocking delivery — how AllowedExtensions actually reaches the machine, covered in full in §5.

Windows macOS
Policy delivery mechanism Registry (HKLM\SOFTWARE\Policies\Microsoft\VSCode) Apple Configuration Profile (.mobileconfig)
Who traditionally owns it Group Policy (AD, ADMX-templated) N/A — Apple's own profile system
Can ai-protect (elevated) write it directly? Yes, confirmed — LocalSystem has unrestricted HKLM access, existing real-world precedent (see §5) Unverified — mechanically possible (not SIP-protected), but whether it's honored/durable against MDM reconciliation is untested
MDM-native push path Intune's Settings Catalog/ADMX ingestion refuses to write this path by design (conflict-avoidance with GPO) Standard MDM profile push (Jamf/Intune-for-Mac/Workspace ONE) — no blocking mechanism found
MDM workaround if native path is blocked Intune Remediations (SYSTEM-context script, writes the registry key directly) N/A found — no equivalent blocker to work around on macOS
Manual/local install path Direct registry write (any elevated process) profiles CLI cannot install profiles as of macOS 11+ (confirmed via man profiles) — human double-click + admin auth in System Settings, or real MDM, only

5. The recommended solution: block Copilot, allow Claude Code and Continue

Step 1 — Block Copilot via AllowedExtensions. This is a strict allowlist, not a denylist: everything omitted is blocked or disabled, installed or not. The value that blocks Copilot while keeping the rest of this reference machine's actual extensions working:

{"anthropic.claude-code":true,"continue.continue":true,"vscodevim.vim":true,"zscaler.zscaler-ide-plugin-monitor":true}
  • Windows: write directly to HKLM\SOFTWARE\Policies\Microsoft\VSCode\AllowedExtensions (REG_SZ, the JSON above as the string value). ai-protect, running as LocalSystem, can do this the same way it writes every other agent's config — no new privilege model needed. If a Windows fleet is Intune-managed, don't push this through Intune's normal policy UI (it will silently no-op); use an Intune Remediation script instead, or have ai-protect write it directly regardless of what Intune does.
  • macOS: requires a .mobileconfig Configuration Profile carrying this value under the AllowedExtensions key, with PayloadScope explicitly set to System (the shipped VS Code template omits this key entirely — don't rely on whatever the undocumented default turns out to be). Installation is either a human double-click + admin auth, or a real MDM push — ai-protect cannot script this locally the way it does the Windows registry write; that's a structural platform difference, not a missing feature.
  • Two reliability caveats apply on both platforms regardless of delivery mechanism: the value can silently be ignored past roughly 1024 characters (acknowledged by a VS Code maintainer as a real limitation of the policy itself), and there is at least one unresolved public report of the policy not blocking installation in some configuration. Treat this as "documented to work," not "proven to work," until the test recipe in §6 has actually been run.

Step 2 — Claude Code needs no new work. It's already a shipped, enabled agent (ENABLED_AGENTS includes "claude"), and §2.3's static analysis shows the VS Code extension shares the CLI's proxy mechanism. The one gap is verification, not construction: run the live dynamic-traffic test before treating extension coverage as equivalent to CLI coverage.

Step 3 — Continue needs real, scoped engineering before it can be wired the same way. §2.2's four items (new adapter, new array-upsert Llm:: shape, confirming YAML support, BaseUrl-style semantics) are the concrete backlog. Until built, Continue's apiBase has no dynamically-resolved value to point at — hand-typing a fixed port is exactly the failure mode the whole config_render pipeline exists to avoid, and shouldn't be done as a stopgap.

Step 4 — MCP is optional, separate scope, not required for the LLM-proxy outcome. If MCP coverage matters for this rollout: enabling the dormant vscode.rs adapter covers VS Code's native mcp.json surface (real code, just switched off, plus the JSONC comment-preservation follow-up); Continue's own mcpServers registry would need a new adapter entirely; Claude Code's MCP surface inside the extension is unverified (§3.3). None of this blocks Step 1–3 — it's additive scope for whoever picks it up next.
